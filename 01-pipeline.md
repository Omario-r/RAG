# Пайплайн целиком: от файла договора до ответа юристу

Дата: 28.07.2026. Документ отвечает на вопрос «как это вообще работает» —
до деталей API. Детали: [02](02-chunking.md), [03](03-embeddings.md),
[04](04-qdrant.md), [05](05-retrieval-rerank.md).

## Идея в одном абзаце

Компьютер не умеет искать по смыслу — он умеет считать. Чтобы искать по смыслу,
текст превращают в **вектор**: список из сотен-тысяч чисел, координаты текста
в «пространстве смыслов». Тексты о похожем оказываются рядом. Тогда поиск по
смыслу = поиск ближайших точек к точке запроса, а это уже арифметика.
Векторная БД (Qdrant) хранит эти точки и умеет быстро находить ближайших
соседей среди миллионов.

## Два контура: подготовка и запрос

**Контур A — индексация (offline, редко, долго):**

```
файл договора
  → извлечение текста (docx/pdf → текст + структура)
  → чанкинг: резка на смысловые куски (пункты договора)
  → векторизация каждого чанка (llama.cpp API) → вектор [0.021, -0.14, ...]
  → пойнты: id + вектор + payload (текст чанка, № договора, № пункта, стороны…)
  → пакетная загрузка в Qdrant
  → (параллельно) формальные реквизиты → SQL-БД
```

**Контур B — запрос (online, часто, быстро):**

```
вопрос юриста
  → (опционально) фильтр по SQL/payload: только договоры такого-то типа
  → векторизация вопроса ТОЙ ЖЕ моделью
  → поиск в Qdrant: top-50 ближайших чанков (грубо, но быстро)
  → реранкер: пересортировать 50 → оставить top-5 (медленно, но точно)
  → сборка контекста: 5 чанков + их метаданные
  → главная LLM: ответ со ссылками на пункты договоров
```

Асимметрия «долго/быстро» — не дефект, а суть конструкции: тяжёлую работу
делаем один раз при загрузке, чтобы запрос отрабатывал за доли секунды.
Отсюда и наблюдение партнёра, что insert дороже поиска.

## Почему запись в векторную БД дорогая

Полезно понимать механику — иначе борьба за скорость загрузки идёт вслепую.

Терминология: отдельной операции `insert` в Qdrant нет — запись всегда идёт
через **`upsert`** (update + insert): «нет пойнта с таким `id` — вставить,
есть — перезаписать». Слово «insert» ниже и у партнёра означает вставку данных
вообще, а не команду. Практическое следствие — в [04-qdrant.md](04-qdrant.md):
при детерминированном `id` повторная загрузка договора заменяет свои же чанки
и не плодит дубли.

При `upsert` происходит две разные вещи:

1. **Запись данных** — точка попадает в WAL (журнал) и в сегмент. Это быстро,
   сравнимо с обычной БД.
2. **Построение индекса HNSW** — вот это дорого. HNSW (см. [04](04-qdrant.md)) —
   многослойный граф соседства: чтобы вставить новую точку, надо найти её
   потенциальных соседей среди уже существующих и перестроить связи. Стоимость
   растёт с размером коллекции и с размерностью вектора.

Индекс строится **фоновым оптимизатором**, а не в момент вставки. Поэтому:

- `upsert` может вернуть «ок» быстро, а нагрузка на сервер будет продолжаться;
- главный приём ускорения массовой загрузки — **временно отключить построение
  индекса**, залить всё, включить обратно и дать построиться один раз. Это и
  есть та «особенность», которую партнёр не вспомнил; подробности и точные
  параметры — [04-qdrant.md](04-qdrant.md#быстрая-пакетная-загрузка).
- GPU-ускорение индексации (Qdrant 1.13+, до 10× против CPU) удешевляет именно
  шаг 2, но не отменяет приём выше.

## Где в этом пайплайне ломается качество

Порядок — по частоте, с которой это оказывается настоящей причиной плохих
ответов. Полезно держать перед глазами: чаще всего виноват не «тупой ИИ».

| # | Место | Типичный симптом | Разбор |
|---|---|---|---|
| 1 | **Чанкинг** | Ответ есть в договоре, но поиск его не находит: пункт разрезан пополам, или чанк вырван из контекста («в течение 5 дней» — а чего?) | [02](02-chunking.md) |
| 2 | **Асимметрия запрос/документ** | Поиск работает «примерно никак»: модели требуются префиксы (`search_query:` / `search_document:`), а их не поставили | [03](03-embeddings.md) |
| 3 | **Модель эмбеддингов** | Русский юртекст ложится плохо, синонимы не сближаются | [03](03-embeddings.md) |
| 4 | **Отсутствие фильтров** | Ищем по всему корпусу там, где надо было по одному договору | [04](04-qdrant.md) |
| 5 | **Нет реранкера** | В top-5 попадает мусор, «похожий по словам, не по смыслу» | [05](05-retrieval-rerank.md) |
| 6 | Модель-ответчик | Ответ красивый, но не по документу | вне этого волта |

Отсюда практический вывод для нашего этапа: **сначала измеряем retrieval
отдельно от генерации**. Если нужный чанк не попал в top-k, никакая главная
модель это не исправит — она просто уверенно ответит по неверному куску.

## Разделение зон: SQL vs вектор vs фильтр

Три типа вопросов и правильный инструмент для каждого:

| Вопрос юриста                                                                | Инструмент                  | Почему                                                                              |
| ---------------------------------------------------------------------------- | --------------------------- | ----------------------------------------------------------------------------------- |
| «Договоры с ООО «Ромашка», истекающие в декабре»                             | SQL (или фильтр по payload) | Точный факт, ответ обязан быть полным и достоверным                                 |
| «Где условия о простое транспорта под погрузкой?»                            | Векторный поиск             | Формулировки в договорах разные: «простой», «сверхнормативное ожидание», «демередж» |
| «В договорах с этим перевозчиком — что про ответственность за утрату груза?» | Фильтр + вектор             | Сначала сузили множество, потом искали смысл                                        |

Третья строка — самый частый реальный случай, и она объясняет, почему
метаданные в payload обязательны, а не «потом добавим». Фильтрация в Qdrant
работает совместно с векторным поиском (filterable HNSW), а не как
постобработка.

Откуда в SQL берутся реквизиты, если договоры нетиповые и все разные —
отдельная и непростая тема: [07-extraction.md](07-extraction.md). Коротко:
парсером нельзя (у каждого контрагента свой шаблон), извлекает модель по
жёсткой схеме, а защита от выдуманных значений — обязательная цитата,
проверяемая кодом на точное вхождение в документ.

## Что считать успехом на этом этапе

Не «работает», а измеримо:

1. Корпус из ~10 договоров загружается воспроизводимо, время загрузки известно.
2. Есть набор из 20–30 контрольных вопросов с заранее известными правильными
   пунктами договоров («золотой набор»).
3. Измерены recall@10 и recall@50 — доля вопросов, где нужный пункт попал
   в выдачу.
4. Показан прирост от реранкера на том же наборе.

Без пункта 2 любые улучшения — вкусовщина. Формирование золотого набора —
самая скучная и самая окупаемая работа этапа; подробнее
[05-retrieval-rerank.md](05-retrieval-rerank.md#как-мерить-качество).
