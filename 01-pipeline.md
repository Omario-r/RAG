Поиск по смыслу сводится к арифметике: текст превращается в вектор — точку в пространстве, где похожее лежит рядом, — и поиск становится поиском ближайших соседей. Что такое эмбеддинг и почему это работает — [[База знаний/02-definition/README|02-definition]].

## Как стоит сейчас

Стенд поднимается одной командой `./start-stand.sh` и держит четыре сервиса:

| Сервис | Порт | Что стоит |
|---|---|---|
| Qdrant | 6333 / 6334 | коллекция `contracts_v1`, 1446 пойнтов, HNSW не построен |
| Эмбеддер | 8080 | `Qwen3-Embedding-0.6B` Q8_0, 1024 измерения |
| Реранкер | 8081 | `bge-reranker-v2-m3` Q8_0 |
| Модель | 8084 | `T-lite-it-2.1` Q6_K — **только для извлечения реквизитов**, ответ юристу она не формулирует |

Сквозной путь «договор → чанки → векторы → Qdrant → поиск → реранкер» работает одной командой, с метриками и журналом. Узел ответа не собран: модель поднята, но генерации в пайплайне нет. Состояние по узлам — таблица в [README](README.md), состояние этапов — [06-roadmap.md](06-roadmap.md).

## Два контура

**A — индексация (офлайн, редко, долго):**

```
файл договора
  → извлечение текста (docx/pdf → текст + структура)
  → чанкинг: родитель с подпунктами одним чанком
  → векторизация каждого чанка (llama.cpp) → вектор 1024
  → пойнты: id + вектор + payload (текст, № договора, № пункта, стороны…)
  → пакетная загрузка в Qdrant
  → (параллельно) формальные реквизиты → SQL
```

**B — запрос (онлайн, часто, быстро):**

```
вопрос юриста
  → (опционально) фильтр по payload: только договоры такого-то типа
  → векторизация вопроса ТОЙ ЖЕ моделью
  → поиск в Qdrant: top-50 (грубо, быстро — 8 мс)
  → реранкер: 50 → top-5 (точно, медленно — 161 мс при top-10)
  → сборка контекста: 5 чанков с метаданными
  → ответ модели со ссылками на пункты   ← узла нет, см. README
```

Асимметрия «долго/быстро» — суть конструкции, а не дефект: тяжёлое делается один раз при загрузке, чтобы запрос отрабатывал за доли секунды.

**Почему запись дороже поиска.** Отдельной операции `insert` в Qdrant нет: запись идёт через `upsert`, и вместе с данными строится граф HNSW — вот он и дорог. Практическое следствие у нас: `id` детерминированный, поэтому повторная загрузка договора заменяет свои же чанки и не плодит дублей; массовая загрузка идёт пакетами по gRPC — ×22 и ×3,3 соответственно ([[04-qdrant#Быстрая пакетная загрузка|04-qdrant.md]]). Механика HNSW — в теории [[База знаний/06-vector-db/README|06-vector-db]].

## Где ломается качество

Порядок — по частоте, с которой это оказывается настоящей причиной плохого ответа. Чаще всего виноват не «тупой ИИ»:

| # | Место | Симптом | У нас |
|---|---|---|---|
| 1 | **Чанкинг** | ответ в договоре есть, поиск его не находит: пункт разрезан, чанк вырван из контекста | подтверждено на своём корпусе: провалившийся вопрос чинился правкой разбора, не моделью — [02](02-chunking.md) |
| 2 | **Асимметрия запрос/документ** | модели нужны префиксы `search_query:` / `search_document:`, их не поставили | **проверено, у нас не воспроизводится:** Qwen3 префиксов не требует — [[11-evidence#3. Префиксы-инструкции не нужны]] |
| 3 | **Пулинг и модель эмбеддингов** | русский юртекст ложится плохо | самый большой замеренный разрыв: `mean` 0,815 против `cls` 0,741 — [03](03-embeddings.md) |
| 4 | **Отсутствие фильтров** | ищем по всему корпусу там, где надо по одному договору | payload-индексы заведены — [04](04-qdrant.md) |
| 5 | **Нет реранкера** | в top-5 мусор, похожий по словам | реранкер даёт `nDCG@5` +0,154 — [05](05-retrieval-rerank.md) |
| 6 | Модель-ответчик | ответ красивый, но не по документу | узла нет; теория — [[База знаний/11-generation/README\|11-generation]] |

> [!warning] Цифры ниже сняты на партии 1 — 144 чанка
> Это вырожденная задача: `top-50` покрывал треть корпуса, и метрики стояли на потолке. На текущей коллекции в 1446 чанков тот же золотой набор даёт `hit@5` 0,562 вместо 1,000 — [[checks/runs#`RUN-20260820-A` — тот же золотой набор на выросшем корпусе|RUN-20260820-A]]. Числа партии 1 годятся для сравнения между собой и не годятся как оценка качества.

Отсюда правило этапа: **retrieval меряется отдельно от генерации.** Если нужный чанк не попал в top-k, никакая модель это не исправит — она уверенно ответит по неверному куску.

## Разделение зон: SQL, вектор, фильтр

| Вопрос юриста | Инструмент | Почему |
|---|---|---|
| «Договоры с ООО „Ромашка“, истекающие в декабре» | SQL или фильтр по payload | точный факт, ответ обязан быть полным |
| «Где условия о простое транспорта под погрузкой?» | векторный поиск | формулировки разные: «простой», «сверхнормативное ожидание», «демередж» |
| «В договорах с этим перевозчиком — что про ответственность за утрату груза?» | фильтр + вектор | сузили множество, потом искали смысл |

Третья строка — самый частый реальный случай, и она объясняет, почему метаданные в payload обязательны сразу, а не «потом добавим». Фильтрация в Qdrant работает совместно с векторным поиском, а не как постобработка.

Решение зафиксировано 28.07.2026: **SQL — источник фильтров, вектор — источник смысла, одно другим не подменяется.** Откуда в SQL берутся реквизиты, если договоры нетиповые, — [07-extraction.md](07-extraction.md).

## Что считать успехом

Не «работает», а измеримо — пороги, единицы и обоснования вынесены в контур проверок:

| Что | Где |
|---|---|
| Критерии-цели с порогами | [checks/criteria.md](checks/criteria.md) |
| Что проверяем и в каком порядке | [checks/hypotheses.md](checks/hypotheses.md) |
| Прогоны с провенансом | [checks/runs.md](checks/runs.md) |

Главное правило оттуда: **критерий — цель, а не ворота.** Пайплайн поднимается целиком, не дожидаясь, пока поиск станет хорошим; разрыв между измеренным и целевым докладывается, а не прячется.

Без золотого набора любые улучшения — вкусовщина. Его формирование — самая скучная и самая окупаемая работа этапа ([[05-retrieval-rerank#Золотой набор|05-retrieval-rerank.md]]).
