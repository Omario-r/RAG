# Лаб 6. Реранкер

Этап 6 из [06-roadmap.md](06-roadmap.md). Справочник — [05-retrieval-rerank.md](05-retrieval-rerank.md);
здесь только последовательность действий. Правила устройства лаб —
[lab-style.md](lab-style.md).

**Цель:** узнать, сколько именно даёт реранкер на нашем корпусе и стоит ли
он задержки. Лаба заканчивается модулем `rag_lab/rerank.py`, встроенным
каскадом и ответом на вопрос про глубину: сколько кандидатов ему давать.

**Лаба поправляет утверждение волта.** Решение от 08.08.2026 гласило, что
корпус первой партии «не различит и реранкер с гибридным поиском». Различает:
девять вопросов из 32 меняют состав пятёрки, и число верных ответов
на первом месте растёт с 22 до 27. Разбор того, почему прежнее рассуждение
было неверным — и почему первая редакция этой лабы опровергала его
некорректным сравнением, — [[lab-06-rerank#Почему корпус различает реранкер, но не различает эмбеддер|в конце]].

## Что нужно знать до первого шага

| Термин | Рабочее определение |
| --- | --- |
| **Кросс-энкодер** | Модель, читающая пару «запрос + документ» **целиком** и выдающая одно число. Реранкер — это он |
| **Би-энкодер** | Эмбеддер: считает вектор документа отдельно от запроса, заранее, один раз на весь корпус |
| **Каскад** | Дешёвый поиск даёт 50 кандидатов, дорогой реранкер пересортировывает их в 5 |
| **Глубина каскада** | Сколько кандидатов отдаётся реранкеру. Главный рычаг «качество против задержки» |
| **`relevance_score`** | Оценка реранкера. У bge — **логит**, а не вероятность: значения отрицательные, сравнивать можно только между собой |

**Почему нельзя реранкером искать сразу.** Би-энкодер считает 144 вектора
один раз навсегда, и поиск сводится к сравнению чисел. Кросс-энкодер обязан
прогнать модель для **каждой** пары «запрос + документ», и ничего нельзя
посчитать заранее. Поиск по всему корпусу реранкером стоил бы 144 прогонов
на каждый вопрос вместо 50.

Маркеры блоков вывода:

| Маркер | Что означает |
|---|---|
| **Вывод (дословно)** | Скопировано из терминала как есть |
| **Выжимка** | Показано только содержательное; команда печатает больше |

Все выводы сняты **09.08.2026**, реранкер `bge-reranker-v2-m3-GGUF:Q8_0`,
коллекция `contracts_v1` из [лаб 4](lab-04-loading.md).

## Шаг 2. Санитарная проверка: модель не битая

```bash
uv run python -c "
import sys; sys.path.insert(0,'src')
from rag_lab.rerank import Reranker
r = Reranker()
pairs = r.rank('во сколько обойдётся простой машины под погрузкой', [
  'За каждый час простоя транспортного средства сверх нормативного времени Заказчик уплачивает 1 500 рублей за час.',
  'Хранитель обеспечивает температурный режим от плюс 5 до плюс 25 градусов Цельсия.',
  'Время простоя исчисляется с момента прибытия транспортного средства в пункт погрузки.',
])
for i, s in pairs: print(f'  документ {i}: {s:+.4f}')
"
```

**Вывод (дословно)**:

```none
  документ 0: -4.1349
  документ 2: -4.5074
  документ 1: -11.0376
```

**Порядок верный:** сколько стоит простой → с какого момента считают →
температура на складе. Разрыв до нерелевантного документа — почти семь
единиц, то есть очевидный.

**Что именно проверено.** Что модель жива: конвертация в GGUF не потеряла
веса. Признак битой сборки из справочника — все документы получают
одинаково ничтожную оценку порядка 1e-23.

**Чего НЕ проверено:** полезен ли реранкер. Санитарная проверка на это
не отвечает и отвечать не может
([[lab-style#Правило 10. Санитарная проверка не заменяет метрику|правило 10]]).
Отвечают шаги 5–7.

**Что заметить в числах:** они отрицательные. Это логиты, а не вероятности.
Порог вида «брать всё выше 0,5» на них не ставится — сравнивать можно
только между собой внутри одного запроса.

## Шаг 5. Сколько вопросов вообще изменили ответ

```bash
uv run python scripts/compare-rerank.py
```

**Прежде чем выполнить — ответьте себе:** замер 08.08.2026 показал, что
пять разных конфигураций эмбеддера меняют ответ в 1–3 вопросах из 27,
то есть неразличимы. Сколько вопросов изменит реранкер?

**Вывод (дословно)**, вторая таблица:

```none
Попарно с «только вектор». Счётчик зависит от метрики — колонки НЕ взаимозаменяемы.
С числом из compare-embedders.py сопоставима только колонка recall@5.
вариант                          Δ nDCG@5    Δ MRR   изм. nDCG@5   изм. recall@5
----------------------------------------------------------------------------------
реранкер, top-10                   +0.138   +0.103      20 из 32         7 из 32
реранкер, top-20                   +0.145   +0.102      20 из 32         8 из 32
реранкер, top-50                   +0.154   +0.102      21 из 32         9 из 32
реранкер, top-50, с шапкой         +0.155   +0.121      21 из 32        10 из 32
```

**Две колонки вместо одной — и это главный урок шага.** В первой редакции
лабы стояла только левая, и из неё делался вывод: «21 из 32, две трети
набора». Вывод был получен сравнением с числом эмбеддера — 1–3 из 27.

**Сравнение было некорректным, и вот почему.** Счётчик «изменили ответ»
не существует сам по себе: он всегда считается **по какой-то метрике**.

| Метрика счётчика | На что реагирует | На что не реагирует |
|---|---|---|
| `recall@5` | смена **состава** пятёрки | перестановка внутри пятёрки |
| `nDCG@5` | любая перестановка внутри пятёрки | — |

Реранкер **переставляет**. Значит по `nDCG@5` его счётчик будет большим
почти всегда — даже когда он поменял местами четвёртый и пятый результат,
чего пользователь не заметит. А число для эмбеддера (1–3 из 27) считалось
по `recall@5`. Сравнивались разные величины под одним именем — ровно то,
что запрещает [[09-experiments#Что запрещено делать с этим журналом|журнал экспериментов]].

**Честное сравнение — правая колонка: 9 вопросов из 32.**

| Что меняли | Изменили ответ (обе цифры по `recall@5`) |
|---|---|
| Модель эмбеддера, пулинг, префиксы (замер 08.08.2026) | 1–3 из 27 |
| Реранкер (этот замер) | **9 из 32** |

Вывод устоял, но похудел вдвое: не «две трети набора», а «каждый третий
вопрос». Этого по-прежнему достаточно — 9 против 1–3 ни при каком
округлении не шум, — но предъявлять надо именно 9.

**Оговорка, которую честность требует дописать.** Даже правая колонка
сравнивает замеры на разных корпусах: 27 вопросов мерились на 127 голых
пунктах до появления чанкера, 32 — на 144 чанках после него. Полностью
сопоставимыми эти два числа станут только на партии 2, когда оба замера
пройдут в одинаковых условиях.

## Шаг 6. Сколько кандидатов ему давать

Своей команды у шага нет — это первая таблица `compare-rerank.py` из шага 5.

**Вывод (дословно)**, первая таблица того же прогона:

```none
вариант                           r@1    r@5   hit@1     MRR  nDCG@5  мс/запрос
----------------------------------------------------------------------------------
только вектор                   0.404  0.854   0.688   0.806   0.750          —
реранкер, top-10                0.508  0.938   0.844   0.909   0.887        161
реранкер, top-20                0.508  0.958   0.844   0.907   0.895        312
реранкер, top-50                0.508  0.974   0.844   0.907   0.904        794
реранкер, top-50, с шапкой      0.523  0.943   0.875   0.927   0.905       1083
```

**Что значит «top-10», когда кандидатов пятьдесят.** Реранкуется **голова**
списка, хвост остаётся в порядке векторного поиска и никуда не девается:

```none
каскад: top-50 -> реранкер top-10 (голый текст пункта)
хвост 40 кандидатов остаётся в порядке векторного поиска
```

Первая редакция скрипта хвост выбрасывала, и это была ошибка: сорок уже
найденных кандидатов терялись только потому, что до них не дошла очередь
второй модели. На партии 1 разницы не видно — верный ответ у всех 32
вопросов и так лежит в первой десятке, — но на партии 2 выброшенный хвост
занизил бы `recall@50` у всех вариантов, кроме top-50.

**Задержка растёт линейно, качество — нет.**

| Глубина | мс | Прирост nDCG@5 от «только вектор» | Доля прироста top-50 |
|---|---|---|---|
| 10 | 161 | +0,137 | 89 % |
| 20 | 312 | +0,145 | 94 % |
| 50 | 794 | +0,154 | 100 % |

**Практический вывод: top-10.** Девять десятых прироста за пятую часть
задержки. Оставшиеся 11 % стоят 630 миллисекунд на каждый запрос.

**Мелочь, о которую спотыкается внимательный читатель.** В таблице шага 5
для top-10 стоит `Δ nDCG@5 = +0.138`, а здесь `+0,137`. Это не опечатка
и не разные прогоны: там среднее из разностей по каждому вопросу, здесь
разность средних. На третьем знаке они расходятся, и ни одно из двух
не «правильнее» — просто считаются они по-разному.

**Оговорка, которая это ограничивает.** На корпусе из 144 чанков top-10 —
это 7 % базы, и верный ответ почти наверняка там. На корпусе из 1500
чанков те же 10 кандидатов будут 0,7 %, и `recall@10` первого каскада
станет узким местом. Глубину придётся замерить заново на партии 2 —
переносится не число 10, а способ его выбрать.

## Шаг 8. Стоит ли давать реранкеру шапку чанка

В вектор уходит текст с шапкой-адресом ([лаб 3](lab-03-chunking.md)), и
соблазн дать то же самое реранкеру велик.

```bash
uv run python scripts/evaluate.py --rerank --head
```

**Было** (голый текст пункта):

```none
recall@5         0.974
hit@5            1.000
MRR              0.907
nDCG@5           0.904
реранкер сверх того: 25.74 с (804 мс на запрос на 50 кандидатов)
вопросов без верного ответа в пятёрке: 0
```

**Стало** (с типом договора и названием раздела):

```none
recall@5         0.943
hit@5            0.969
MRR              0.927
nDCG@5           0.905
реранкер сверх того: 33.53 с (1048 мс на запрос на 50 кандидатов)
вопросов без верного ответа в пятёрке: 1
  поз. 6: какая сейчас предельная сумма по перевозке для Ромашки
```

**Смотреть надо на последние две строки, а не на средние.** По средним это
ничья: `MRR` +0,020, `nDCG@5` без изменений, `recall@5` −0,031. Так эта лаба
и была написана в первой редакции — «ничья, побеждает более простой вариант».

Но `hit@5` ушёл с 1,000 на 0,969, и за этой третью знака стоит событие:
**вариант с шапкой выбил вопрос из пятёрки** — тот самый, про предельную
сумму для Ромашки. Голый текст держит его на пятой позиции, шапка роняет
на шестую.

Решение: **оставить голый текст** — дешевле на 30 % и не теряет вопросов.

Почему этот вывод едва не был упущен —
[[lab-06-rerank#Как метрика на потолке чуть не спрятала ухудшение|в разборе]].

Критерий из роадмапа: «известно, сколько именно даёт реранкер на нашем
корпусе, и стоит ли он задержки».

- [x] прирост проверен счётчиком по той же метрике, что у эмбеддера:

- [x] задержка замерена: +161 / +312 / +794 мс на глубинах 10 / 20 / 50;
- [x] глубина замерена, но **не выбрана в продукт**: см. ниже;
- [x] проверено, где реранкер вредит (2 вопроса из 32);
- [x] проверено, что шапка чанка реранкеру не нужна и стоит одного вопроса.

**Стоит ли он задержки:** да. 161 мс при top-10 против 37 мс без него —
за 89 % прироста; оставшиеся 11 % стоят ещё 630 мс и того не стоят.

**Почему глубина не зафиксирована в коде.** Число 10 получено на корпусе,
где top-10 — это 7 % базы, и верный ответ лежит там почти всегда. На партии 2
те же 10 кандидатов станут 0,7 %, и `recall@10` первого каскада окажется
узким местом. Записывать 10 в дефолт значило бы выдать замер за решение;
дефолт остаётся 50 — инструмент измерения обязан показывать полную картину, —
а продуктовое значение выбирается на партии 2 тем же способом.
Переносится не число, а способ.

# Разбор

## Почему корпус различает реранкер, но не различает эмбеддер

Решение волта от 08.08.2026 звучало так: корпус, который не различает пять
разных конфигураций эмбеддера, «не различит и реранкер с гибридным поиском».
Рассуждение выглядело убедительно и оказалось неверным. Разбор, почему —
полезнее самой поправки.

**Что именно не различает корпус.** Метрики, упёршиеся в потолок:
`hit@5` = `hit@50` = 1,000. Верный ответ есть в пятёрке у всех 32 вопросов
ещё до всякого реранкера.

**Чего потолок не касается.** Метрик порядка. При загрузке `recall@1` = 0,404
и `nDCG@5` = 0,750 — запаса больше чем достаточно.

**Что делает реранкер.** Он не добавляет кандидатов (`recall@50` не
изменился вовсе, 0,984 до и после) — он их **переставляет**. То есть
работает ровно с теми метриками, у которых запас есть.

**Что делает смена эмбеддера.** Она меняет, какие чанки вообще попадут
в кандидаты. На корпусе, где в top-50 влезает треть базы, верный ответ
попадает в кандидаты при любой модели — поэтому конфигурации и оказались
неразличимы.

**Общее правило, которое из этого следует:**

> «Корпус не различает X» — утверждение не про корпус, а про пару
> «корпус + метрика». Прежде чем переносить его на Y, проверить, теми же
> ли метриками измеряется Y.

Прежнее рассуждение перенесло вывод с одних метрик на другие молча —
и на этом сломалось.

**И та же ошибка повторилась при проверке поправки.** Опровергая старый
вывод, первая редакция этой лабы предъявила счётчик «21 из 32» против
«1–3 из 27» — не заметив, что первое число считалось по `nDCG@5`,
а второе по `recall@5` (шаг 5). То есть утверждение «нельзя молча
переносить между метриками» доказывалось сравнением, которое молча
переносило между метриками.

Стоит задержаться на том, почему это так легко произошло. Оба числа
называются одинаково — «сколько вопросов изменили ответ», — оба печатаются
в одной колонке, оба выглядят как свойство корпуса. Имя метрики при них
не стоит нигде: оно спрятано внутри скрипта, в одной строке кода.
**Величина без единицы измерения выглядит как число, и с ней обращаются
как с числом.**

Отсюда практическое следствие для всех будущих замеров: счётчик изменившихся
вопросов печатать **с именем метрики в заголовке колонки**, а не рядом
в тексте. Сделано — в `compare-rerank.py` теперь две подписанные колонки
вместо одной безымянной.

**Что при этом остаётся верным.** Абсолютной базовой линии на этом корпусе
по-прежнему нет, и партия 2 по-прежнему блокер этапа 5. Числа 0,904 нельзя
предъявлять как качество продукта. Но **сравнивать варианты между собой**
корпус позволяет — там, где вариант влияет на порядок.

## Как метрика на потолке чуть не спрятала ухудшение

Вариант с шапкой чанка сначала был записан в ничью, и запись выглядела
обоснованной: `MRR` +0,020, `nDCG@5` без изменений, `recall@5` −0,031 —
на 32 вопросах это один-два вопроса в любую сторону.

Ухудшение выдал `hit@5`: 1,000 → 0,969. **А этой метрики не было ни в одной
таблице сравнения** — ни в шаге 4, ни в шаге 6. И по понятной причине:
она у всех вариантов равнялась единице, то есть колонка из одинаковых
единиц, которую первым делом выкидывают, чтобы таблица влезла по ширине.

Получается ловушка с двойным дном:

1. метрика на потолке не показывает улучшений — её перестают печатать;
2. именно потому, что она на потолке, **любое** её падение значимо: ухудшать
   некуда, кроме как вниз с максимума.

То есть выкидывают ровно ту колонку, где сигнал чище всего.

**Правило.** Метрики на потолке из таблиц не убирать. Если места нет —
печатать их отдельной строкой под таблицей, но печатать. Смотреть при этом
всё равно на изменившиеся: потолок интересен не значением, а моментом,
когда он перестал быть потолком.

## Почему реранкер дорогой

| | Эмбеддер | Реранкер |
|---|---|---|
| Что читает | документ отдельно от запроса | пару «запрос + документ» целиком |
| Когда считает | заранее, один раз на корпус | в момент запроса, на каждую пару |
| Стоимость поиска | сравнение чисел | N прогонов модели |
| Можно кэшировать | да, вектор чанка | нет: пара уникальна |

Отсюда 794 мс на 50 кандидатов и 161 мс на 10 — почти строго линейно
по числу кандидатов, потому что каждый из них требует отдельного прогона.

И отсюда же схема каскада: дешёвая модель отбирает кандидатов, дорогая
их упорядочивает. Кэшировать результат реранкера бессмысленно — пара
«этот запрос + этот чанк» второй раз не встретится.

## Чем этот замер не является

1. **Не оценкой качества продукта.** Корпус сгенерирован нами,
   формулировки однообразнее реальных, абсолютные числа завышены.
2. **Не выбором модели реранкера.** Сравнивался bge-reranker-v2-m3
   сам с собой на разной глубине. Альтернативы (Qwen3-Reranker и прочие)
   не пробовались.
3. **Не замером на железе партнёра.** У него GPU; 794 мс на 50 кандидатов
   там будут другими, и вывод про глубину каскада может измениться.
4. **Не проверкой на длинных чанках.** Наши чанки — 76 токенов по медиане
   у e5. Контекст реранкера 8192, и на длинных документах цена вырастет.

## Открытые вопросы

1. **Глубина каскада замерена, но в продукт не выбрана.** Дефолт `--depth`
   остаётся 50; число 10 получено на 144 чанках, где top-10 — это 7 % базы.
   На партии 2 повторить: там те же 10 кандидатов будут 0,7 %.
2. **Порог отсечения по `relevance_score` не изучен.** Скоры — логиты,
   и просто так порог на них не поставить. Для продукта нужен ответ
   «не найдено», а не пять худших кандидатов.
3. **Ухудшение в двух вопросах не разобрано по существу.** Почему
   реранкер опустил верный ответ — неизвестно.
4. **Батчинг запросов к реранкеру не проверялся.** Сейчас 50 документов
   уходят одним запросом; распараллеливание по нескольким запросам
   не пробовалось.
5. **Сравнение с гибридным поиском не сделано.** Возможно, часть прироста
   реранкера дешевле получить через BM25 + RRF. Этап 8.
