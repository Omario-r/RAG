# Qdrant: модель данных, индекс, загрузка, поиск

Дата: 28.07.2026. Шаг 3 из вводной партнёра и первый практический шаг
(«сейчас просто тыкаем Qdrant»). Здесь же — ответ на вопрос про «особенность
быстрой загрузки».

## Модель данных

Три понятия, дальше всё из них:

- **Коллекция** (collection) — аналог таблицы. Задаётся при создании:
  размерность вектора и метрика расстояния. **Изменить размерность потом
  нельзя** — только пересоздать.
- **Пойнт** (point) — единица хранения: `id` + `vector` + `payload`.
  Аналог строки. Наш пойнт = один чанк договора.
- **Payload** — произвольный JSON при пойнте: текст чанка, номер договора,
  номер пункта, даты, стороны. По нему фильтруют и его возвращают в выдаче.

```
Коллекция "contracts"
├── point id=1  vector=[0.02, -0.14, ...]  payload={doc_id:"TR-114", clause:"4.2", text:"За просрочку..."}
├── point id=2  vector=[...]               payload={...}
```

Про `id`: допустимы целые числа и UUID. Практика — детерминированный id
(например UUID5 от `doc_id + clause_no`), тогда повторная загрузка того же
договора **перезапишет** свои пойнты, а не создаст дубли. Это дешёвая
идемпотентность, которая экономит много времени при отладке.

Коллекция поддерживает **несколько именованных векторов** на один пойнт
(например `dense` и `sparse`) — это понадобится для гибридного поиска
([05](05-retrieval-rerank.md)); закладывать имена лучше сразу.

## Создание коллекции

```python
from qdrant_client import QdrantClient, models

client = QdrantClient(url="http://HOST:6333", api_key="...", prefer_grpc=True)

client.create_collection(
    collection_name="contracts",
    vectors_config=models.VectorParams(
        size=1024,                      # размерность — из ответа llama.cpp
        distance=models.Distance.COSINE,
        on_disk=True,                   # векторы на диск, не держать всё в RAM
    ),
    optimizers_config=models.OptimizersConfigDiff(
        indexing_threshold=0,           # ← индексация выключена на время загрузки
    ),
)
```

Порты: `6333` — REST и web-UI (`http://HOST:6333/dashboard`), `6334` — gRPC.
Дашборд удобен на этапе «тыкаем»: видно коллекции, пойнты, можно выполнять
запросы руками.

## HNSW: что за индекс и почему он дорогой

HNSW (Hierarchical Navigable Small World) — многослойный граф: каждый вектор
связан с ближайшими соседями, верхние слои разрежённые для «дальних прыжков»,
нижние плотные для точного доспуска. Поиск идёт жадным спуском — вместо
перебора миллионов векторов трогаются тысячи.

Плата — при вставке нового вектора надо найти его соседей и перестроить связи.
Отсюда «insert тяжелее поиска». Ключевые параметры:

| Параметр | Смысл | Эффект |
|---|---|---|
| `m` | Число связей на узел (обычно 16) | Больше → точнее и быстрее поиск, больше памяти и дольше индексация |
| `ef_construct` | Ширина поиска при построении (обычно 100) | Больше → качественнее граф, дольше индексация |
| `hnsw_ef` (при поиске) | Ширина поиска при запросе | Больше → выше recall, выше latency. Настраивается на запрос, без переиндексации |

Важное следствие: **HNSW приблизительный** (ANN). Он не гарантирует, что
нашёл истинно ближайших соседей — он находит их с высокой вероятностью.
Отсюда параметр `hnsw_ef` как рычаг «точность против скорости» и отсюда же
смысл брать в кандидаты top-50, а не top-5, с последующим реранкингом.

> [!note] Дополнение 17.08.2026: на стенде всего этого нет — но появится
> HNSW у нас **не построен** и, пока корпус не вырастет, строиться
> не будет. Значит, поиск сейчас точный, ANN-recall равен 1,000
> по построению, а `hnsw_ef` ни на что не влияет. Это не наша
> особенность: Qdrant так задуман, Weaviate переключается с полного
> перебора на граф только с 10 000 объектов, академический разбор
> (Lin, 2024) рекомендует то же.
>
> **Оговорка, без которой это читается как «индекс нам не нужен».**
> 1446 пойнтов — масштаб стенда, а не цели. Задача — «портфель
> из тысяч договоров», и порог пересекается **примерно на двухстах
> договорах**, то есть на первом же реальном клиенте. Арифметика
> и что из неё следует — раздел «Масштаб стенда против целевого»
> ниже.
>
> Практических следствий два. **`hnsw_ef`, приблизительность выдачи
> и разница между способами применения фильтра проверяются
> на коллекции с принудительно включённым индексом** — иначе проверка
> проходит тривиально и не меряет ничего. И **точная выдача сегодня
> бесплатна**: эталон для будущих замеров ANN-recall стоит
> зафиксировать заранее, потом его придётся считать специально.
> Разбор — `База знаний/06-vector-db/02-index.md`, раздел 6.
>
> Туда же — результат, меняющий интуицию про сам алгоритм: работа
> «Down with the Hierarchy» (2024) показала, что **иерархия слоёв
> HNSW не даёт выигрыша на высокоразмерных данных** — плоский граф
> даёт ту же задержку и тот же recall при меньшей памяти, потому что
> роль верхних слоёв берёт на себя самопроизвольно возникающая сеть
> хабов. Третье утверждение из этого справочника, не выдержавшее
> проверки внешними источниками.

Qdrant с версии 1.13 умеет строить HNSW на GPU (NVIDIA/AMD/Intel), заявлено
до 10× против CPU — это про инфраструктуру партнёра («оптимизации на GPU»).
Ускоряет построение индекса, но не отменяет приёмы ниже.

## Быстрая пакетная загрузка

Та самая «особенность», о которой партнёр помнил, что она есть. Их несколько,
и они складываются.

### 1. Отключить индексацию на время загрузки — главный приём

Пока идёт заливка, строить HNSW бессмысленно: граф перестраивается снова и
снова. Правильно — залить всё «плоско», потом включить индексацию один раз.

```python
# перед загрузкой (или сразу при создании коллекции)
client.update_collection(
    collection_name="contracts",
    optimizer_config=models.OptimizersConfigDiff(indexing_threshold=0),
)

#  ... загрузка ...

# после загрузки — вернуть порог, индекс построится один раз
client.update_collection(
    collection_name="contracts",
    optimizer_config=models.OptimizersConfigDiff(indexing_threshold=20000),
)
```

`indexing_threshold` — в килобайтах: сегменты меньше порога не индексируются
(на малых объёмах полный перебор быстрее графа). Значение `0` = индексацию
не строить вообще. Документация Qdrant прямо называет динамическое изменение
этого параметра приёмом эффективной первоначальной загрузки. По оценке из
статьи Qdrant — порядка +30% пропускной способности поверх gRPC.

**Замер 09.08.2026 этих 30 % не подтвердил: −8 %, то есть ничего.** Более
того, при рабочем пороге 20000 КБ сравнивать не с чем — индексация на нашем
объёме не запускается ни в одном из режимов. Приём не отменяется (на объёмах
партнёра он будет значить больше), но цифра из статьи на нашем железе
не воспроизвелась ([[11-evidence#Qdrant и загрузка]]).

Замеренные на стенде цифры по остальным приёмам: пакетно вместо поштучно —
**×22**, gRPC вместо REST — **×3,3**, размер батча 256–512 (не 64–256),
`parallel > 1` — **вредит**.

**Не забыть вернуть порог обратно.** Забытый `indexing_threshold=0` = коллекция
без HNSW = линейный перебор на каждом запросе. На десяти договорах разницы не
заметно, на корпусе клиента — катастрофа. Это стоит вынести в чек-лист.

### 2. gRPC вместо REST

```python
client = QdrantClient(url="http://HOST:6333", prefer_grpc=True)
```

Меньше накладных расходов на сериализацию, ощутимо быстрее на больших
загрузках. Ограничение: размер сообщения gRPC по умолчанию 4 МБ — при батчах
больше ~1000 точек с большой размерностью упрётесь; поднимается параметром
клиента (`max_message_size`).

### 3. Батчи, а не поштучно

Никогда не `upsert` по одному пойнту в цикле — это единственный приём
из статей, который замер не преувеличил: **×22**.

Размер батча статьи советуют 64–256. **Замер 09.08.2026 сдвинул оптимум
вверх: 256–512.** Нижняя граница совета явно мала — 64 работает вдвое
медленнее 512:

| `batch_size` | пойнт/с |
|---|---|
| 32 | 11 400 |
| 64 | 15 300 |
| 128 | 21 400 |
| 256 | 27 200 |
| 512 | **28 100** |

Выше 512 не проверялось: ограничение gRPC на размер сообщения — 4 МБ,
и при 1024 точках на 1024 измерения это уже предел.

Клиент умеет батчить сам:

```python
client.upload_points(
    collection_name="contracts",
    points=points_iterator,   # генератор, не список — не держим всё в памяти
    batch_size=256,
    parallel=1,               # НЕ 4: замер показал, что больше — вредит, см. ниже
    wait=False,
)
```

`upload_points` / `upload_collection` принимают итератор и сами режут его
на батчи.

### 4. Параллелизм

Статьи советуют 2–4 потока. **Замер 09.08.2026 этот совет опроверг:
на одном узле `parallel=1` быстрее всех.**

| `parallel` | пойнт/с | разброс |
|---|---|---|
| 1 | **23 700** | 0,36–0,45 с |
| 2 | 16 800 | 0,58–0,72 с |
| 4 | 17 700 | 0,53–0,61 с |

Разбросы не перекрываются — это не шум.

**И отдельная грабля, дороже самой потери скорости.** `parallel > 1`
в `qdrant-client` разводит работу **процессами**, а не потоками. На macOS
процессы порождаются через spawn, то есть дочерний заново импортирует
главный модуль: скрипт без `if __name__ == "__main__"` выполняется целиком
в каждом работнике. На нашем стенде это дало три процесса, заново
векторизующих корпус, вместо загрузки
([[11-evidence#Qdrant и загрузка]]).

Если у коллекции несколько шардов — отправная точка «один поток на шард»
может заработать (у каждого шарда свой WAL и свой воркер записи), но у нас
один узел, и проверить это негде. Помечено **проверить**.

### 5. Параметр wait

Запись проходит **три стадии**, но точек возврата у неё только **две** —
и третья стадия к `wait` отношения не имеет вовсе:

```
запрос
  │
  ├─ 1. записан в WAL ────────► ответ при wait=false   status: acknowledged
  │
  ├─ 2. применён к сегменту ──► ответ при wait=true    status: completed
  │                             ← с этого момента пойнты видны поиску
  │
  └─ 3. построен HNSW ────────► ответа не бывает ни при каком wait
                                ← отдельный фоновый оптимизатор
```

Разницу видно прямо в ответе сервера — проверено на стенде 06.08.2026:

| Режим                     | `result.status` | Смысл                      |
| ------------------------- | --------------- | -------------------------- |
| без `wait` (по умолчанию) | `acknowledged`  | «Принял в журнал, применю» |
| `?wait=true`              | `completed`     | «Применил, данные видны»   |

**Для массовой загрузки нужен `wait=false`.** `wait=true` на каждом батче
сериализует заливку: отправили батч → стоим, пока он применится → только потом
шлём следующий. Канал простаивает ровно то время, пока работает сервер, и
наоборот. С `wait=false` поток остаётся заполненным — сервер применяет
предыдущий батч, пока клиент уже отправляет следующий.

**Обратная сторона:** раз мы не ждём, сразу после загрузки данных в поиске
может ещё не быть. Перед замерами дождаться, пока `indexed_vectors_count`
достигнет `points_count`.

> [!warning] Поправка 09.08.2026: ждать `green` бесполезно
> Прежняя редакция предписывала «дождаться, пока статус станет `green`».
> Замер показал, что это не проверка: **зелёный статус означает
> «оптимизатору нечего делать» и выставлен с самого начала**.
>
> 10 000 пойнтов после возврата порога были зелёными сразу и оставались
> зелёными 24 секунды с `indexed_vectors_count = 0` — индекс не строился
> вовсе, потому что `indexing_threshold` применяется **к сегменту**,
> а не к коллекции, и пяти сегментам по 8 МБ до порога в 20 МБ далеко.
>
> Проверять надо `indexed_vectors_count` против `points_count`, вместе
> с числом сегментов ([[11-evidence#4. `indexing_threshold` считается на сегмент, а не на коллекцию]]).

**Ловушка, которую стоит развести явно.** `wait=true` **не означает
«проиндексировано»** — он доводит запись до стадии 2 и останавливается.
Асинхронностей здесь две, и они независимы:

| Что | Чем управляется | Когда закончится |
|---|---|---|
| Применение записи | `wait` | При `wait=true` — до ответа |
| Построение HNSW | оптимизатор + `indexing_threshold` | Когда оптимизатор сочтёт нужным |

То есть данные могут быть видны поиску и при этом искаться полным перебором,
пока граф не построен. Практическое следствие для этапа 4: после массовой
заливки **не полагаться на `wait` вообще**, а опрашивать коллекцию. «Данные
записаны» и «индекс построен» — разные события; замерять скорость поиска
между ними значит получить красивые и бессмысленные цифры.

### 6. Payload-индексы — до загрузки

Индексы по полям payload (для фильтрации) дешевле создать **до** массовой
заливки, чем достраивать после.

```python
client.create_payload_index("contracts", "doc_id", models.PayloadSchemaType.KEYWORD)
client.create_payload_index("contracts", "doc_type", models.PayloadSchemaType.KEYWORD)
client.create_payload_index("contracts", "date_expire", models.PayloadSchemaType.DATETIME)
```

### 7. Память: `on_disk` и квантизация

- `on_disk=True` у `VectorParams` — векторы лежат на диске, в RAM только
  необходимое; снимает давление на память при загрузке.
- Квантизация (сжатие векторов, в свежих версиях — семейство TurboQuant,
  от 4 до 1 бита) держит сжатую копию в RAM для быстрого грубого прохода,
  а точные значения подтягивает с диска. На нашем масштабе не нужна;
  понадобится на корпусе клиента — отметить и вернуться.

  **Уточнено 17.08.2026.** TurboQuant — алгоритм Google Research
  (ICLR 2026), приехавший в Qdrant 1.18 (11.05.2026); его отличие
  от квантизации произведений в том, что он **не требует подгонки под
  конкретную модель эмбеддингов**. Вендорские числа: на четырёх битах
  recall 0,9169–0,9271 против 0,9014–0,9339 у скалярной квантизации
  при вдвое лучшем сжатии; на одном бите 0,6300–0,7924 против
  0,4683–0,6921 у наивной бинарной. Две детали, важные при включении:
  квантизация **асимметрична** — сжимаются только хранимые векторы,
  запрос считается точно (даровое улучшение, стоит проверять в любой
  системе); и в 1.19 появился тип `Turbo4`, где полноточной копии
  нет вовсе — до девятикратной экономии, но рескоринг по точным
  значениям становится невозможен. Разбор —
  `База знаний/06-vector-db/03-compression.md`.
  Наши 1446 × 1024 × 4 байта ≈ 5,9 МБ сжимать не от чего; по разбору
  квантизация становится осмысленной примерно от миллиона пойнтов,
  то есть от двадцати тысяч договоров.

### Чек-лист загрузки

Уточнён замером 09.08.2026 — изменения помечены.

1. Коллекция создана с нужной размерностью и `on_disk=True`.
2. Payload-индексы созданы **вместе с коллекцией**, а не «когда понадобятся».
3. `indexing_threshold=0`.
4. Клиент с `prefer_grpc=True` **и явным `grpc_port`** — из URL клиент его
   не выведет и молча останется на REST.
5. Загрузка `upload_points`, **`batch_size≈256`** (не 128: 32 вдвое хуже,
   оптимум 256–512), **`parallel=1`** (замер: больше вредит), `wait=False`.
6. `indexing_threshold` возвращён (например 20000).
7. Дождались, пока **`indexed_vectors_count` достигнет `points_count`**,
   зафиксировали время загрузки. Ждать `status=green` бесполезно — он
   зелёный с самого начала.
8. Если индекс не строится — посмотреть на **число сегментов**: порог
   применяется к сегменту, и на малых объёмах HNSW не строится вовсе.
   Это не ошибка, но знать об этом надо: поиск идёт полным перебором.

Шаги 3 и 6 — парные; ошибка ровно здесь и стоит той самой «забытой
особенности». Прохождение чек-листа целиком — лаб 4.

## Поиск

Современный универсальный метод — `query_points` (Query API), он же основа
гибридного поиска:

```python
res = client.query_points(
    collection_name="contracts",
    query=query_vector,          # вектор запроса от той же модели
    limit=50,                    # кандидатов под реранкер — не 5
    with_payload=True,
    search_params=models.SearchParams(hnsw_ef=128),
).points

for p in res:
    print(p.score, p.payload["doc_id"], p.payload["clause_no"], p.payload["text"][:100])
```

`score` при COSINE — косинусная близость, больше = ближе. Абсолютное значение
малоинформативно (0,72 — это хорошо или плохо? зависит от модели), сравнивать
имеет смысл только внутри одной выдачи. Порог отсечения по score подбирать
эмпирически и с осторожностью.

## Фильтрация

Сильная сторона Qdrant: фильтр применяется **внутри** обхода графа
(filterable HNSW), а не как постобработка — то есть `limit=10` с фильтром
вернёт 10 подходящих, а не «10 ближайших, из которых 2 прошли фильтр».

```python
flt = models.Filter(must=[
    models.FieldCondition(key="doc_type", match=models.MatchValue(value="перевозка")),
    models.FieldCondition(key="date_expire", range=models.DatetimeRange(gte="2026-10-01")),
])
res = client.query_points("contracts", query=qv, query_filter=flt, limit=50).points
```

Это техническая основа связки с SQL из вводной партнёра: реквизиты живут в SQL,
их копия — в payload, и тогда «найди смысл среди вот этих договоров» делается
одним запросом.

> [!warning] Дополнение 17.08.2026: это самое важное свойство базы для нас — и оно не проверено
> Фильтр `doc_id` на корпусе из сотен договоров имеет селективность
> в доли процента. Это ровно тот режим, где распространённая
> альтернатива — **пост-фильтр** (взять top-`k` по вектору, потом
> отбросить непрошедшие) — отказывает: возвращает три результата
> вместо десяти и **не даёт при этом ошибки**. Снаружи это выглядит
> как «поиск иногда не находит».
>
> Отсюда переоценка: фильтрация — не удобство Qdrant, а условие
> работоспособности функции различения договора
> (`checks/README.md`, открытый вопрос 3). И отсюда же — что её надо
> **измерить**, а не принять на веру: три утверждения этого
> справочника замер уже не подтвердил. Прибор — фильтрованный
> ANN-recall против точного перебора среди прошедших фильтр, кривой
> по нескольким селективностям. Существенная деталь: пока индекса
> нет, проверка проходит тривиально и ничего не измеряет — ставить
> её надо на коллекции с **принудительно включённым** индексом.
> Методика — `База знаний/06-vector-db/08-evaluation.md`, раздел 6;
> гипотеза `H-020`.
>
> Ещё одно, о чём стоит знать: у этой задачи есть общее
> исследовательское решение — **ACORN** (SIGMOD 2024), индекс,
> строящийся без знания о том, по каким полям будут фильтровать.
> Разброс заявленного выигрыша против предшественников — от 2×
> до 1000× — сам по себе показывает, насколько плохо ведут себя
> обычные реализации на сложных предикатах. Разбор —
> `База знаний/06-vector-db/04-filtering.md`.

## Что смотреть при отладке

```python
client.get_collection("contracts")   # status, points_count, indexed_vectors_count, config
client.count("contracts", exact=True)
client.scroll("contracts", limit=3, with_payload=True)   # глазами посмотреть, что реально лежит
```

`scroll` на первых шагах бесценен: половина «поиск не работает» оказывается
«в payload не то, что мы думали» или «в тексте чанка мусор из парсера».

Полезно с самого начала: **снапшоты** коллекции (`create_snapshot`) перед
экспериментами с параметрами — переиндексация корпуса дороже, чем кажется.

## Масштаб стенда против целевого

Добавлено 17.08.2026 по итогам разбора внешних источников
(`База знаний/06-vector-db/`). Раздел отвечает на один вопрос: какие
выводы теории применимы к нам сейчас, какие применимы к цели,
и где между ними разница.

### Арифметика

Опорные числа: коллекция `contracts_v1` — **1446 пойнтов**
на 48 документов и **30 договоров** (пересобрана 15.08.2026), то есть
**около 48 чанков на договор**. Порог, за которым Qdrant начинает
строить HNSW, — порядка 10 000 объектов **в сегменте**.

Задача сформулирована как «найти по портфелю из **тысяч** договоров»
([00-context.md](00-context.md)). Отсюда:

| Портфель | Пойнтов | Векторы (1024 × `float32`) | Режим |
|---|---|---|---|
| 30 договоров (стенд) | 1 446 | 5,9 МБ | полный перебор |
| **~200 договоров** | **~10 000** | 41 МБ | **порог: индекс начинает строиться** |
| 1 000 договоров | ~48 000 | 197 МБ | HNSW в памяти |
| 10 000 договоров | ~480 000 | 2,0 ГБ | HNSW в памяти |
| 100 000 договоров | ~4,8 млн | 20 ГБ | один узел; здесь начинается разговор про диск и квантизацию |

**Порог пересекается примерно на двухстах договорах.** Для «портфеля
из тысяч» это не отдалённая перспектива, а первый же реальный клиент.
Режим без индекса — режим отладки, который закончится на первой
настоящей загрузке.

### Что при этом НЕ меняется

Полезно отделить опасение от факта, потому что три четверти материала
про векторные БД к нам не относятся ни сейчас, ни потом:

- **Выбор Qdrant не пересматривается.** Специализированные движки
  окупаются от десятков миллионов векторов; мы на два порядка левее
  даже на ста тысячах договоров.
- **Шарды и объектное хранилище не понадобятся.** 4,8 млн векторов —
  это один узел.
- **Квантизация не по делу** до порядка миллиона пойнтов, то есть
  примерно до двадцати тысяч договоров.
- **Скорость поиска не проблема** ни сейчас (8 мс из ~200 мс полного
  цикла), ни на цели (в этом диапазоне HNSW работает без ухищрений).

Дефицит у нас не в производительности, а в проверенности.

### Что меняется, и всё сразу

В момент, когда сегмент дорастёт до порога, включаются **четыре
механизма, которых сейчас нет**:

| Механизм | Как проявится |
|---|---|
| Приблизительность выдачи | часть верных пунктов перестанет находиться |
| Зависимость от `hnsw_ef` | качество начнёт зависеть от параметра запроса |
| Разница между способами применения фильтра | `doc_id` под узким фильтром вернёт меньше `k` |
| Накопленные надгробия от перезаливок | качество будет медленно падать со временем |

**Ни один из четырёх не даёт ошибки** — все проявляются как «поиск
стал хуже». Это профиль дефекта «работало на стенде, сломалось
у клиента», и ни один не наблюдаем на текущей конфигурации.

### Что из этого следует делать

По убыванию отношения «польза к стоимости».

1. **Зафиксировать эталон полным перебором — сейчас.** Пока индекса
   нет, выдача точна по определению: прогнать золотой набор
   с `exact=true`, сохранить идентификаторы **и оценки** (при равных
   оценках порядок не определён, и расхождение может оказаться
   артефактом сортировки). Это готовый ground truth для всех будущих
   замеров ANN-recall. Стоимость — минуты; после перехода порога его
   придётся считать специально.
2. **Прогон с принудительно включённым индексом.** Единственный способ
   увидеть заранее все четыре механизма из таблицы выше. Технически —
   снизить `indexing_threshold` либо задать `default_segment_number`,
   чтобы сегменты доросли до порога. Гипотеза `H-019`.
3. **На этой конфигурации — проверить фильтр `doc_id`**: полнота
   выдачи и фильтрованный ANN-recall кривой по селективностям
   (50 %, 10 %, 1 %, 0,1 %). Гипотеза `H-020`; закрывает открытый
   вопрос 3(а) в `checks/README.md`.
4. **Пересоздавать коллекцию вместо перезаливки поверх — пока это
   дёшево.** Заливка занимает 0,03 с, экономия от перезаписи мнимая,
   а надгробия реальны. Срок годности правила короткий: на тысяче
   договоров пересоздание — это переиндексация ~48 000 чанков, то есть
   часы работы эмбеддера (7,10 с на 144 чанка). Дальше обходиться
   придётся штатными средствами базы — гипотеза `H-021`.
5. **Не сравнивать базы по скорости.** Ни на 1446 пойнтах (различия
   в шуме), ни на целевом объёме (в этом диапазоне работают все).

### Один незакрытый шов

Реквизиты живут в SQL, их копия — в payload. Транзакции между базами
нет: договор, обновлённый в SQL, но не переиндексированный, даст поиск
по устаревшему payload **и не даст никакой ошибки**. Это единственное
место, где вариант «всё в PostgreSQL с pgvector» имел бы структурное
преимущество, не связанное ни со скоростью, ни с recall. На пересмотр
архитектуры не тянет, но помнить стоит — разбор
`База знаний/06-vector-db/06-operations.md`, раздел 4.

   TurboQuant) и как он развёрнут (docker, k8s, один узел?).
2. Один узел или шарды/реплики — влияет на параллелизм загрузки.
3. Есть ли уже коллекции и соглашения об именовании.
4. ~~Наш замер: сколько реально занимает загрузка корпуса с приёмами и без~~ —
   **закрыто 09.08.2026 лабой 4.** Пакетно против
   поштучно — ×22, gRPC против REST — ×3,3, оптимум батча 256–512,
   `parallel > 1` вредит, `indexing_threshold=0` не даёт обещанных +30 %.
   Три утверждения этого справочника из пяти замер не подтвердил.
5. Сколько сегментов правильно. Автосегментация дала 5 и тем самым отключила
   индексацию: ни один сегмент не дорос до порога. Лечится ли это
   `default_segment_number` или пересмотром порога — на нашем масштабе
   не проверить ([[11-evidence#4. `indexing_threshold` считается на сегмент, а не на коллекцию]]).
6. `on_disk=True` не сравнивался с `False`, квантизация не трогалась вовсе.
   Понадобится на объёмах партнёра.
7. **Фильтрация внутри обхода графа не проверена.** Свойство
   документировано и является для нас определяющим (различение
   договора), но три утверждения этого справочника замер уже
   не подтвердил. Прибор — фильтрованный ANN-recall кривой
   по селективностям, на коллекции с принудительно включённым
   индексом. Гипотеза `H-020`.
8. **Эталон точного поиска не зафиксирован, хотя сейчас бесплатен.**
   Пока HNSW не построен, выдача точна по определению; сохранённая
   сегодня выдача золотого набора — готовый ground truth для всех
   будущих замеров ANN-recall. Позже его придётся считать специально.
9. **Устойчивость к перезаливкам не измерена.** Корпус
   перезаливается десятками раз, перезапись по тому же `id` —
   это удаление плюс вставка, то есть накопление tombstone.
   Сейчас безвредно (индекса нет), при росте корпуса станет
   источником тихой деградации. Дешёвая защита без измерения —
   пересоздавать коллекцию вместо upsert поверх: заливка занимает
   0,03 с. Гипотеза `H-021`.
