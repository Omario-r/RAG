## Модель данных

Три понятия, дальше всё из них:

- **Коллекция** (collection) — аналог таблицы. Задаётся при создании:
размерность вектора и метрика расстояния. **Изменить размерность потом нельзя** — только пересоздать.
- **Пойнт** (point) — единица хранения: `id` + `vector` + `payload`.
Аналог строки. Наш пойнт = один чанк договора.
- **Payload** — произвольный JSON при пойнте: текст чанка, номер договора,
номер пункта, даты, стороны. По нему фильтруют и его возвращают в выдаче.

```
Коллекция "contracts"
├── point id=1  vector=[0.02, -0.14, ...]  payload={doc_id:"TR-114", clause:"4.2", text:"За просрочку..."}
├── point id=2  vector=[...]               payload={...}
```

Про `id`: допустимы целые числа и UUID. Практика — детерминированный id (например UUID5 от `doc_id + clause_no`), тогда повторная загрузка того же договора **перезапишет** свои пойнты, а не создаст дубли. Это дешёвая идемпотентность, которая экономит много времени при отладке.

Коллекция поддерживает **несколько именованных векторов** на один пойнт (например `dense` и `sparse`) — это понадобится для гибридного поиска ([05](05-retrieval-rerank.md)); закладывать имена лучше сразу.

## Создание коллекции

```python
from qdrant_client import QdrantClient, models

client = QdrantClient(url="http://HOST:6333", api_key="...", prefer_grpc=True)

client.create_collection(
    collection_name="contracts",
    vectors_config=models.VectorParams(
        size=1024,                      # размерность — из ответа llama.cpp
        distance=models.Distance.COSINE,
        on_disk=True,                   # векторы на диск, не держать всё в RAM
    ),
    optimizers_config=models.OptimizersConfigDiff(
        indexing_threshold=0,           # ← индексация выключена на время загрузки
    ),
)
```

Порты: `6333` — REST и web-UI (`http://HOST:6333/dashboard`), `6334` — gRPC. Дашборд удобен на этапе «тыкаем»: видно коллекции, пойнты, можно выполнять запросы руками.

## HNSW у нас не построен

HNSW — многослойный граф соседства, по которому поиск идёт жадным спуском вместо перебора. Он приблизительный: истинно ближайший сосед может не попасть в выдачу — отсюда и смысл брать в кандидаты top-50 с последующим реранкингом. Устройство, параметры (`m`, `ef_construct`, `hnsw_ef`) и то, почему вставка дороже поиска, — [[База знаний/06-vector-db/02-index|02-index]].

**На нашем стенде графа нет и, пока корпус не вырастет, не будет.** Значит, поиск сейчас точный, ANN-recall равен 1,000 по построению, а `hnsw_ef` ни на что не влияет. Это не наша особенность: Qdrant так задуман, Weaviate переключается на граф только с 10 000 объектов.

Два следствия, и оба практические:

1. **`hnsw_ef`, приблизительность выдачи и разница между способами применения
фильтра проверяются на коллекции с принудительно включённым индексом** — иначе проверка проходит тривиально и не меряет ничего.
2. **Точная выдача сегодня бесплатна.** Эталон для будущих замеров ANN-recall
стоит зафиксировать сейчас, потом его придётся считать специально.

Читается это легко как «индекс нам не нужен» — неверно: 1446 пойнтов масштаб стенда, а не цели, и порог пересекается примерно на двухстах договорах. Арифметика — в разделе «Масштаб стенда против целевого» ниже.

Qdrant с 1.13 умеет строить HNSW на GPU, заявлено до 10× против CPU — это пригодится на машине с дискретной картой. Ускоряет построение, но не отменяет приёмы ниже.

## Быстрая пакетная загрузка

Приёмов несколько, и они складываются.

### 1. Отключить индексацию на время загрузки — главный приём

> **У нас стоит:** `indexing_threshold=0` при создании коллекции, возвращается после загрузки

Пока идёт заливка, строить HNSW бессмысленно: граф перестраивается снова и снова. Правильно — залить всё «плоско», потом включить индексацию один раз.

```python
# перед загрузкой (или сразу при создании коллекции)
client.update_collection(
    collection_name="contracts",
    optimizer_config=models.OptimizersConfigDiff(indexing_threshold=0),
)

#  ... загрузка ...

# после загрузки — вернуть порог, индекс построится один раз
client.update_collection(
    collection_name="contracts",
    optimizer_config=models.OptimizersConfigDiff(indexing_threshold=20000),
)
```

`indexing_threshold` — в килобайтах: сегменты меньше порога не индексируются (на малых объёмах полный перебор быстрее графа). Значение `0` = индексацию не строить вообще. Документация Qdrant прямо называет динамическое изменение этого параметра приёмом эффективной первоначальной загрузки. По оценке из статьи Qdrant — порядка +30% пропускной способности поверх gRPC.

**Замер 09.08.2026 этих 30 % не подтвердил: −8 %, то есть ничего.** Более того, при рабочем пороге 20000 КБ сравнивать не с чем — индексация на нашем объёме не запускается ни в одном из режимов. Приём не отменяется (на объёмах корпусах он будет значить больше), но цифра из статьи на нашем железе не воспроизвелась ([[11-evidence#Qdrant и загрузка]]).

Замеренные на стенде цифры по остальным приёмам: пакетно вместо поштучно — **×22**, gRPC вместо REST — **×3,3**, размер батча 256–512 (не 64–256), `parallel > 1` — **вредит**.

**Не забыть вернуть порог обратно.** Забытый `indexing_threshold=0` = коллекция без HNSW = линейный перебор на каждом запросе. На десяти договорах разницы не заметно, на корпусе клиента — катастрофа. Это стоит вынести в чек-лист.

### 2. gRPC вместо REST

> **У нас стоит:** gRPC, `prefer_grpc=True` и явный `grpc_port`

```python
client = QdrantClient(url="http://HOST:6333", prefer_grpc=True)
```

Меньше накладных расходов на сериализацию, ощутимо быстрее на больших загрузках. Ограничение: размер сообщения gRPC по умолчанию 4 МБ — при батчах больше ~1000 точек с большой размерностью упрётесь; поднимается параметром клиента (`max_message_size`).

### 3. Батчи, а не поштучно

> **У нас стоит,** но размер батча 128 против замеренного оптимума 256–512 — см. расхождение выше

Никогда не `upsert` по одному пойнту в цикле — это единственный приём из статей, который замер не преувеличил: **×22**.

Размер батча статьи советуют 64–256. **Замер 09.08.2026 сдвинул оптимум вверх: 256–512.** Нижняя граница совета явно мала — 64 работает вдвое медленнее 512:

| `batch_size` | пойнт/с |
|---|---|
| 32 | 11 400 |
| 64 | 15 300 |
| 128 | 21 400 |
| 256 | 27 200 |
| 512 | **28 100** |

Выше 512 не проверялось: ограничение gRPC на размер сообщения — 4 МБ, и при 1024 точках на 1024 измерения это уже предел.

Клиент умеет батчить сам:

```python
client.upload_points(
    collection_name="contracts",
    points=points_iterator,   # генератор, не список — не держим всё в памяти
    batch_size=256,
    parallel=1,               # НЕ 4: замер показал, что больше — вредит, см. ниже
    wait=False,
)
```

`upload_points` / `upload_collection` принимают итератор и сами режут его на батчи.

### 4. Параллелизм

> **У нас не используется:** `parallel=1`, и это подтверждено замером

Статьи советуют 2–4 потока. **Замер 09.08.2026 этот совет опроверг: на одном узле `parallel=1` быстрее всех.**

| `parallel` | пойнт/с | разброс |
|---|---|---|
| 1 | **23 700** | 0,36–0,45 с |
| 2 | 16 800 | 0,58–0,72 с |
| 4 | 17 700 | 0,53–0,61 с |

Разбросы не перекрываются — это не шум.

**И отдельная грабля, дороже самой потери скорости.** `parallel > 1` в `qdrant-client` разводит работу **процессами**, а не потоками. На macOS процессы порождаются через spawn, то есть дочерний заново импортирует главный модуль: скрипт без `if __name__ == "__main__"` выполняется целиком в каждом работнике. На нашем стенде это дало три процесса, заново векторизующих корпус, вместо загрузки ([[11-evidence#Qdrant и загрузка]]).

Если у коллекции несколько шардов — отправная точка «один поток на шард» может заработать (у каждого шарда свой WAL и свой воркер записи), но у нас один узел, и проверить это негде. Помечено **проверить**.

### 5. Параметр wait

> **У нас стоит:** `wait=False`

Запись проходит **три стадии**, но точек возврата у неё только **две** — и третья стадия к `wait` отношения не имеет вовсе:

```
запрос
  │
  ├─ 1. записан в WAL ────────► ответ при wait=false   status: acknowledged
  │
  ├─ 2. применён к сегменту ──► ответ при wait=true    status: completed
  │                             ← с этого момента пойнты видны поиску
  │
  └─ 3. построен HNSW ────────► ответа не бывает ни при каком wait
                                ← отдельный фоновый оптимизатор
```

Разницу видно прямо в ответе сервера — проверено на стенде 06.08.2026:

| Режим                     | `result.status` | Смысл                      |
| ------------------------- | --------------- | -------------------------- |
| без `wait` (по умолчанию) | `acknowledged`  | «Принял в журнал, применю» |
| `?wait=true`              | `completed`     | «Применил, данные видны»   |

**Для массовой загрузки нужен `wait=false`.** `wait=true` на каждом батче сериализует заливку: отправили батч → стоим, пока он применится → только потом шлём следующий. Канал простаивает ровно то время, пока работает сервер, и наоборот. С `wait=false` поток остаётся заполненным — сервер применяет предыдущий батч, пока клиент уже отправляет следующий.

**Обратная сторона:** раз мы не ждём, сразу после загрузки данных в поиске может ещё не быть. Перед замерами дождаться, пока `indexed_vectors_count` достигнет `points_count`.

> [!warning] Поправка 09.08.2026: ждать `green` бесполезно
> Прежняя редакция предписывала «дождаться, пока статус станет `green`».
> Замер показал, что это не проверка: **зелёный статус означает
> «оптимизатору нечего делать» и выставлен с самого начала**.
>
> 10 000 пойнтов после возврата порога были зелёными сразу и оставались
> зелёными 24 секунды с `indexed_vectors_count = 0` — индекс не строился
> вовсе, потому что `indexing_threshold` применяется **к сегменту**,
> а не к коллекции, и пяти сегментам по 8 МБ до порога в 20 МБ далеко.
>
> Проверять надо `indexed_vectors_count` против `points_count`, вместе
> с числом сегментов ([[11-evidence#4. `indexing_threshold` считается на сегмент, а не на коллекцию]]).

**Ловушка, которую стоит развести явно.** `wait=true` **не означает «проиндексировано»** — он доводит запись до стадии 2 и останавливается. Асинхронностей здесь две, и они независимы:

| Что | Чем управляется | Когда закончится |
|---|---|---|
| Применение записи | `wait` | При `wait=true` — до ответа |
| Построение HNSW | оптимизатор + `indexing_threshold` | Когда оптимизатор сочтёт нужным |

То есть данные могут быть видны поиску и при этом искаться полным перебором, пока граф не построен. Практическое следствие для этапа 4: после массовой заливки **не полагаться на `wait` вообще**, а опрашивать коллекцию. «Данные записаны» и «индекс построен» — разные события; замерять скорость поиска между ними значит получить красивые и бессмысленные цифры.

### 6. Payload-индексы — до загрузки

> **У нас стоит:** шесть полей, создаются вместе с коллекцией

Индексы по полям payload (для фильтрации) дешевле создать **до** массовой заливки, чем достраивать после.

```python
client.create_payload_index("contracts", "doc_id", models.PayloadSchemaType.KEYWORD)
client.create_payload_index("contracts", "doc_type", models.PayloadSchemaType.KEYWORD)
client.create_payload_index("contracts", "date_expire", models.PayloadSchemaType.DATETIME)
```

### 7. Память: `on_disk` и квантизация

> **У нас:** `on_disk=True` стоит, квантизация не трогалась вовсе

- `on_disk=True` у `VectorParams` — векторы лежат на диске, в RAM только
необходимое; снимает давление на память при загрузке.
- Квантизация (сжатие векторов, в свежих версиях — семейство TurboQuant,
от 4 до 1 бита) держит сжатую копию в RAM для быстрого грубого прохода, а точные значения подтягивает с диска. На нашем масштабе не нужна; понадобится на корпусе клиента — отметить и вернуться.

**Уточнено 17.08.2026.** TurboQuant не требует подгонки под конкретную модель эмбеддингов и потому включается без переобучения; квантизация вдобавок асимметрична — сжимаются только хранимые векторы, запрос считается точно. Разбор, вендорские числа и подводный камень типа `Turbo4` (полноточной копии нет вовсе, рескоринг невозможен) — [[База знаний/06-vector-db/03-compression|03-compression]]. Наши 1446 × 1024 × 4 байта ≈ 5,9 МБ сжимать не от чего: квантизация становится осмысленной примерно от миллиона пойнтов, то есть от двадцати тысяч договоров.

### Чек-лист загрузки

Уточнён замером 09.08.2026 — изменения помечены.

1. Коллекция создана с нужной размерностью и `on_disk=True`.
2. Payload-индексы созданы **вместе с коллекцией**, а не «когда понадобятся».
3. `indexing_threshold=0`.
4. Клиент с `prefer_grpc=True` **и явным `grpc_port`** — из URL клиент его
не выведет и молча останется на REST.
5. Загрузка `upload_points`, **`batch_size≈256`** (не 128: 32 вдвое хуже,
оптимум 256–512), **`parallel=1`** (замер: больше вредит), `wait=False`.
6. `indexing_threshold` возвращён (например 20000).
7. Дождались, пока **`indexed_vectors_count` достигнет `points_count`**,
зафиксировали время загрузки. Ждать `status=green` бесполезно — он зелёный с самого начала.
8. Если индекс не строится — посмотреть на **число сегментов**: порог
применяется к сегменту, и на малых объёмах HNSW не строится вовсе. Это не ошибка, но знать об этом надо: поиск идёт полным перебором.

Шаги 3 и 6 — парные; ошибка ровно здесь и стоит той самой «забытой особенности». Прохождение чек-листа целиком — лаб 4.

## Поиск

Современный универсальный метод — `query_points` (Query API), он же основа гибридного поиска:

```python
res = client.query_points(
    collection_name="contracts",
    query=query_vector,          # вектор запроса от той же модели
    limit=50,                    # кандидатов под реранкер — не 5
    with_payload=True,
    search_params=models.SearchParams(hnsw_ef=128),
).points

for p in res:
    print(p.score, p.payload["doc_id"], p.payload["clause_no"], p.payload["text"][:100])
```

`score` при COSINE — косинусная близость, больше = ближе. Абсолютное значение малоинформативно (0,72 — это хорошо или плохо? зависит от модели), сравнивать имеет смысл только внутри одной выдачи. Порог отсечения по score подбирать эмпирически и с осторожностью.

## Фильтрация

Сильная сторона Qdrant: фильтр применяется **внутри** обхода графа (filterable HNSW), а не как постобработка — то есть `limit=10` с фильтром вернёт 10 подходящих, а не «10 ближайших, из которых 2 прошли фильтр».

```python
flt = models.Filter(must=[
    models.FieldCondition(key="doc_type", match=models.MatchValue(value="перевозка")),
    models.FieldCondition(key="date_expire", range=models.DatetimeRange(gte="2026-10-01")),
])
res = client.query_points("contracts", query=qv, query_filter=flt, limit=50).points
```

Это техническая основа связки с SQL: реквизиты живут в SQL, их копия — в payload, и тогда «найди смысл среди вот этих договоров» делается одним запросом.

> [!warning] Это самое важное свойство базы для нас — и оно не проверено
> Фильтр `doc_id` на корпусе из сотен договоров имеет селективность в доли
> процента. Это ровно тот режим, где распространённая альтернатива —
> пост-фильтр (взять top-`k` по вектору, потом отбросить непрошедшие) —
> отказывает: возвращает три результата вместо десяти и **не даёт при этом
> ошибки**. Снаружи выглядит как «поиск иногда не находит».
>
> Отсюда переоценка: фильтрация — не удобство Qdrant, а условие
> работоспособности функции различения договора. И отсюда же — что её надо
> **измерить**, а не принять на веру: три утверждения этого справочника
> замер уже не подтвердил. Прибор — фильтрованный ANN-recall против точного
> перебора среди прошедших фильтр, кривой по нескольким селективностям,
> на коллекции с **принудительно включённым** индексом. Гипотеза `H-020`,
> методика — [[База знаний/06-vector-db/08-evaluation|08-evaluation]].
>
> Общее решение задачи в отрасли — ACORN, индекс без знания о будущих
> предикатах; разброс заявленного выигрыша от 2× до 1000× сам показывает,
> насколько плохо ведут себя обычные реализации на сложных предикатах.
> Разбор — [[База знаний/06-vector-db/04-filtering|04-filtering]].

## Что смотреть при отладке

```python
client.get_collection("contracts")   # status, points_count, indexed_vectors_count, config
client.count("contracts", exact=True)
client.scroll("contracts", limit=3, with_payload=True)   # глазами посмотреть, что реально лежит
```

`scroll` на первых шагах бесценен: половина «поиск не работает» оказывается «в payload не то, что мы думали» или «в тексте чанка мусор из парсера».

Полезно с самого начала: **снапшоты** коллекции (`create_snapshot`) перед экспериментами с параметрами — переиндексация корпуса дороже, чем кажется.

## Масштаб

Арифметика роста корпуса, что при этом не меняется и что включится сразу, — вынесены в [17-scale.md](17-scale.md). Коротко: HNSW у нас не строится, порог пересекается примерно на двухстах договорах, и вместе с ним включаются четыре механизма, которых сейчас нет.

## Открытые вопросы

1. На чужом сервере первым делом выясняется версия Qdrant — от неё зависит
наличие Query API, GPU-индексации и TurboQuant — и способ развёртывания.
2. Один узел или шарды/реплики — влияет на параллелизм загрузки.
3. Есть ли уже коллекции и соглашения об именовании.
4. ~~Наш замер: сколько реально занимает загрузка корпуса с приёмами и без~~ —
**закрыто 09.08.2026 лабой 4.** Пакетно против поштучно — ×22, gRPC против REST — ×3,3, оптимум батча 256–512, `parallel > 1` вредит, `indexing_threshold=0` не даёт обещанных +30 %. Три утверждения этого справочника из пяти замер не подтвердил.
5. Сколько сегментов правильно. Автосегментация дала 5 и тем самым отключила
индексацию: ни один сегмент не дорос до порога. Лечится ли это `default_segment_number` или пересмотром порога — на нашем масштабе не проверить ([[11-evidence#4. `indexing_threshold` считается на сегмент, а не на коллекцию]]).
6. `on_disk=True` не сравнивался с `False`, квантизация не трогалась вовсе.
Понадобится на боевых объёмах.
7. **Фильтрация внутри обхода графа не проверена.** Свойство
документировано и является для нас определяющим (различение договора), но три утверждения этого справочника замер уже не подтвердил. Прибор — фильтрованный ANN-recall кривой по селективностям, на коллекции с принудительно включённым индексом. Гипотеза `H-020`.
8. **Эталон точного поиска не зафиксирован, хотя сейчас бесплатен.**
Пока HNSW не построен, выдача точна по определению; сохранённая сегодня выдача золотого набора — готовый ground truth для всех будущих замеров ANN-recall. Позже его придётся считать специально.
9. **Устойчивость к перезаливкам не измерена.** Корпус
перезаливается десятками раз, перезапись по тому же `id` — это удаление плюс вставка, то есть накопление tombstone. Сейчас безвредно (индекса нет), при росте корпуса станет источником тихой деградации. Дешёвая защита без измерения — пересоздавать коллекцию вместо upsert поверх: заливка занимает 0,03 с. Гипотеза `H-021`.
