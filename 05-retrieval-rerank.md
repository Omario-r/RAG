# Поиск, реранкер и измерение качества

Дата: 28.07.2026. Третий пункт плана партнёра: «реранкер — второй эшелон
семантического поиска».

## Почему одного векторного поиска мало

Эмбеддинг-модель — **би-энкодер**: она сжимает документ в один вектор
*заранее*, ничего не зная о будущем запросе. Отсюда её слабости:

- весь пункт договора сжат в 1024 числа — детали неизбежно теряются;
- запрос и документ никогда не «встречаются» — модель не может взвесить,
  какая часть пункта относится к вопросу;
- HNSW к тому же приблизительный: истинно ближайший сосед может не попасть
  в выдачу.

Плюс — скорость: миллион документов просматривается за миллисекунды.

## Реранкер: что это

**Кросс-энкодер**: на вход подаётся *пара* (запрос, документ) целиком, модель
читает их вместе и выдаёт одно число — насколько документ отвечает на запрос.
Точность заметно выше, потому что модель видит взаимодействие слов запроса и
документа.

Плата — стоимость: нельзя посчитать заранее, надо гонять модель на каждой паре
в момент запроса. Для миллиона документов невозможно, для 50 кандидатов —
десятки-сотни миллисекунд.

Отсюда **каскад** — ровно то, что описал партнёр:

```
запрос
 → Qdrant (би-энкодер + HNSW): 100 000 чанков → top-50   [быстро, грубо]
 → реранкер (кросс-энкодер):        top-50 → top-5       [медленно, точно]
 → контекст главной модели
```

Смысл каскада: дешёвый этап отвечает за **полноту** (не потерять нужное),
дорогой — за **точность** (не пустить лишнее). Поэтому `limit` на первом
этапе ставится щедро (50–100), а не 5: то, что не попало в кандидаты,
реранкер уже не спасёт.

## Модели-реранкеры (июль 2026)

| Модель | Размер | Лицензия | Замечание |
|---|---|---|---|
| **bge-reranker-v2-m3** | ~0,6B | Apache 2.0 | Мультиязычный, безопасный дефолт; проверенно работает в llama.cpp |
| Qwen3-Reranker (0.6B / 4B / 8B) | 0,6–8B | Apache 2.0 | Генеративный, понимает инструкции («что считать релевантным»); в GGUF есть подводные камни (см. ниже) |
| mxbai-rerank-large-v2 | — | Apache 2.0 | Альтернатива с чистой лицензией |
| jina-reranker-v2-base-multilingual | ~0,3B | **CC-BY-NC-4.0** | Быстрый, но **некоммерческая лицензия — нам не подходит** |

Кандидат по умолчанию для нашего случая: **bge-reranker-v2-m3** — мультиязычный,
лёгкий, Apache 2.0, отлаженный путь запуска. Qwen3-Reranker — второй кандидат
для сравнения на нашем корпусе.

Лицензия здесь — не формальность: продукт ставится в контур клиента, NC-лицензия
закрывает коммерческое использование (тот же критерий, что для моделей в
`Business/legal-ai/02-tech.md`).

## Запуск реранкера в llama.cpp

Тот же сервер, отдельный процесс с другой моделью и флагами:

```bash
llama-server -m bge-reranker-v2-m3.gguf --embedding --pooling rank --reranking --port 8081
```

Обязательны все три: `--embedding`, `--pooling rank`, `--reranking`.

Эндпоинты: `/rerank`, `/reranking`, `/v1/rerank`, `/v1/reranking`.

```json
POST /v1/rerank
{ "model": "reranker", "query": "простой транспорта под погрузкой",
  "documents": ["текст чанка 1", "текст чанка 2", ...], "top_n": 5 }
```

Ответ: `{"results": [{"index": 3, "relevance_score": 0.94}, ...]}` — то есть
номера входных документов и их оценки; сами тексты возвращать не обязательно.

**Известная ловушка:** у части GGUF-конвертаций Qwen3-Reranker скоры выходят
почти нулевыми (порядка 1e-23) из-за неверной конвертации (потерянные веса
`cls.output.weight`). Симптом — все документы получают одинаково ничтожную
оценку. Лечится правильной конвертацией; ещё один довод начать с bge-reranker-v2-m3.

Санитарная проверка после запуска: подать один заведомо релевантный документ
и один заведомо нерелевантный — разница в скорах должна быть очевидной.

## Гибридный поиск — вероятный следующий шаг

Векторный поиск плохо ловит **точные редкие токены**: номер договора
«ТР-114/2026», ИНН, фамилию, специфический термин. Классический полнотекстовый
(BM25) — наоборот, ловит их отлично, но не понимает синонимов.

Qdrant умеет держать в одной коллекции плотный и разреженный векторы и
объединять выдачи в одном запросе через Query API:

```python
client.query_points(
    collection_name="contracts",
    prefetch=[
        models.Prefetch(query=dense_vector,  using="dense",  limit=50),
        models.Prefetch(query=sparse_vector, using="sparse", limit=50),
    ],
    query=models.FusionQuery(fusion=models.Fusion.RRF),
    limit=50,
)
```

**RRF** (Reciprocal Rank Fusion) объединяет два списка по *позициям*, а не по
оценкам — и это не деталь: косинус ограничен диапазоном, BM25 не ограничен
вообще, складывать их напрямую некорректно без нормализации. RRF обходит
проблему, используя только порядок.

Для договоров с их номерами, реквизитами и терминологией гибрид почти наверняка
даст прирост. Но по порядку: сначала dense + реранкер, замер; потом гибрид,
замер. Иначе непонятно, что именно помогло.

## Как мерить качество

Без этого раздела всё остальное — вкусовщина. Идея та же, что в плане
бенчмарка моделей из бизнес-волта: **ворота, а не мнение**.

### Золотой набор

20–30 вопросов, для каждого заранее указан правильный ответ — конкретные
пункты конкретных договоров:

```yaml
- q: "Какая неустойка за просрочку доставки?"
  relevant: ["TR-114#4.2", "TR-118#5.1"]
- q: "Кто оплачивает простой транспорта под погрузкой?"
  relevant: ["TR-114#3.7"]
- q: "Договоры, где ответственность экспедитора ограничена суммой"
  relevant: ["TR-120#6.3", "TR-122#6.1"]
```

Составляется руками по тестовым договорам — час-два работы, окупается всем
дальнейшим. Вопросы формулировать **не словами договора**: если в вопросе те
же слова, что в пункте, задача вырождается в поиск по подстроке и любой метод
покажет отличный результат.

### Метрики

| Метрика | Что показывает | Где смотреть |
|---|---|---|
| **recall@50** | Доля вопросов, где нужный чанк попал в кандидаты | Потолок качества: что потеряно здесь, не вернуть |
| **recall@5** | То же для финальной выдачи | Что реально увидит модель |
| **MRR** | Средняя обратная позиция первого верного | Чувствительна к порядку |
| **nDCG@5** | Учитывает и порядок, и несколько верных ответов | Общая оценка |
| latency | Время запроса по этапам | Практическая пригодность |

Реранкер оценивается ровно одним сравнением: recall@5 и nDCG@5 **до** и
**после** него на одном золотом наборе. Если прироста нет — проблема не там
(скорее всего в чанкинге), и это ценный результат.

### Дисциплина эксперимента

Менять по одному параметру за раз и записывать результат в журнал:

| Дата | Изменение | recall@50 | recall@5 | nDCG@5 | Комментарий |
|---|---|---|---|---|---|
| … | базовая линия: чанки 512, dense | … | … | … | … |
| … | + контекстуализация чанков | … | … | … | … |
| … | + реранкер bge-v2-m3 | … | … | … | … |

Такой журнал — заодно готовый материал для демо крупному клиенту: «вот как мы
настраивали качество на вашем типе документов». Отдельный файл заведём, когда
появятся первые цифры.

### Оговорка про сгенерированные договоры

Тестовые договоры сгенерированы LLM. Риск: они однообразны по формулировкам,
и поиск на них покажет качество выше реального. Поэтому золотой набор стоит
строить с намеренно «чужими» формулировками вопросов, а окончательные выводы
делать на настоящих документах, когда появятся. Пометить это как ограничение
всех цифр этапа.

## Открытые вопросы

1. Поднимать реранкер на том же VPS или отдельно (память, конкуренция за GPU).
2. Сколько кандидатов оптимально: 50 или 100 — компромисс качество/latency.
3. Нужен ли гибрид уже на MVP или после замера dense.
4. Кто составляет золотой набор — партнёр по сгенерированным договорам или мы.
