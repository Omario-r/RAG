# Векторизация: llama.cpp-сервер и модели эмбеддингов

Дата: 28.07.2026. Шаг 2 из вводной партнёра: скрипт обращается к VPS
с llama.cpp, получает вектора.

## Что такое эмбеддинг — рабочее определение

Эмбеддинг — массив чисел фиксированной длины (например 1024), в который
модель сворачивает смысл текста. Свойства, которые нам важны:

- **Длина фиксирована** и определяется моделью, а не длиной текста. И пункт
  из 20 слов, и раздел из 500 дают вектор одной длины. Эта длина —
  **размерность** — задаётся при создании коллекции Qdrant и потом не
  меняется: сменили модель → пересоздали коллекцию и переиндексировали всё.
- **Близость = похожесть смысла.** Метрика для текстовых моделей — косинусная
  (угол между векторами), диапазон −1…1, где 1 — «про одно и то же».
- **Модель одна на всё.** Документы и запросы обязаны векторизоваться одной
  моделью и одним способом. Разные модели дают несопоставимые пространства —
  поиск выдаст шум, и это не будет выглядеть как ошибка.

## Нормализация и почему это не мелочь

Если векторы нормированы (длина = 1), косинусная близость равна скалярному
произведению — считается быстрее, и `Distance.COSINE` и `Distance.DOT` дают
одинаковый порядок результатов.

llama.cpp по умолчанию нормализует по евклидовой норме: флаг `--embd-normalize`
имеет значение по умолчанию `2` (евклидова), `-1` — без нормализации. Эндпоинт
`/v1/embeddings` возвращает векторы, нормализованные по евклидовой норме.

Практика: в Qdrant всё равно ставим `Distance.COSINE` — он корректен и для
ненормированных векторов; терять на этом нечего, а от ошибки конфигурации
страхует.

## llama.cpp-сервер: запуск и API

### Флаги, относящиеся к эмбеддингам

| Флаг | Что делает |
|---|---|
| `--embedding` / `--embeddings` | Включает режим эмбеддингов и эндпоинт `/v1/embeddings`. Только для эмбеддинг-моделей |
| `--pooling {none,mean,cls,last,rank}` | Как свернуть токены в один вектор. Если не задан — берётся дефолт модели |
| `--embd-normalize N` | Нормализация: `-1` нет, `2` евклидова (по умолчанию) |
| `--ubatch-size N` | Физический размер батча, по умолчанию 512 |
| `-c N` | Контекст |

**Про pooling.** Модель выдаёт вектор на каждый токен; pooling сворачивает их
в один вектор на текст. Тип зависит от модели и задан её архитектурой:
у BGE-M3 — `cls`, у многих других — `mean`. Неверный pooling не даёт ошибки —
он тихо даёт плохие векторы. Это ровно тот класс дефектов, который обнаруживается
только замером качества поиска.

**Про `--ubatch-size` — практическая ловушка.** Для моделей с pooling вся
последовательность должна поместиться в один физический батч: увеличивать
`n_batch` выше `n_ubatch` смысла нет. Если `--ubatch-size 512`, то текст
длиннее 512 токенов обрабатывать нечем — при длинных чанках сервер нужно
поднимать с бо́льшим `--ubatch-size` (например 2048 = максимум 2048 токенов
на текст). Наш чанк в 200–500 токенов сюда влезает, но контекстуализированные
чанки и small-to-big-родители могут не влезть — проверить у партнёра.

### Эндпоинты

| Эндпоинт | Особенности |
|---|---|
| `POST /v1/embeddings` | OpenAI-совместимый. Требует pooling ≠ `none`. Возвращает нормализованные векторы. Удобен: работает любой OpenAI-клиент |
| `POST /embedding` | Нативный llama.cpp. Поддерживает все режимы pooling, включая `none`, принимает `content` и `embd_normalize` |

Практика: берём `/v1/embeddings` — совместимость с экосистемой важнее
тонкой настройки.

Формат запроса (OpenAI-совместимый):

```json
POST /v1/embeddings
{ "model": "любая-строка", "input": ["текст чанка 1", "текст чанка 2"] }
```

Ответ:

```json
{ "data": [ {"index": 0, "embedding": [0.021, -0.14, ...]}, ... ],
  "usage": {...} }
```

`input` принимает массив — **это наш главный рычаг скорости на шаге 2**:
батчить тексты пачками по 16–64, а не слать по одному. Размер батча
подбирается по `--ubatch-size` и памяти сервера. Порядок ответов
соответствует порядку входа, но при батчинге надёжнее опираться на `index`.

### Как проверить сервер, когда появится адрес

```bash
curl -s http://VPS:PORT/v1/models
```

```bash
curl -s http://VPS:PORT/v1/embeddings -H 'Content-Type: application/json' -d '{"model":"x","input":["тест"]}' | python3 -c "import json,sys; d=json.load(sys.stdin)['data'][0]['embedding']; print(len(d), d[:5])"
```

Вторая команда сразу даёт **размерность вектора** — число, без которого нельзя
создать коллекцию в Qdrant.

Санитарная проверка качества (до всякого пайплайна): взять три текста —
два про одно и то же, один про другое — и убедиться, что косинус первых двух
заметно выше. Звучит наивно, но ловит и неверный pooling, и неподходящую
модель, и забытые префиксы.

## Префиксы и инструкции — источник тихих провалов

Многие эмбеддинг-модели обучены **асимметрично**: запрос и документ надо
подавать по-разному.

| Семейство | Как подавать |
|---|---|
| E5 (`multilingual-e5-*`) | `query: <текст>` и `passage: <текст>` |
| FRIDA | Префиксы задач: `search_query:` / `search_document:` (проверить актуальный список) |
| GigaEmbeddings-instruct | Инструктивный формат: `Instruct: <описание задачи>\nQuery: <текст>` |
| Qwen3-Embedding | Поддерживает инструкции для запроса; документы — без |
| BGE-M3 | Без префиксов |

Забытый префикс не даёт ошибки — он даёт незаметно деградировавший поиск.
Поэтому вопрос «какая модель и какие префиксы» — первый в списке партнёру,
а формирование текста для векторизации в коде должно быть **одной функцией**,
общей для индексации и для запроса, с явным параметром «это запрос или
документ».

## Модели для русского языка (июль 2026)

Ориентиры по ruMTEB (русская часть MTEB). Цифры — из обзорной статьи, не наши
замеры; служат для выбора кандидатов, а не для решения.

| Модель | Параметры | Контекст | Размерность | ruMTEB* | Лицензия |
|---|---|---|---|---|---|
| Qwen3-Embedding-8B | 8B | 32k | 4096 | ~70,6 | Apache 2.0 |
| Qwen3-Embedding-4B | 4B | 32k | 2560 | ~69,5 | Apache 2.0 |
| Giga-Embeddings-instruct (Sber) | 3B | 4096 | 1024 | ~69,1 | MIT |
| Qwen3-Embedding-0.6B | 0,6B | 32k | 1024 | — | Apache 2.0 |
| BGE-M3 | ~0,6B | 8192 | 1024 | ниже | MIT |
| FRIDA (SberDevices) | ~0,8B | 512 | 1536 | ниже | MIT |
| multilingual-e5-large | ~0,6B | 512 | 1024 | заметно ниже | MIT |

\* Порядок величин; разница в 1–1,5 пункта на практике неразличима.

Выводы для нас:

- **Поколение важнее тонкого выбора.** Модели прошлого поколения (e5, RoSBERTa)
  отстают на 4–5 пунктов — на них имеет смысл идти только при отсутствии GPU.
- **Размерность влияет на стоимость хранения линейно.** 4096 против 1024 —
  вчетверо больше памяти под векторы и заметно более дорогая индексация.
  Для корпуса договоров средней компании выигрыш в качестве почти наверняка
  не окупает 4096; кандидаты по умолчанию — 1024–1536.
- **Лицензии чистые** (MIT/Apache 2.0) у всех кандидатов — важно для
  коммерческого использования в контуре клиента (критерий из
  `Business/legal-ai/02-tech.md`).
- **Контекст 512 токенов у FRIDA** — реальное ограничение: контекстуализированный
  чанк может не влезть. Учитывать при выборе.

Что именно стоит на VPS — вопрос партнёру; от ответа зависят размерность
коллекции, префиксы и максимальная длина чанка.

## Сколько это стоит по времени

Ориентир для планирования, проверить замером: десяток договоров → сотни чанков →
одна пачка запросов на векторизацию, минуты. То есть на нашем масштабе
векторизация — не узкое место; узким местом станет загрузка в Qdrant
([04](04-qdrant.md)) и качество ([05](05-retrieval-rerank.md)).

Планировать на будущее стоит другое: при переиндексации корпуса крупного
клиента (десятки тысяч документов) векторизация станет часами GPU-времени.
Отсюда практическое требование к коду с самого начала — **кэшировать векторы
по хэшу текста чанка**, чтобы повторная сборка не пересчитывала то, что не
менялось.

## Открытые вопросы

1. Какая модель на VPS, её размерность, pooling, префиксы, `--ubatch-size`.
2. Один ли это процесс с чат-моделью или отдельный (влияет на параллелизм).
3. Есть ли аутентификация на эндпоинте и лимиты на размер батча.
4. Планируется ли сменить модель — если да, слой абстракции над векторизацией
   нужен сразу.
