# Векторизация: наш llama.cpp-сервер и наши замеры

> [!info] Узел «Эмбеддинги»
> **Теория:** [[База знаний/05-embeddings/README|05-embeddings]] — методы,
> измерение качества, ландшафт моделей, словарь ·
> **Лаба:** [Лаб 2: векторизация](Лабы/lab-02-embeddings.md)
>
> Здесь — как поднят и настроен наш эмбеддер, что на нём замерено и какие
> из замеров опровергли ожидания. Устройство эмбеддингов, обзор моделей
> и метрик — в теории.

Рабочее определение: эмбеддинг — массив чисел фиксированной длины (у нас 1024), в который модель сворачивает смысл текста; близость = похожесть. Три свойства, из которых следуют наши решения:

- **длина задаётся моделью, а не текстом.** Размерность фиксируется при
создании коллекции: сменили модель → пересоздали коллекцию и переиндексировали всё;
- **модель одна на всё.** Документы и запросы векторизуются одной моделью
с одинаковой подготовкой текста;
- **нормализация.** llama.cpp нормализует по евклидовой норме
(`--embd-normalize 2` по умолчанию), `/v1/embeddings` возвращает уже нормализованные векторы. В Qdrant всё равно ставим `Distance.COSINE`: он корректен и для ненормированных, терять нечего, а от ошибки конфигурации страхует.

## Как стоит сейчас

Снимок стенда — `RAG-stand/run-embedder.sh`. Всё ниже читается относительно него.

| Параметр | Значение у нас |
|---|---|
| Модель | `Qwen/Qwen3-Embedding-0.6B-GGUF:Q8_0`, 1024 измерения |
| Флаги | `--embeddings`, `--parallel 1`, `-c 8192`, порт 8080, `--api-key` |
| Пулинг | **флагом не задан** — берётся дефолт модели (`mean`) |
| Префиксы | **не используются**: Qwen3 их не требует, замер прироста не показал |
| Нормализация | дефолтная евклидова, в Qdrant всё равно `Distance.COSINE` |
| Кэш векторов по хэшу | требование записано, **в коде стенда нет** |

## Флаги, которые нас касаются

| Флаг | Что делает |
|---|---|
| `--embedding` / `--embeddings` | режим эмбеддингов и эндпоинт `/v1/embeddings` |
| `--pooling {none,mean,cls,last,rank}` | как свернуть токены в один вектор; без флага — дефолт модели |
| `--embd-normalize N` | `-1` нет, `2` евклидова (по умолчанию) |
| `--ubatch-size N` | физический размер батча, по умолчанию 512 |
| `-c N` | контекст |

**Пулинг задан архитектурой модели и не даёт ошибки при промахе** — он тихо даёт плохие векторы. У нас это самый большой замеренный разрыв: `mean` 0,815 против `cls` 0,741 по `recall@5`. Дефекты этого класса ловятся только замером качества поиска.

**`--ubatch-size` не ограничивает длину текста — опровергнуто 06.08.2026.** Раньше здесь стояло обратное со ссылкой на обсуждение в трекере llama.cpp от 2024 года. На сборке b10280 текст в 30 000 токенов проходит при дефолтном `n_ubatch=512`. Предел задаёт `-c`, при превышении приходит явная ошибка `400 exceed_context_size_error` с полями `n_prompt_tokens` и `n_ctx` — молчаливого обрезания нет ([[11-evidence#8. Предельную длину текста задаёт `-c`, а не `--ubatch-size`]]).

Следствие: на чужом сервере спрашивать `--ubatch-size` незачем — важен `-c`, и он виден в `/props`. Длина текста — размен на память, замер на Qwen3-Embedding-0.6B Q8_0, один слот:

| `-c` | Память |
|---|---|
| 2048 | 947 МБ |
| 4096 | 1171 МБ |
| 8192 | 1619 МБ |
| 16384 | 2515 МБ |

Число слотов (`--parallel`) множит KV-кэш: дефолтные 4 слота с большим контекстом дают многократный перерасход при нулевой пользе для пакетной векторизации.

Урок общего характера: цифра из чужого трекера — гипотеза, а не результат, даже когда звучит технически убедительно. Проверка заняла три минуты.

## Эндпоинты

| Эндпоинт | Особенности |
|---|---|
| `POST /v1/embeddings` | OpenAI-совместимый, требует pooling ≠ `none`, возвращает нормализованные векторы. **Наш выбор** — совместимость с экосистемой важнее тонкой настройки |
| `POST /embedding` | нативный, поддерживает все режимы пулинга, принимает `content` и `embd_normalize` |

```json
POST /v1/embeddings
{ "model": "любая-строка", "input": ["текст чанка 1", "текст чанка 2"] }
```

Ответ: `{"data": [{"index": 0, "embedding": [0.021, -0.14, ...]}, ...]}`. Порядок ответов соответствует входу, но опираться надёжнее на `index`.

**Батчинг ничего не ускоряет — опровергнуто 07.08.2026.** Здесь раньше было записано, что батчить пачками по 16–64 обязательно. На нашем стенде 100 реальных пунктов векторизуются за 3,5–4,2 с в любой комбинации: по одному, по 16, по 64, в четыре потока, с одним слотом и с четырьмя. Узкое место — сам расчёт модели на Metal, а не накладные расходы на запросы ([[11-evidence#1. Батчинг ничего не ускоряет]]).

Следствия:

1. Батчинг в коде всё равно делаем — ради аккуратности и меньшего числа
точек отказа, а не ради скорости. Обещать ускорение в отчётах нельзя.
2. `--parallel 1` на стенде ничего не стоит; решение экономить KV-кэш
подтверждено замером, а не оправдано задним числом.
3. **На GPU проверять заново:** замер снят на M4 с моделью 0,6B
и текстами по ~50 токенов, на дискретной карте соотношение может быть другим.

## Как опросить чужой сервер, имея только адрес

```bash
curl -s http://ХОСТ:ПОРТ/v1/models
```

Размерность видна прямо здесь, векторизовать ничего не нужно — в ответе, кроме OpenAI-совместимого `data`, лежит блок `meta`:

| Поле | На нашем стенде | Что означает |
|---|---|---|
| `n_embd` | 1024 | **размерность вектора** — размер коллекции Qdrant |
| `n_ctx` | 8192 | фактический контекст сервера |
| `n_ctx_train` | 32768 | на каком контексте модель обучали |
| `n_params` | 595776512 | размер модели |
| `ftype` | Q8_0 | квантизация |

Расхождение `n_ctx` с `n_ctx_train` — чужое решение при запуске, а не свойство модели. Полю `capabilities` не верить: у эмбеддера в нём стоит `["completion"]`, что неверно.

`/props` возвращает **фактически применённую** конфигурацию — имя модели, квантизацию, версию сборки, эффективный контекст, число слотов:

```bash
curl -s http://ХОСТ:ПОРТ/props | python3 -m json.tool
```

**Правило: конфигурацию читать у сервера, а не у скрипта.** На нашем же стенде скрипт запуска содержал `--ubatch-size 2048`, а сервер работал с 512 — команда в bash оборвалась на пустой строке после обратного слеша. `/props` показывал реальность, ошибались мы ([08](08-local-stand.md)).

Чего в `/props` нет — **типа пулинга**. Его придётся спрашивать или выводить косвенно — сравнением векторов чужого сервера с локальной копией той же модели, косинус 0,9998 с `cls` против 0,90–0,94 с `mean` ([[11-evidence#15. Тип pooling определяется по API, если есть та же модель рядом]]).

Предельную длину входа тоже можно измерить, а не спрашивать: слать тексты растущей длины до `400 exceed_context_size_error`.

## Один текст — два вектора

Ожидание: одинаковый вход даёт одинаковый выход. **На llama.cpp это неверно**, и неверно предсказуемым образом — результат зависит от того, лежит ли текст в кэше промптов:

| Состояние сервера | Результат |
|---|---|
| холодный расчёт | побитово один и тот же вектор, сколько ни повторяй |
| тёплый (кэш держит этот же текст) | тоже стабильный — но **другой** вектор |
| два одинаковых текста в одном запросе | побитово равны между собой |

Расхождение холодного и тёплого: косинус 0,99999929. `cache_prompt: false` эндпоинт `/v1/embeddings` игнорирует.

Для качества поиска это ничто — разрыв между «похоже» и «не похоже» на нашем стенде 0,47. Но два вывода важные:

1. **Не проверять пайплайн сравнением векторов на равенство.** Сравнивать
косинусом с порогом (`> 0,9999`), а не `==`.
2. **Кэш по хэшу текста нужен ради воспроизводимости, а не только скорости.**
Без него «переиндексировали, метрика сдвинулась на 0,3 %» неотличимо от настоящего изменения ([[11-evidence#2. Один и тот же текст даёт два разных вектора]]).

## Пустой текст не даёт ошибки

`""`, `"   "` и `"\n"` возвращают нормальный вектор длины 1024 с нормой 1,0 — каждый свой, никакого `400`. Значит, пустой чанк молча займёт место в коллекции и будет находиться поиском наравне с осмысленными. Отсюда требование к чанкеру ([02](02-chunking.md)): отбрасывать пустые и слишком короткие чанки на своей стороне.

## Префиксы: два разных утверждения

Многие модели обучены асимметрично — запрос и документ подаются по-разному (`query:` / `passage:` у E5, инструкции у Qwen3, без префиксов у BGE-M3). Забытый префикс не даёт ошибки, он даёт незаметно деградировавший поиск. Поэтому подготовка текста в коде — **одна функция**, общая для индексации и запроса, с явным параметром «запрос или документ».

Замер 08.08.2026 на `multilingual-e5-large` развёл два тезиса, которые принято смешивать.

**«Модель требует префиксов» — подтверждено.** Без них возникает семантическая инверсия: «код» оказывается ближе к «коту», чем «собака» — совпадение по буквам бьёт совпадение по смыслу. Префиксы её чинят при обоих режимах пулинга.

> [!warning] Цифры ниже сняты на партии 1 — 144 чанка
> Это вырожденная задача: `top-50` покрывал треть корпуса, и метрики стояли на потолке. На текущей коллекции в 1446 чанков тот же золотой набор даёт `hit@5` 0,562 вместо 1,000 — [[checks/runs#`RUN-20260820-A` — тот же золотой набор на выросшем корпусе|RUN-20260820-A]]. Числа партии 1 годятся для сравнения между собой и не годятся как оценка качества.

**«Префиксы дают прирост поиска» — не подтверждено.** На золотом наборе:

| Конфигурация | recall@5 | recall@10 | MRR |
|---|---|---|---|
| e5 mean, без префиксов | **0,815** | 0,827 | **0,848** |
| e5 mean, `query:`/`passage:` | 0,796 | **0,883** | 0,831 |

Различие — один вопрос из 27, то есть шум.

**Вывод.** Префиксы ставить надо: они предписаны устройством модели. Обещать от них прирост нельзя — измерить его на нашем корпусе не удалось. Формулировка «без префиксов поиск деградирует» — переоценка, в переписке наружу не использовать. Для нашей рабочей модели Qwen3 префиксы не требуются вовсе ([[11-evidence#3. Префиксы-инструкции не нужны]]).

**И про метод.** Проверка на парах слов предсказала эффект, которого на метрике нет; с пулингом вышло наоборот — на парах слов ничего, а на `recall@5` самый большой разрыв из всех измеренных. Игрушечный тест годится для ловли грубых поломок и не годится для выбора конфигурации ([[11-evidence#11. Санитарная проверка не предсказывает метрику]]).

## Выбор модели

Работаем на **Qwen3-Embedding-0.6B Q8_0**: 1024 измерения, контекст 32k, Apache 2.0. Что из ландшафта важно для решения — три вещи, остальное в теории:

- **Разрыв поколений по ruMTEB на нашей задаче не проявляется.**
`multilingual-e5-large` против Qwen3: `recall@5` 0,815 против 0,790 — два вопроса из 27, статистически неотличимо. Вывод не в том, что e5 лучше, а в том, что **на нашем корпусе разница между поколениями моделей не измеряется** — выбирать по ruMTEB не на чем.
- **Размерность стоит линейно.** 4096 против 1024 — вчетверо больше памяти
под векторы и дороже индексация; для корпуса договоров средней компании выигрыш почти наверняка не окупается. Кандидаты — 1024–1536.
- **Контекст 512 у FRIDA** — реальное ограничение: контекстуализированный
чанк может не влезть.

Лицензии у всех кандидатов чистые (MIT / Apache 2.0), это обязательное условие для контура клиента.

## Сколько это стоит по времени

Замерено 07.08.2026, Qwen3-Embedding-0.6B Q8_0, MacBook Air M4:

| Что | Значение |
|---|---|
| Один текст ~50 токенов | ≈40 мс |
| 100 текстов | 3,5–4,2 с, как ни батчи |
| Пропускная способность | ≈1350 токенов/с |
| Корпус партии 1 (168 пунктов) | ≈7 с |

На нашем масштабе векторизация — не узкое место вообще; узкое место дальше, в загрузке ([04](04-qdrant.md)) и в качестве ([05](05-retrieval-rerank.md)).

Производная для чанкинга: русский юридический текст даёт **2,76 символа на токен**. Средний пункт TR-114 — 140 символов, около 50 токенов; в контекст 8192 помещается раздел на ~22 000 символов, упереться в предел на пунктах невозможно — только на родительских разделах small-to-big. Коэффициент несопоставим между моделями, у каждой свой токенизатор ([[11-evidence#5. Коэффициент «символов на токен» несопоставим между моделями]]).

На будущее: при переиндексации корпуса крупного клиента векторизация станет часами GPU-времени. Отсюда требование к коду с самого начала — **кэшировать векторы по хэшу текста чанка**.

## Открытые вопросы

1. Смена модели эмбеддера ломает всё сразу — размерность, пулинг, префиксы,
предел длины. Слой абстракции над векторизацией нужен до того, как она понадобится, а не после.
2. **Обратимость векторов ни с кем не обсуждалась.** Из эмбеддинга
восстанавливается исходный текст (порядка 92 % на коротких фрагментах), то есть коллекция Qdrant по режиму доступа равна хранилищу самих договоров, а не обезличенным данным. Вопрос к архитектуре контура: считается ли векторная база отдельным объектом защиты. Разбор — [[База знаний/05-embeddings/01-methods|01-methods]], раздел 8.
3. **Кривая усечения размерности не построена.** Модель заявляет матрёшку —
значит, 1024 можно урезать до 512 или 256 без смены модели и без повторной векторизации. Проверяется из готового индекса за один прогон, гипотеза `H-016` в [checks/hypotheses.md](checks/hypotheses.md).
4. **Линейный адаптер на запросах** улучшает поиск без переиндексации —
самый дешёвый неиспользованный приём, упирается в размер золотого набора.

**Приём опроса чужого сервера отработан 10.08.2026** на второй площадке: модель, размерность, пулинг, контекст и аутентификация выясняются по API, без доступа к машине — [[Партнёр/README|другие площадки]].
