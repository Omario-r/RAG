## Как читать вывод

Qdrant заворачивает **любой** ответ в одну и ту же оболочку:

```json
{"result": ...полезное..., "status": "ok", "time": 0.000273}
```

Дальше показывается только содержимое `result` — иначе примеры разбухают
втрое. Чтобы не гадать, что перед вами, у каждого блока с выводом стоит
маркер:

| Маркер | Что означает |
|---|---|
| **Вывод (дословно)** | Скопировано из терминала как есть, вместе с оболочкой |
| **Выжимка** | Показано только содержательное; команда печатает больше |
| **Схема формата** | Показаны поля, значения выдуманы — со своими не сравнивать |

Если ваш вывод отличается от блока с маркером **Вывод (дословно)** — есть
что разбирать. Если от **Выжимки** — сначала убедитесь, что отличие не
сводится к оболочке `result` / `status` / `time`.

## Подготовка

Поднять стенд, если не поднят:

```bash
~/Development/Home/RAG-stand/start-stand.sh
```

Загрузить адреса и ключи в текущую оболочку:

```bash
source ~/Development/Home/RAG-stand/.env
```

Определить короткую обёртку, чтобы не повторять ключ в каждой команде:

```bash
qd() { curl -s -H "api-key: $QDRANT_API_KEY" -H 'Content-Type: application/json' "$@" | python3 -m json.tool --no-ensure-ascii; }
```

`--no-ensure-ascii` здесь обязателен. Без него `json.tool` печатает русский
текст как `"ответ..."` — формально верный JSON,
но читать payload договоров становится невозможно.

Обёртка живёт до закрытия окна терминала. Открыли новое — повторить `source`
и определение `qd`.

Дашборд: http://127.0.0.1:6333/dashboard — попросит API-ключ, он в `.env`.
Держите открытым во второй вкладке: после каждой команды полезно посмотреть
на то же самое глазами.

## Шаг 2. Создать игрушечную коллекцию

Размерность 4 вместо настоящих 1024 — чтобы векторы можно было писать руками
и предсказывать результат поиска.

```bash
qd -X PUT $QDRANT_URL/collections/toy -d '{"vectors": {"size": 4, "distance": "Cosine"}}'
```

Посмотреть, что получилось:

```bash
qd $QDRANT_URL/collections/toy
```

В команде два параметра, и оба задаются навсегда:

| В запросе | Значение | Что это |
|---|---|---|
| `size` | 4 | **размерность** — сколько чисел в каждом векторе |
| `distance` | `Cosine` | **метрика близости** — по какому правилу Qdrant считает, что два вектора похожи |

Дальше в лабе слово «метрика» означает именно поле `distance`. `Cosine` —
косинус угла между векторами; чем ближе к 1, тем ближе смысл. Что именно
он измеряет, видно будет в шаге 8, где мы это проверим руками.

**Что заметить:** оба параметра меняются только пересозданием коллекции —
[[#Почему размерность нельзя поменять|почему]].

В ответе есть `status`, `points_count`, `indexed_vectors_count` и полный
конфиг. К последнему полю вернёмся в шаге 16.

## Шаг 3. Залить пойнты

Шесть чанков из воображаемых договоров. Числа в `vector` **вписаны руками,
а не посчитаны моделью** — для лабы введено соглашение: каждая координата
отвечает за одну тему.

| Позиция | Тема | У каких пойнтов большая |
|---|---|---|
| 1-я | ответственность | 1, 2 |
| 2-я | оплата | 3, 4 |
| 3-я | сроки | 5, 6 |
| 4-я | ничего, запас | — |

Поэтому пойнт 1 — `[0.9, 0.1, 0, 0]`: сильно «про ответственность», чуть-чуть
«про оплату». Пойнт 5 — `[0, 0, 0.9, 0.1]`: чистые сроки. В настоящей системе
такого соглашения нет — [[#Чем игрушечные векторы отличаются от настоящих|чем игрушка отличается от настоящего]].

```bash
qd -X PUT "$QDRANT_URL/collections/toy/points?wait=true" -d '{"points": [
  {"id": 1, "vector": [0.9, 0.1, 0.0, 0.0], "payload": {"doc_id": "TR-114", "clause": "4.2", "topic": "ответственность", "doc_type": "перевозка",      "date_expire": "2026-12-31T00:00:00Z", "amount": 4500000, "text": "За просрочку доставки Перевозчик уплачивает неустойку 0,1%"}},
  {"id": 2, "vector": [0.8, 0.2, 0.0, 0.0], "payload": {"doc_id": "TR-118", "clause": "6.1", "topic": "ответственность", "doc_type": "экспедирование", "date_expire": "2026-10-15T00:00:00Z", "amount": 1200000, "text": "Ответственность Экспедитора ограничена суммой 500 000 рублей"}},
  {"id": 3, "vector": [0.0, 0.9, 0.1, 0.0], "payload": {"doc_id": "TR-114", "clause": "3.1", "topic": "оплата",          "doc_type": "перевозка",      "date_expire": "2026-12-31T00:00:00Z", "amount": 4500000, "text": "Оплата производится в течение 10 банковских дней"}},
  {"id": 4, "vector": [0.1, 0.85, 0.05, 0.0], "payload": {"doc_id": "TR-120", "clause": "3.4", "topic": "оплата",         "doc_type": "аренда_ТС",      "date_expire": "2027-03-01T00:00:00Z", "amount": 900000,  "text": "Арендная плата вносится ежемесячно до 5 числа"}},
  {"id": 5, "vector": [0.0, 0.0, 0.9, 0.1], "payload": {"doc_id": "TR-118", "clause": "2.3", "topic": "сроки",            "doc_type": "перевозка",      "date_expire": "2026-10-15T00:00:00Z", "amount": 1200000, "text": "Срок доставки груза — 5 календарных дней с даты погрузки"}},
  {"id": 6, "vector": [0.0, 0.1, 0.85, 0.05], "payload": {"doc_id": "TR-120", "clause": "8.2", "topic": "сроки",          "doc_type": "аренда_ТС",      "date_expire": "2027-03-01T00:00:00Z", "amount": 900000,  "text": "Договор действует до 1 марта 2027 года"}}
]}'
```

Проверить количество:

```bash
qd -X POST $QDRANT_URL/collections/toy/points/count -d '{"exact": true}'
```

**Выжимка** — в `result` придёт `{"count": 6}`.

`wait=true` в первой команде намеренно: без него `count` может успеть
отработать раньше, чем заливка применится, и вернуть меньше шести. Три стадии
записи разобраны в [[04-qdrant#5. Параметр wait|04-qdrant.md, «Параметр wait»]].

## Шаг 4. Идемпотентность

**Прежде чем выполнить — ответьте себе:** если повторить заливку из шага 3
без единого изменения, пойнтов станет 12 или останется 6?

Повторите команду заливки, затем посчитайте снова:

```bash
qd -X POST $QDRANT_URL/collections/toy/points/count -d '{"exact": true}'
```

**По-прежнему 6, а не 12.** Это `upsert`: пойнт с существующим `id`
перезаписывается, а не добавляется.

**Ловушка:** перезаписывается пойнт **целиком**, а не по изменённым полям.
Пусть мы зальём вот это, намереваясь поправить только текст:

```json
{"id": 1, "vector": [0.9, 0.1, 0, 0], "payload": {"text": "новый"}}
```

У пойнта 1 сотрутся `doc_id`, `clause`, `topic`, `doc_type`, `date_expire`
и `amount` — всё, чего нет в новом payload. Останется один `text`.

Дальше, в шагах 5 и 12, мы будем делать с коллекцией две разные вещи —
и после такой заливки они разойдутся:

| Что делаем | Как себя поведёт |
|---|---|
| Ищем по вектору (шаг 5) | Пойнт 1 находится как ни в чём не бывало: вектор мы залили тот же |
| Фильтруем по `doc_type = перевозка` (шаг 12) | Пойнт 1 исчезает: поля больше нет, фильтровать не по чему |

Вот в этом и опасность: **половина системы работает, половина молча
теряет документ**. Ошибка сделана при загрузке, а замечена будет при поиске
с фильтром — возможно, через неделю, и искать её будут не там.

Отсюда — правило шага ниже.

Отсюда требование делать `id` детерминированным (UUID5 от `doc_id + clause`),
чтобы повторная загрузка договора заменяла свои же чанки, —
[[04-qdrant#Модель данных|04-qdrant.md, «Модель данных»]].

## Шаг 5. Первый поиск

Ищем «про ответственность» — вектор, наклонённый в первую координату,
по тому же соглашению, что и векторы пойнтов:

```bash
qd -X POST $QDRANT_URL/collections/toy/points/query -d '{"query": [0.9, 0.1, 0.0, 0.0], "limit": 3, "with_payload": true}'
```

**Вывод (дословно)** — один раз показан целиком, чтобы было видно, из чего
состоит ответ поиска. Третий пойнт отрезан, он устроен так же:

```json
{
    "result": {
        "points": [
            {
                "id": 1,
                "version": 4,
                "score": 1.0,
                "payload": {
                    "doc_id": "TR-114",
                    "clause": "4.2",
                    "topic": "ответственность",
                    "doc_type": "перевозка",
                    "date_expire": "2026-12-31T00:00:00Z",
                    "amount": 4500000,
                    "text": "За просрочку доставки Перевозчик уплачивает неустойку 0,1%"
                }
            },
            {
                "id": 2,
                "version": 3,
                "score": 0.9909924,
                "payload": {
                    "doc_id": "TR-118",
                    "clause": "6.1",
                    "topic": "ответственность",
                    "doc_type": "экспедирование",
                    "date_expire": "2026-10-15T00:00:00Z",
                    "amount": 1200000,
                    "text": "Ответственность Экспедитора ограничена суммой 500 000 рублей"
                }
            }
        ]
    },
    "status": "ok",
    "time": 0.011877042
}
```

Здесь видно всё, что возвращает поиск: `id`, `score` — мера близости,
`payload` целиком и `version` — счётчик перезаписей пойнта.

Дальше в лабе таких полотен не будет: на шести пойнтах ещё терпимо,
но при `limit: 50` на настоящих чанках это сотни строк. Определим вторую
обёртку, рядом с `qd`, не вместо неё: она шлёт тело запроса в `points/query`
коллекции `toy` и печатает по строке на найденный пойнт.

```bash
qq() { curl -s -H "api-key: $QDRANT_API_KEY" -H 'Content-Type: application/json' -X POST "$QDRANT_URL/collections/toy/points/query" -d "$1" | python3 -c 'import json,sys
for p in json.load(sys.stdin)["result"]["points"]:
    pl = p["payload"]
    print("id=%s  score=%.4f  %-16s %s" % (p["id"], p["score"], pl["topic"], pl["doc_type"]))'; }
```

**Что заметить:** вектор запроса и векторы пойнтов обязаны жить **в одном
пространстве** — одинаковой размерности для этого мало, нужен ещё и одинаковый
смысл координат. В настоящей системе это же требование звучит как
«векторизовать запрос и документы одной моделью»
([03-embeddings.md](../03-embeddings.md)). Что бывает, когда требование нарушено, —
[[#Что значит «одно пространство»|в разборе]].

## Шаг 7. Что показывает `score`

Своей команды у шага нет — смотрим на числа из шага 6.

`score` — мера близости в той метрике, что задана при создании коллекции.
У нас `Cosine`: косинус угла между вектором запроса и вектором пойнта,
больше = ближе, максимум 1.

**Чем score не является** — три ошибки, которые делают почти все:

- не вероятность и не процент: `0.75` не значит «подходит на 75%»;
- не сравним между запросами: `0.95` на один вопрос может быть хуже,
  чем `0.45` на другой;
- не сравним между моделями: смените эмбеддер — шкала поедет целиком,
  хотя качество поиска может не измениться.

Практическое следствие: отсекать выдачу фиксированным порогом («берём всё
выше 0,7») — приём хрупкий. Порог придётся подбирать под модель, а после
смены модели — заново и молча. Почему так, с замерами игрушки против
настоящей модели, — [[#Почему абсолютное значение score обманывает|в разборе]].

**И главное:** нерелевантный пойнт всё равно получает score. «Ничего не
нашлось» векторный поиск не отвечает никогда — он всегда возвращает `limit`
ближайших, даже если все мимо. В шаге 12 вы увидите это в предельном виде.
Отсекать мусор — работа реранкера
([05-retrieval-rerank.md](../05-retrieval-rerank.md)).

## Шаг 8. Проверьте сами: длина вектора не важна

Замените запрос на ровно третью ось, без хвоста:

```bash
qq '{"query": [0.0, 0.0, 1.0, 0.0], "limit": 3, "with_payload": true}'
```

Сравните с выдачей на `[0.0, 0.0, 0.9, 0.1]` из шага 6 — она продублирована
здесь, возвращаться не нужно.

**Было** — запрос `[0, 0, 0.9, 0.1]`:

```
id=5  score=1.0000  сроки            перевозка
id=6  score=0.9918  сроки            аренда_ТС
id=3  score=0.1098  оплата           перевозка
```

**Стало** — запрос `[0, 0, 1, 0]`:

```
id=5  score=0.9939  сроки            перевозка
id=6  score=0.9915  сроки            аренда_ТС
id=3  score=0.1104  оплата           перевозка
```

Порядок тот же, скоры сдвинулись на тысячные.

**Проверьте и это** — тот же вектор, растянутый в девять раз, и он же,
сжатый почти в ноль:

```bash
qq '{"query": [0.0, 0.0, 9.0, 0.0], "limit": 3, "with_payload": true}'
```

```bash
qq '{"query": [0.0, 0.0, 0.001, 0.0], "limit": 3, "with_payload": true}'
```

**Обе выдачи совпадают с предыдущей до последнего знака** (проверено
07.08.2026): те же `0.9939`, `0.9915`, `0.1104`.

**Что заметить:** косинус измеряет **угол между векторами, а не их длину**.
Растягивание вектора в 9000 раз не сдвинуло ни одного скора.

Раз длина ни на что не влияет, её у всех векторов приводят к единице —
это называется **нормированием**. Посчитаем для вектора пойнта 1:

```bash
python3 -c 'import math
v=[0.9,0.1,0,0]; n=math.sqrt(sum(x*x for x in v))
print("длина    :", round(n,10))
print("нормиров.:", [round(x/n,8) for x in v])'
```

**Вывод (дословно):**

```
длина    : 0.9055385138
нормиров.: [0.99388373, 0.11043153, 0.0, 0.0]
```

**Запомните это число.** В шаге 15 оно вернётся с другой стороны: Qdrant
отдаст вектор пойнта 1 не тем, что мы клали, а именно таким. Как считается
и зачем — [[#Как устроено нормирование|в разборе]].

## Шаг 9. Зачем нужен payload

Своей команды у шага нет, он объясняет следующие три. Вопрос пользователя
к готовой системе почти никогда не бывает чисто смысловым:

> Какая ответственность за просрочку по действующим договорам перевозки?

| Часть вопроса | Чем отрабатывается |
|---|---|
| «ответственность за просрочку» | вектор — смысл |
| «перевозки» | payload, поле `doc_type` |
| «действующим» | payload, поле `date_expire` |

На вторую и третью строки вектор ответить не может: он посчитан из текста
абзаца и не знает ни типа договора, ни даты окончания. Соблазн есть — у пойнта
6 в тексте прямо написано «Договор действует до 1 марта 2027 года», и поиск
по запросу «действующие договоры» его найдёт. Но найдёт он **абзац про срок**,
а не отберёт документы по сроку: дату, вытащенную из текста, не с чем
сравнить.

Отбор по реквизитам — работа payload. Шаги 10–11 её готовят, шаги 12–14
показывают.

## Шаг 10. Создать payload-индексы

Три команды отличаются только `field_schema`:

| Схема | Для чего | Что открывает |
|---|---|---|
| `keyword` | Строки-категории: `doc_type`, `doc_id`, ИНН | Точное совпадение `match` |
| `datetime` | Даты ISO 8601: `2026-12-31T00:00:00Z` | Диапазоны по времени |
| `float` | Числа: `amount` | Диапазоны по величине |

Каждая из трёх команд ниже **создаёт payload-индекс** на одно поле: первая
на `doc_type`, вторая на `date_expire`, третья на `amount`. Выполнить нужно
все три.

```bash
qd -X PUT $QDRANT_URL/collections/toy/index -d '{"field_name": "doc_type", "field_schema": "keyword"}'
```

```bash
qd -X PUT $QDRANT_URL/collections/toy/index -d '{"field_name": "date_expire", "field_schema": "datetime"}'
```

```bash
qd -X PUT $QDRANT_URL/collections/toy/index -d '{"field_name": "amount", "field_schema": "float"}'
```

**Выжимка** — в `result` придёт вот это (проверено 06.08.2026, своё будет
только `operation_id` и `time`):

```json
{"operation_id": 2, "status": "acknowledged"}
```

**Что заметить:** тип выбирается под то, **как поле будут спрашивать**, а не
под то, что в нём лежит. `amount` можно объявить `keyword` — данные те же, но
вопрос «дороже 2 млн» станет невозможен.

`acknowledged`, а не `completed`: команда принята, индекс строится фоном.
Сколько это стоит и как устроено — [[#Как payload-индекс устроен и где лежит|в разборе]].

## Шаг 11. Проверить индексы

Проверять будем поле `payload_schema` в описании коллекции.

**Прежде чем выполнить — ответьте себе:** полей в payload у каждого пойнта
семь (`doc_id`, `clause`, `topic`, `doc_type`, `date_expire`, `amount`,
`text`), а индексов мы создали три. Сколько строк окажется
в `payload_schema` — три или семь?

```bash
qd $QDRANT_URL/collections/toy
```

Смотреть в поле `payload_schema`. До шага 10 там было пусто — `{}`. После
трёх команд появятся три записи вида:

```json
"doc_type": {"data_type": "keyword", "points": 6}
```

**Три, а не семь.** `payload_schema` перечисляет не поля payload, а поля,
на которые создан индекс. Остальные четыре никуда не делись — они лежат
в каждом пойнте, и фильтровать по ним можно, просто перебором.

`points` — сколько пойнтов попало в индекс. Число меньше общего означает,
что у части пойнтов поля просто нет: payload произвольный, одинаковый набор
полей никто не гарантирует. На настоящем корпусе это первое место, куда
смотреть, когда фильтр возвращает подозрительно мало.

**То же самое в дашборде:** коллекция `toy` → вкладка **Info** → раздел
**Payload Indexes**. Таблица `Field` / `Type` / `Points`, на строках иконки
`Edit index` и `Delete index`, в шапке кнопка `Create Index`.

До первого созданного индекса **раздела в дашборде нет вообще** — не пустой,
а отсутствует. Через API в том же случае честно приходит `{}`.

## Шаг 12. Фильтр по одному значению

Держите под рукой — что лежит в коллекции:

| id | topic | doc_type | date_expire | amount |
|---|---|---|---|---|
| 1 | ответственность | перевозка | 2026-12-31 | 4 500 000 |
| 2 | ответственность | экспедирование | 2026-10-15 | 1 200 000 |
| 3 | оплата | перевозка | 2026-12-31 | 4 500 000 |
| 4 | оплата | аренда_ТС | 2027-03-01 | 900 000 |
| 5 | сроки | перевозка | 2026-10-15 | 1 200 000 |
| 6 | сроки | аренда_ТС | 2027-03-01 | 900 000 |

**Прежде чем выполнить — ответьте себе:** `limit` тот же, что и без фильтра,
то есть три. Подходящих под фильтр в коллекции три из шести, а близких по
смыслу среди них один. Вернётся три или один?

```bash
qq '{"query": [0.9, 0.1, 0.0, 0.0], "limit": 3, "with_payload": true, "filter": {"must": [{"key": "doc_type", "match": {"value": "перевозка"}}]}}'
```

**Было** — тот же запрос без фильтра, повтор выжимки из шага 6:

```
id=1  score=1.0000  ответственность  перевозка
id=2  score=0.9910  ответственность  экспедирование
id=4  score=0.2254  оплата           аренда_ТС
```

**Стало** — он же с фильтром `doc_type = перевозка`:

```
id=1  score=1.0000  ответственность  перевозка
id=3  score=0.1098  оплата           перевозка
id=5  score=0.0000  сроки            перевозка
```

**Ключевое, ради чего этот шаг:** вернулось три из трёх, а не «три ближайших,
из которых один прошёл фильтр». Фильтрация — не постобработка: Qdrant не ищет
сначала соседей, чтобы потом выбросить неподходящих. Пойнты 2 и 4 исчезли
совсем, на их места встали 3 и 5 — те же перевозки, но далёкие по смыслу.

Заодно посмотрите на пойнт 5: `score=0.0000`. С запросом про ответственность
общего ничего, но фильтр пройден, а лучших кандидатов не осталось. Это то
самое «поиск не отвечает „не нашлось“» из шага 7, в предельном виде.

Оговорка про механизм — [[#Про filterable HNSW — честная оговорка|в разборе]].

## Шаг 13. Диапазон и два условия

Диапазоны задаются четырьмя сокращениями: `gt` — больше, `gte` — больше или
равно, `lt` — меньше, `lte` — меньше или равно.

«Истекающие до конца 2026»:

```bash
qq '{"query": [0.0, 0.9, 0.1, 0.0], "limit": 5, "with_payload": true, "filter": {"must": [{"key": "date_expire", "range": {"lt": "2027-01-01T00:00:00Z"}}]}}'
```

**Выжимка** (`qq`, дословно):

```
id=3  score=1.0000  оплата           перевозка
id=2  score=0.2411  ответственность  экспедирование
id=5  score=0.1098  сроки            перевозка
id=1  score=0.1098  ответственность  перевозка
```

Просили `limit: 5`, вернулось четыре. **`limit` — потолок, а не обещание:**

| id | date_expire | Прошёл `lt: 2027-01-01`? |
|---|---|---|
| 1 | 2026-12-31 | да |
| 2 | 2026-10-15 | да |
| 3 | 2026-12-31 | да |
| 5 | 2026-10-15 | да |
| 4 | 2027-03-01 | нет |
| 6 | 2027-03-01 | нет |

Подходящих во всей коллекции четыре, пятого взять неоткуда.

Два условия сразу — перевозка **и** дороже 2 млн:

```bash
qq '{"query": [0.9, 0.1, 0.0, 0.0], "limit": 5, "with_payload": true, "filter": {"must": [{"key": "doc_type", "match": {"value": "перевозка"}}, {"key": "amount", "range": {"gt": 2000000}}]}}'
```

**Выжимка** (`qq`, дословно):

```
id=1  score=1.0000  ответственность  перевозка
id=3  score=0.1098  оплата           перевозка
```

Перевозок три — 1, 3 и 5, — а осталось две:

| id | doc_type | amount | Прошёл оба условия? |
|---|---|---|---|
| 1 | перевозка | 4 500 000 | да |
| 3 | перевозка | 4 500 000 | да |
| 5 | перевозка | 1 200 000 | нет — дешевле 2 млн |

Условия в `must` соединены через И: пойнту мало быть перевозкой.

## Шаг 14. Три кирпича: must, should, must_not

Из них собираются все фильтры, какими бы сложными ни были:

| Кирпич | Логика | Читается как |
|---|---|---|
| `must` | И | все условия обязаны выполниться |
| `should` | ИЛИ | достаточно любого одного |
| `must_not` | НЕ | ни одно не должно выполниться |

`should` — «экспедирование или аренда»:

```bash
qq '{"query": [0.9, 0.1, 0.0, 0.0], "limit": 5, "with_payload": true, "filter": {"should": [{"key": "doc_type", "match": {"value": "экспедирование"}}, {"key": "doc_type", "match": {"value": "аренда_ТС"}}]}}'
```

`must_not` — «всё, кроме перевозки»:

```bash
qq '{"query": [0.9, 0.1, 0.0, 0.0], "limit": 5, "with_payload": true, "filter": {"must_not": [{"key": "doc_type", "match": {"value": "перевозка"}}]}}'
```

**Выжимка** (`qq`, дословно) — **у обеих команд одинаковая**:

```
id=2  score=0.9910  ответственность  экспедирование
id=4  score=0.2254  оплата           аренда_ТС
id=6  score=0.0129  сроки            аренда_ТС
```

Совпадение не случайно — оба условия дают одно множество, разными путями:

```
should:    экспедирование {2}  ∪  аренда_ТС {4, 6}   = {2, 4, 6}
must_not:  всё {1,2,3,4,5,6}   −  перевозка {1, 3, 5} = {2, 4, 6}
```

Сходится только потому, что типов договоров ровно три: перечислили два —
значит исключили третий. На настоящем справочнике контрагентов такие два
фильтра разойдутся при первом же новом типе договора. Правило: `must_not`
описывает исключение, `should` — перечисление, и менять одно на другое можно
только там, где список значений закрыт.

Кирпичи вкладываются друг в друга: внутри `must` может лежать вложенный фильтр
со своим `should`. Так собираются условия вида «перевозка И (истекает в 2026
ИЛИ дороже 5 млн)».

## Шаг 16. Состояние коллекции

```bash
qd $QDRANT_URL/collections/toy
```

**Вторая неожиданность:** `indexed_vectors_count` равен нулю, хотя пойнтов
шесть и `status: green`. Это не поломка.

Виноват `indexing_threshold` — **порог в килобайтах**: сегменты меньше него
Qdrant не индексирует вовсе, потому что на малых объёмах полный перебор
быстрее обхода графа HNSW. По умолчанию в Qdrant 1.19.0 порог 10 000 КБ,
а шесть пойнтов весят несопоставимо меньше.

Поиск при этом работает и даже точнее обычного: перебор даёт истинно ближайших
соседей, а HNSW — приблизительных
([[04-qdrant#1. Отключить индексацию на время загрузки — главный приём|04-qdrant.md]]).

**Запомните это поле.** На настоящем корпусе нулевой `indexed_vectors_count`
означает ровно обратное: забытый `indexing_threshold=0` после массовой
загрузки, то есть линейный перебор на каждом запросе.

# Разбор

Дальше — объяснения к шагам. Выполнять ничего не нужно; читать лучше после
того, как лаба пройдена целиком.

## Почему размерность нельзя поменять

К шагу 2. Векторы разной длины несравнимы в принципе — косинус между массивом
из 4 чисел и массивом из 1024 не определён. Сменить размерность значит
объявить всё уже лежащее мусором: пришлось бы пересчитать каждый вектор
заново новой моделью, а это переиндексация корпуса с нуля. Поэтому Qdrant
такой операции просто не предлагает.

Практическое следствие: не хардкодить размерность в коде, а читать её из
ответа эмбеддера — [[08-local-stand#Что переносится на сервер партнёра, а что нет|08-local-stand.md]].
У партнёра модель почти наверняка другая, и коллекцию придётся создавать
с другим числом.

## Что значит «одно пространство»

К шагу 5. Одинаковой размерности мало — нужен ещё и одинаковый смысл
координат. В нашей игрушке смысл назначен таблицей из шага 3: первая
координата — ответственность, вторая — оплата, третья — сроки. Запрос
`[0.9, 0.1, 0, 0]` попадает в пойнт 1 только потому, что мы составили его
по той же таблице.

Возьмите ту же таблицу и переставьте темы местами:

| | 1-я координата | 2-я | 3-я |
|---|---|---|---|
| Пойнты залиты по такому соглашению | ответственность | оплата | сроки |
| Запрос составлен по такому | сроки | ответственность | оплата |

Размерность осталась 4, Qdrant не заметит ничего, ошибки не будет —
а поиск начнёт выдавать оплату на вопросы про сроки.

В настоящей системе таблицы нет, смысл координат назначает модель, и то же
требование звучит как «векторизовать запрос и документы **одной моделью**».
Две разные модели дадут одинаковую размерность 1024 и полностью
несопоставимые пространства ([03-embeddings.md](../03-embeddings.md)).

## Как устроено нормирование

К шагу 8. Каждая координата делится на длину самого вектора, а длина
считается по теореме Пифагора — только слагаемых не два, а сколько есть
координат. Для вектора пойнта 1:

```
длина = √(0,9² + 0,1² + 0² + 0²) = √0,82 = 0,9055385138

нормированный = [0,9/0,9055,  0,1/0,9055,  0,  0]
              = [0.99388373, 0.11043153, 0.0, 0.0]
```

После этого длина вектора равна ровно 1, а направление — то же самое.
Именно поэтому выдача не изменилась: косинус смотрит на направление.

Qdrant делает это сам при записи, если метрика коллекции `Cosine` — отсюда
«неожиданность» шага 15, где обратно приходит не тот вектор, что клали.
Смысл в скорости: у нормированных векторов косинус равен скалярному
произведению, то есть отпадает деление на две длины при каждом сравнении
([03-embeddings.md](../03-embeddings.md)).

## Чем игрушечные векторы отличаются от настоящих

К шагу 3. В лабе смысл координат назначен человеком. В настоящей системе
вектор считает эмбеддер:

```
игрушка:   человек придумал      → [0, 0, 0.9, 0.1]      ← 4 числа, смысл назначен
настоящее: "срок доставки груза" → [0.021, -0.14, ...]   ← 1024 числа, смысл не читается
```

В настоящей коллекции никто не знает, что означает 137-я координата — она
не «про сроки», она вообще ни про что по отдельности. Смысл размазан по всем
1024 числам сразу, и предсказать результат поиска в уме невозможно; поэтому
качество приходится **мерить** ([05-retrieval-rerank.md](../05-retrieval-rerank.md)),
а не оценивать на глаз.

Размерность 4 и ручные числа нужны ровно затем, чтобы один раз увидеть
механику целиком — и дальше понимать, что происходит внутри непрозрачной
тысячи чисел.

## Почему абсолютное значение score обманывает

К шагу 7. Лучше всего видно на контрасте игрушки и настоящей модели.

В игрушечной коллекции векторы сделаны руками и взаимно перпендикулярны —
шкала честная и полная:

| Пара | score |
|---|---|
| точное совпадение | 1,0000 |
| та же тема | 0,9910 |
| другая тема | 0,2254 |
| ничего общего | **0,0000** |

На настоящем эмбеддере ноля не бывает никогда. Замер нашего стенда
([[08-local-stand#Измерено на этой машине|08-local-stand.md]]):

| Пара | score |
|---|---|
| «неустойка 0,1% за просрочку» ↔ «пеня одна десятая процента в сутки» | 0,6755 |
| то же ↔ «санитарное состояние помещения» | **0,2097** |

Неустойка и санитария не имеют общего вообще ничего — и получают 0,21. Модель
сжимает все тексты в узкий конус пространства, и «далеко» у неё начинается
не от нуля. Поэтому вопрос «0,6 — это хорошо?» ответа не имеет.

Информативен **разрыв внутри одной выдачи**, а не абсолютные значения:

```
игрушка:  0,9910 → 0,2254   разрыв 0,77
стенд:    0,6755 → 0,2097   разрыв 0,47
```

Числа разные, вывод один: провал между соседними позициями показывает, где
кончились осмысленные результаты.

## Как payload-индекс устроен и где лежит

К шагам 10–11. Индекс — заранее построенная структура, которая позволяет
не просматривать всё подряд. Бумажный аналог — предметный указатель в конце
книги. Сам текст указатель не меняет, только скорость поиска.

**В Qdrant таких структур две, и путать их дорого:**

| | Векторный индекс (HNSW) | Payload-индекс |
|---|---|---|
| Построен по | векторам | одному полю payload |
| Ускоряет | поиск ближайших соседей | фильтрацию по этому полю |
| Сколько на коллекцию | один | по одному на каждое нужное поле |
| Чем управляется | `indexing_threshold` (шаг 16) | командой `PUT /index` (шаг 10) |

### Из чего он сделан: та же информация, вывернутая наизнанку

Payload лежит внутри каждого пойнта, в направлении «пойнт → значение»:

```
пойнт 1 → doc_type: перевозка
пойнт 2 → doc_type: экспедирование
пойнт 3 → doc_type: перевозка
пойнт 4 → doc_type: аренда_ТС
пойнт 5 → doc_type: перевозка
пойнт 6 → doc_type: аренда_ТС
```

А фильтр спрашивает в обратную сторону: «дай пойнты, у которых `doc_type` =
перевозка». Хранилище устроено от пойнта к значению, вопрос идёт от значения
к пойнтам — поэтому без индекса приходится открыть все шесть пойнтов и у
каждого посмотреть.

Payload-индекс — вторая табличка, где то же самое записано наоборот:

```
перевозка      → 1, 3, 5
экспедирование → 2
аренда_ТС      → 4, 6
```

Отсюда ответ, почему команд три, а не одна: вывернуть можно только одно поле
за раз. Табличка по `doc_type` ничего не знает про `amount`.

### Где он физически лежит

Отдельная структура рядом с данными, а не что-то дописанное в пойнты. Сами
пойнты команда `PUT /index` не меняет.

**Выжимка** (`find`, показан один сегмент из пяти; имена сегментов — UUID,
у вас будут свои):

```
~/Development/Home/RAG-stand/storage/collections/toy/
├── payload_index.json          ← список: какие поля проиндексированы
├── config.json
└── 0/segments/0d530a47-…/
    ├── vector_storage/         ← векторы
    ├── payload_storage/        ← payload всех пойнтов
    └── payload_index/          ← вот он
        ├── config.json
        └── 9vh014…-doc_type-map/   ← та самая табличка; «map» в имени не случайно
            ├── page_0.dat
            ├── bitmask.dat
            └── …
```

Индексы строятся **посегментно**, поэтому каталог `payload_index/` появляется
в каждом из пяти сегментов. Верхний файл — реестр проиндексированных полей,
**вывод (дословно)** 06.08.2026 после первой из трёх команд:

```json
{"schema":{"doc_type":"keyword"}}
```

Заглянуть внутрь самого индекса нельзя: к нему нет запроса. Структура
служебная, ею пользуется только Qdrant, когда видит `filter`. Наружу торчит
единственное окно — `payload_schema`, перечень без содержимого.

### Как он появляется и кто его поддерживает

По команде `PUT /index` Qdrant делает две разные вещи:

1. **Разово:** проходит по всем уже лежащим пойнтам, у каждого читает только
   один ключ, собирает табличку и пишет на диск.
2. **Дальше всегда:** запоминает поле в `payload_index.json`. При каждом
   `upsert` дописывает новый пойнт в табличку, при удалении вычёркивает.

Индекс не снимок: он живёт вместе с данными, обновлять руками не нужно.

Пункт 2 — механика правила «payload-индексы до массовой заливки»
([[04-qdrant#6. Payload-индексы — до загрузки|04-qdrant.md]]). До загрузки
работает только пункт 2: таблички наполняются попутно, даром. После загрузки
сначала отрабатывает пункт 1 — полный проход по корпусу. **Команда при этом
одна и та же**, и по её ответу не видно, много ли работы она повлекла.
Меняется не команда, а её цена.

В лабе порядок обратный правилу: пойнты залиты в шаге 3, индексы созданы
в шаге 10. Сделано ради простоты изложения, и на шести пойнтах стоит нуль.

### Сколько стоит построение

Замер на пустой коллекции 06.08.2026:

| Режим | `status` | `time` |
|---|---|---|
| без `wait` | `acknowledged` | 0,016 с |
| `?wait=true` | `completed` | 0,392 с |

Двадцатикратная разница — это и есть время построения индекса, которое
в первом случае уехало в фон. Отсюда правило «дождаться `green` перед
замерами»: на `yellow` вы измеряете не поиск, а конкуренцию с фоновой
перестройкой ([[04-qdrant#5. Параметр wait|04-qdrant.md, «Параметр wait»]]).

### Индекс нужен для скорости, а не для правильности

Проверено на этом стенде 06.08.2026: все фильтры шагов 12–14 отрабатывают
**верно и без единого индекса** — Qdrant честно перебирает payload всех
пойнтов подряд. На шести пойнтах перебор незаметен, на корпусе клиента это
разница между миллисекундами и секундами.

Забытый payload-индекс не сломает результат и не выдаст ошибку — он тихо
сделает поиск медленным. Тот же класс дефектов, что забытый
`indexing_threshold` в шаге 16.

### Почему `keyword`, а не `text`

`keyword` сравнивает строку целиком: `doc_type` со значением `перевозка`
найдётся по `перевозка` и не найдётся по `перев`. `text` — полнотекстовый
поиск по словам внутри значения. Для `doc_type` правилен `keyword`: это
справочное значение из короткого списка. `text` понадобится на гибридном
поиске ([05-retrieval-rerank.md](../05-retrieval-rerank.md)).

Схем в Qdrant больше трёх — есть `integer`, `bool`, `uuid`, `geo` и другие.

## Про filterable HNSW — честная оговорка

К шагу 12. На настоящем корпусе «три из трёх» обеспечивает filterable HNSW —
фильтр применяется внутри обхода графа
([[04-qdrant#Фильтрация|04-qdrant.md, «Фильтрация»]]). Но **на вашей коллекции
графа сейчас нет**: `indexed_vectors_count: 0` из шага 16, и Qdrant делает
точный перебор, проверяя условие на каждом пойнте. Результат совпадает,
причина другая.

Наблюдаемое поведение здесь не доказывает работу filterable HNSW, оно лишь
не противоречит ей. Проверить сам механизм можно только на объёме, где граф
действительно строится. Связка «сузили по реквизитам, потом искали смысл
одним запросом» — обещание, подтверждённое документацией и устройством
Qdrant, а не этим замером.

## Почему вернулся не тот вектор, который клали

К шагу 15. При метрике Cosine Qdrant нормирует векторы на входе (приводит
длину к 1), потому что у нормированных косинус равен скалярному произведению,
а оно считается быстрее. Направление сохранено, значит сохранён и косинус —
единственное, что нужно этой коллекции.

Евклидовы расстояния нормировка, наоборот, меняет; поэтому приём применяется
только к метрикам, которым важен угол, а не длина. Наш эмбеддер и так отдаёт
нормированные векторы ([03-embeddings.md](../03-embeddings.md)), так что на
реальных данных разницы не будет видно.

## Если что-то не так

| Симптом | Причина |
|---|---|
| `Expecting value: line 1 column 1 (char 0)` | Не выполнен `source .env`: `$QDRANT_URL` пуст, curl никуда не сходил, а жалуется питон на пустой вход. Сообщение про JSON почти всегда значит «запрос не дошёл до Qdrant» |
| `401 Unauthorized` | Адрес есть, а ключа нет — `$QDRANT_API_KEY` не подхватился |
| `Connection refused` | Стенд не поднят — `start-stand.sh` |
| `Wrong input: Vector dimension error` | Вектор не из 4 чисел |
| Поиск возвращает не то, что ждали | Посмотреть `scroll` — скорее всего в payload или векторе не то, что думали |
| Пойнтов вдвое больше | Не тот случай: при одинаковых `id` этого не бывает. Значит `id` разные |
