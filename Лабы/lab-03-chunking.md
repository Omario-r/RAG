## Что нужно знать до первого шага

| Термин | Рабочее определение |
| --- | --- |
| **Пункт** (`Clause`) | Смысловая единица договора: «4.2. Общая стоимость…». Узел дерева: у 3.4 дети 3.4.1–3.4.3 |
| **Чанк** (`Chunk`) | Единица индекса: один пункт или родитель вместе со своими подпунктами. В Qdrant поедет по одному пойнту на чанк |
| **Адрес** | `TR-114, п. 4.2` — то, что увидит юрист |
| **Идентификатор** | `TR-114#4.2` — то, по чему считается совпадение с золотым набором. Форму задаёт `golden-set.yaml`, не парсер |
| **`clause_ids`** | Все пункты, попавшие в чанк. Совпадение с набором считается по нему: вопрос может указывать на подпункт внутри чанка родителя |
| **`text`** | Чистый текст. Идёт в контекст модели и в цитаты |
| **`embed_text`** | Тот же текст с шапкой-адресом. Идёт **в вектор**. Это разные поля, и путать их дорого |
| **Контекстуализация** | Приписывание шапки: заголовок договора + раздел + адрес |
| **Сквозная нумерация** | Пункты идут 1…33 подряд, разделы называются «Статья N», связи между номерами нет (EKS-77) |
| **Приложение** | Часть того же документа под тем же `doc_id`: юрист ищет «по договору», а не «по файлу» |

Маркеры блоков вывода те же, что в лаб 1 и 2:

| Маркер | Что означает |
|---|---|
| **Вывод (дословно)** | Скопировано из терминала как есть |
| **Выжимка** | Показано только содержательное; команда печатает больше |
| **Схема формата** | Поля настоящие, значения выдуманы — со своими не сравнивать |

Все выводы сняты **09.08.2026** на корпусе первой партии (`RAG-stand/corpus/`, 5 документов, 172 пункта).

## Шаг 6. Три вида адреса

```bash
uv run python -c "
import sys; sys.path.insert(0,'src')
from rag_lab.chunk import parse, display
for f, d in [('corpus/TR-114-2026.md','TR-114'), ('corpus/EKS-77-2026.md','EKS-77'), ('corpus/SH-45-2026.docx','SH-45')]:
    t, cl = parse(f)
    c = [x for x in cl if x.number in ('1.2','12')][0]
    print(f'{d:7s} сквозная={c.sequential!s:5s} номер={c.number:5s} раздел={c.section_no:3s} адрес: {display(d, c)}')
"
```

**Вывод (дословно)**:

```none
TR-114  сквозная=False номер=1.2   раздел=1   адрес: TR-114, п. 1.2
EKS-77  сквозная=True  номер=12    раздел=3   адрес: EKS-77, Статья 3, п. 12
SH-45   сквозная=False номер=1.2   раздел=1   адрес: SH-45, п. 1.2
```

**Что заметить:** при сквозной нумерации в адрес добавляется статья — юристу «Статья 3, п. 12» говорит больше, чем «п. 12». На метрику это не влияет: recall считается по идентификатору `EKS-77#12`, где статьи нет.

**Адрес и идентификатор — разные вещи, и это не педантизм.** Форму идентификатора задаёт `corpus/golden-set.yaml`: по совпадению с его ссылками считается весь recall. Форму адреса выбираем мы. Разбор — [[lab-03-chunking#Почему адресацию задаёт золотой набор|Почему адресацию задаёт золотой набор]].

```bash
uv run python -c "

"
```

**Прежде чем выполнить — ответьте себе:** 47 пунктов дадут больше чанков или меньше?

**Вывод (дословно)**:

```none
пунктов: 47 -> чанков: 28
id        : AR-203#3.4
clause_ids: ['3.4', '3.4.1', '3.4.2', '3.4.3', '3.4.3.1', '3.4.3.2']
```

Почему склейка именно с родителем, а не с соседями по длине — [[lab-03-chunking#Почему склейка с родителем, а не с соседями|в разборе]].

```bash
"
```

**Вывод (дословно)**:

```none
ДОГОВОР АРЕНДЫ ТРАНСПОРТНОГО СРЕДСТВА С ЭКИПАЖЕМ № АР-203/2026
Раздел 3. АРЕНДНАЯ ПЛАТА И ПОРЯДОК РАСЧЁТОВ → AR-203, п. 3.4

3.4. В арендную плату не включены и оплачиваются Арендатором отдельно:
3.4.1. Топливо и смазочные материалы.
3.4.2. Платежи в системе «Платон» и иные дорожные сборы.
3.4.3. Штрафы за нарушения правил дорожного движения, совершённые по указанию Арендатора либо в связи с исполнением его заданий.
3.4.3.1. Штрафы, связанные с техническим состоянием транспортного средства, относятся на Арендодателя.
3.4.3.2. Штрафы за превышение допустимой массы и нагрузки на ось относятся на Арендатора, если перегруз допущен при загрузке по его заданию.
```

Две первые строки — шапка, её в исходном пункте нет. Она стоит денег (токены) и даёт вектору то, чего в тексте пункта нет: что речь про аренду транспорта, а не про поставку. Вопрос «на кого вешают штрафы за нарушения на дороге» слова «аренда» не содержит, а найти должен именно этот пункт.

**Чистый текст хранится отдельно, в поле `text`** — он идёт в контекст модели и в цитаты, там шапка не нужна и мешает проверке цитаты на вхождение ([07-extraction.md](../07-extraction.md)).

```json
{
```

## Шаг 10. Приложение — часть того же договора

```bash
ch = chunk_document('EKS-77', t, cl, doc_type='экспедирование')

"
```

**Вывод (дословно)**:

```none
ДОГОВОР ТРАНСПОРТНОЙ ЭКСПЕДИЦИИ № ЭКС-77/2026
Приложение 1 → EKS-77, п. П.2
```

```none
TR-114-DS1#2.1   исключает  TR-114#6.3
```

**Что заметить:** операции три, и они не синонимы. «Изложить в редакции» отменяет старый пункт, «исключить» убирает его, «дополнить пунктом» — не отменяет ничего, потому что такого пункта в договоре не было.

Проверка сходимости: пункты 5.5 и 3.2.5 в основном договоре отсутствуют (шаг 13 это печатает) — ровно то, чего и ждём от «добавляет». Если бы «добавляет» указывал на существующий пункт, это была бы ошибка разметки.

**Допсоглашение к договору не применяется.** Пункты ДС остаются отдельными чанками, исходный пункт не переписывается. Почему — [[lab-03-chunking#Почему допсоглашение не применяется к договору|в разборе]].

# Разбор

Читать не обязательно, чтобы пройти лабу.

## Почему чанк — это пункт, а не N символов

Резка по фиксированной длине ломает три вещи сразу, и ни одна не лечится моделью получше:

| Что ломается | Как выглядит |
|---|---|
| Пункт разрезан посередине | Половина условия в одном чанке, половина в другом; находится половина |
| Номер уехал в соседний чанк | Текст найден, адрес указывает не туда — юристу такой ответ не годится |
| Иерархия потеряна | «3.4.1. Топливо и смазочные материалы» без «3.4. В арендную плату не включены» значит противоположное |

Третья строка — не выдумка ради красоты примера. Пункт 3.4.1 сам по себе читается как «топливо входит в аренду»; смысл задаёт родитель.

## Почему склейка с родителем, а не с соседями

Первая редакция [02-chunking.md](../02-chunking.md) предписывала склеивать короткие пункты с соседями до порога в токенах. Замер корпуса 08.08.2026 это опроверг.

Медиана пункта — 39 токенов, 53 % пунктов короче 40. То есть по правилу «склеивать всё короче 40» склеилась бы половина корпуса. Но самые короткие пункты почти все оказались **родителями перечислений**:

```none
3.1. Перевозчик обязан:                     7 токенов
3.1.1. Подать под погрузку исправное…      
3.1.2. Обеспечить сохранность груза…       
```

Склейка «с соседями» приклеила бы «3.1. Перевозчик обязан:» к пункту 2.5 из предыдущего раздела и разрезала бы перечисление посередине — ровно тот дефект, против которого чанкинг и делается.

Склейка «родитель + его дети» сохраняет и смысл, и адрес. На корпусе первой партии она срабатывает 7 раз из 144.

## Почему адресацию задаёт золотой набор

Идентификатор чанка — не деталь реализации парсера. По совпадению идентификатора со ссылками `golden-set.yaml` считается recall, то есть вся метрика этапа 5. Значит форму выбирает тот, кто разметил ответы, а парсер обязан её воспроизвести.

Практически это дало три правила:

1. идентификатор — `<doc_id>#<номер пункта>`, голый номер. При сквозной
нумерации статья в идентификатор **не** входит: в наборе `EKS-77#13`, а не «Статья 3, п. 13». Статья живёт в адресе и в payload;
2. у SH-45 адрес позиционный;
3. пункты допсоглашения — отдельные чанки со своими адресами.

Если форма меняется, она меняется одновременно в парсере и в наборе. В одностороннем порядке — никогда: recall тихо обнулится.

## Почему у SH-45 адрес позиционный

Номера в файле есть — в стилях, через `numPr` (numId 5 и 6). Их можно было бы восстановить. Мы этого не делаем, и вот почему.

Нумерация в стилях **плоская**: две независимые последовательности на два уровня, а не иерархические `4.2`. Восстановленный из них номер разошёлся бы с тем, что Word показывает юристу на экране. Неверная ссылка хуже отсутствующей: отсутствие видно сразу, а расхождение обнаружится, когда юрист откроет договор и не найдёт там пункта 4.2.

Поэтому адрес позиционный — `<номер раздела>.<номер пункта в разделе>`, — и ровно в этой форме ссылки на SH-45 лежат в золотом наборе.

## Почему допсоглашение не применяется к договору

Соблазн: взять «изложить в редакции» и переписать пункт 4.2 основного договора новым текстом. Тогда в индексе лежит «что действует сейчас», и поиск отвечает правильно.

Так делать нельзя. Применённая правка стирает первоначальную редакцию, а для юриста первоначальная редакция — предмет спора: важно не только что действует сейчас, но и что действовало в марте, когда возникло разногласие.

Поэтому пункты ДС — отдельные чанки, исходный пункт помечается как изменённый. В золотом наборе это разные поля, `relevant` и `superseded`: на вопрос «какая **сейчас** предельная сумма» верен пункт ДС, а исходный числится отдельно.

Кроме того, «дополнить пунктом» вообще ничего не отменяет — применять там нечего.

## Почему оценка токенов не заменяет замер

В `chunk.py` есть `estimate_tokens` — оценка длины по символам. Она нужна, чтобы разбор договора не требовал поднятого llama.cpp: парсер должен работать сам по себе.

Оценка была объявлена консервативной — «берём худший из замеренных коэффициентов, чтобы не превысить предел молча», константа 3,4 символа на токен. Замер 09.08.2026 показал, что консервативной она не была:

| Токенизатор | симв./токен, мин | мед | max | Оценка занижала |
|---|---|---|---|---|
| `multilingual-e5-large` | 2,33 | 3,26 | 4,03 | в 91 чанке из 144 |
| `Qwen3-Embedding-0.6B` | 1,46 | 1,99 | 2,51 | **во всех 144** |

Откуда взялась ошибка. Прежние 3,4 замерены ([[08-local-stand#Плотность токенизации: лимит чанка считать в токенах]]) на окнах по 2180 символов — там плотность усредняется по длинному куску. На коротком чанке с таблицей или с номерами усреднять нечего, и плотность доходит до 2,33 у e5 и 1,46 у Qwen3.

Константа заменена на 1,4 — ниже худшей наблюдавшейся плотности у более мелкого из двух токенизаторов. Оценка теперь завышает (для e5 вдвое), и это правильная сторона ошибки: лишний раз разрезать чанк дешевле, чем молча отдать модели текст длиннее предела. Лишних разрезов на корпусе первой партии не появилось ни одного.

**Правило, которое из этого следует.** Коэффициент «символов на токен» — свойство пары «модель + тип текста», а не текста. Переносить его между моделями нельзя, и в выводе любого скрипта оценка обязана быть подписана оценкой.

## Пять дефектов, которые нашла только проверка глазами

Все пять пережили `check-parser.py` и `check-chunks.py` — обе проверки считают пункты, покрытие и длины, и ни одна не смотрит на текст, который уходит в вектор.

**1. Задвоение текста, 12 чанков из 144.**

`embed_text` собирался в два приёма: сначала «шапка + текст ведущего пункта», потом последний абзац отрезался и подставлялся текст всей группы. На пунктах с пустой строкой внутри — таблицы, цитаты допсоглашения — отрезался не тот абзац.

**Было (дословно)**, `TR-114-DS1#1.1` до правки:

```none
ДОПОЛНИТЕЛЬНОЕ СОГЛАШЕНИЕ № 1
Раздел 1. ИЗМЕНЕНИЯ УСЛОВИЙ ДОГОВОРА → TR-114-DS1, п. 1.1

1.1. Пункт 4.2 Договора изложить в следующей редакции:

1.1. Пункт 4.2 Договора изложить в следующей редакции:

> «4.2. Общая стоимость услуг по настоящему Договору не может превышать 6 200 000…»
```

**Стало (дословно)**:

```none
ДОПОЛНИТЕЛЬНОЕ СОГЛАШЕНИЕ № 1
Раздел 1. ИЗМЕНЕНИЯ УСЛОВИЙ ДОГОВОРА → TR-114-DS1, п. 1.1

1.1. Пункт 4.2 Договора изложить в следующей редакции:

> «4.2. Общая стоимость услуг по настоящему Договору не может превышать 6 200 000…»
```

Задетые чанки — как раз самые дорогие: три таблицы тарифов и все шесть изменяющих пунктов допсоглашения.

**2. Приложения без адреса, 4 чанка.**

У приложения нет раздела, а адрес печатался только вместе с разделом. Таблица тарифов ЭКС-77 уходила в вектор с одной строкой шапки — заголовком договора, без указания, что это приложение и какой в нём пункт.

**3. Склеенный чанк адресовался первым подпунктом.**

Текст начинался с «3.4. В арендную плату не включены…», а шапка обещала `п. 3.4.1`. Причина — выражение `part[min(1, len(part) - 1)]`, верное для продолжений длинной группы (там родитель только повторённый контекст) и неверное для первой части.

**4. Сквозная нумерация ломалась на первом пункте.**

У `EKS-77#1` номер пункта совпадает с номером статьи, а признак сквозной нумерации вычислялся по одному пункту: «номер не равен номеру раздела». В итоге один пункт из 33 показывался как «п. 1», а весь остальной документ — как «Статья N, п. M».

Сквозная нумерация — свойство документа, а не пункта. Признак перенесён на документ и проставляется парсером всем пунктам сразу.

**5. Горизонтальная линейка markdown в тексте пункта.**

`---` отделяет приложение от договора и потому попадала в буфер последнего пункта раздела: `EKS-77#33` уезжал в индекс со строкой `---` на конце.

**Что из этого следует для проверок.** Автоматическая проверка проверяет то, что ей велели: количество пунктов, покрытие набора, предел длины. Все пять дефектов лежали в тексте, идущем в вектор, — там, где «правильно» формализовать заранее не получилось бы. Полчаса чтения нашли их все.

## Открытые вопросы

1. **Вторичная резка слишком длинной группы не проверена на данных.**
Ветка, которая режет группу «родитель + дети» при превышении предела, на корпусе первой партии не срабатывает ни разу: самый длинный чанк — 299 токенов при пределе 512. Проверить на партии 2.
2. **Правило склейки замерено, но не оптимизировано.** Склейка «родитель +
дети» выбрана как заведомо безопасная. Даёт ли она лучший recall, чем чанк на пункт, — вопрос к этапу 8, и мерить его можно только на корпусе, который различает конфигурации ([[checks/runs#`RUN-20260808-A` — конфигурации эмбеддера|RUN-20260808-A: корпус не различает конфигурации]]).
