## Что нужно знать до первого шага

| Термин | Рабочее определение |
| --- | --- |
| **Золотой набор** | 32 вопроса, для каждого заранее указаны верные пункты. Лежит в `corpus/golden-set.yaml` |
| **`relevant`** | Верные пункты вопроса |
| **`superseded`** | Пункт, отменённый допсоглашением. В верные **не** входит: на вопрос «какая сейчас сумма» он и должен быть промахом |
| **recall@k** | Какая **доля** верных пунктов попала в top-k. Три верных, нашёлся один → 0,33 |
| **hit@k** | Нашёлся ли **хоть один** верный. Тот же случай → 1,0 |
| **MRR** | Средняя обратная позиция первого верного. Первое место → 1,0, третье → 0,33 |
| **nDCG@5** | Порядок и число верных вместе. Единица — все верные стоят первыми |
| **Случайная выдача** | Точка отсчёта: те же метрики на случайно перемешанном корпусе |

**Двум разным вещам досталось одно слово «recall»**, и это не педантизм:
справочник определяет recall@50 как «доля вопросов, где нужный чанк попал
в кандидаты» — это `hit@50`. Замер 08.08.2026 считал долю найденных пунктов.
Цифры несравнимы. Поэтому печатаются обе.

Маркеры блоков вывода:

| Маркер | Что означает |
|---|---|
| **Вывод (дословно)** | Скопировано из терминала как есть |
| **Выжимка** | Показано только содержательное; команда печатает больше |

import sys, time, statistics; sys.path.insert(0,'src')
from rag_lab import store

    t0=time.perf_counter(); v=e.embed_one(q, kind='query', use_cache=False); emb_t.append(time.perf_counter()-t0)

## Шаг 9. Убедиться, что потолок настоящий

Утверждение «метрики упёрлись в потолок» стоит проверить, а не принять
на слово.

```bash
uv run python -c "
import sys; sys.path.insert(0,'src')
from rag_lab.corpus import build_chunks, golden_set, chunk_by_clause
ch = build_chunks(); by = chunk_by_clause(ch)
qs = golden_set()
print('чанков:', len(ch), '  вопросов:', len(qs))
print('верных чанков на вопрос: мин', min(len({by[r] for r in q[\"relevant\"]}) for q in qs),
      ' max', max(len({by[r] for r in q[\"relevant\"]}) for q in qs))
print('доля корпуса в top-50: {:.0%}'.format(50/len(ch)))
print('доля корпуса в top-5 : {:.0%}'.format(5/len(ch)))
"
```

**Вывод (дословно)**:

```none
чанков: 144   вопросов: 32
верных чанков на вопрос: мин 1  max 4
доля корпуса в top-50: 35%
доля корпуса в top-5 : 3%
```

**top-50 — это треть корпуса.** Метрика, которая берёт треть базы
в кандидаты, измеряет размер базы, а не качество поиска. На корпусе
из ~1500 чанков (партия 2) те же 50 кандидатов будут 3 % — вот тогда
recall@50 начнёт что-то значить.

`top-5` в 3 % уже осмысленно, поэтому `recall@1` = 0,404 и `nDCG@5` = 0,750
— единственные цифры этой лабы, у которых есть запас на улучшение.

# Разбор

## Почему это не базовая линия

Три независимых признака, каждого достаточно:

1. **Потолок.** `hit@5` = `hit@50` = 1,000. Метрика на потолке не может
   показать улучшение — только ухудшение, да и то не всякое.
2. **Случайная выдача берёт половину.** `hit@50` = 0,469 без всякого
   поиска. Если случайность решает половину задачи, задача слишком лёгкая.
3. **Замер 08.08.2026.** Пять разных конфигураций эмбеддера — другая
   модель, другой пулинг, другие префиксы — дали одинаковый ответ
   в 21–26 вопросах из 27
   ([[08-local-stand#Корпус первой партии не различает конфигурации]]).
   Корпус не различает того, что влияет на **состав** кандидатов: в top-50
   влезает треть базы, и верный ответ попадает туда при любой модели.

> [!warning] Здесь была ошибка, и её стоит увидеть до лаб 6
> Первая редакция этого списка продолжала третий пункт словами «корпус,
> не различающий столь разные сборки, не различит и реранкер». Это оказалось
> неверным: реранкер он различает — девять вопросов из 32 меняют состав
> пятёрки, а верных ответов на первом месте становится 27 вместо 22.
>
> Причина в том, что признаки 1–3 говорят о метриках **состава** (`hit@k`,
> `recall@50`), а реранкер работает с метриками **порядка** (`recall@1`,
> `MRR`, `nDCG@5`), у которых запас есть. Переносить вывод с одних на другие
> нельзя — разбор в [[lab-06-rerank#Почему корпус различает реранкер, но не различает эмбеддер|лаб 6]].
>
> На сам вывод «это не базовая линия» ошибка не влияет: первых двух признаков
> достаточно.

Отсюда решение волта: партия 2 переведена из «желательно» в блокер этапа 5.

## Что всё-таки даёт этот прогон

Не базовую линию, но три полезные вещи:

| Что | Ценность |
|---|---|
| Работающая механика | На партии 2 запускается той же командой, без переписывания |
| Найденный дефект разбора | Допсоглашение не находилось вопросом про договор — это баг, а не шум |
| Задержка по этапам | 28 мс эмбеддер + 8 мс Qdrant. Не зависит от размера корпуса так сильно, как метрики |

## Почему `superseded` не считается верным ответом

В золотом наборе есть вопросы с двумя списками:

```yaml
- q: "какая сейчас предельная сумма по перевозке для Ромашки"
  relevant: ["TR-114-DS1#1.1"]
  superseded: ["TR-114#4.2"]
```

`TR-114#4.2` — пункт с суммой 4 500 000, которую допсоглашение заменило
на 6 200 000. Он в корпусе есть, он про предельную сумму, и векторный
поиск находит его охотно. Но на вопрос со словом «сейчас» это **неверный
ответ**, и метрика обязана считать его промахом.

Есть и обратный случай:

```yaml
- q: "как быстро нужно расплатиться по выставленному счёту"
  relevant: ["TR-114#4.3", "EKS-77#19", "SH-45#3.5", "TR-114-DS1#1.2"]
  superseded: ["TR-114#4.3"]
```

Здесь `TR-114#4.3` числится и верным, и отменённым: вопрос без слова
«сейчас», и показать обе редакции — правильное поведение.

Различать эти два случая автоматически поиск не умеет и не должен.
Это работа слоя над ним — истории значений из
[07-extraction.md](../07-extraction.md).

## Почему метрика считается по чанкам, а не по пунктам

Ссылка золотого набора указывает на **пункт** (`AR-203#3.4.3.1`), а поиск
возвращает **чанк** (`AR-203#3.4`, внутри которого этот подпункт лежит).
Считать напрямую по ссылкам — значит записать в промахи каждую склейку
родителя с подпунктами и занизить recall из-за чанкинга, а не из-за поиска.

Поэтому ссылки переводятся в идентификаторы чанков через `chunk_by_clause`,
и совпадение считается уже по ним. Обратная сторона: **чем крупнее чанки,
тем легче метрике** — предельный случай «весь договор одним чанком» даёт
recall 1,0 и полную бесполезность для юриста.

Значит, размер чанка нельзя подбирать по recall в одиночку. Нужна вторая
метрика — сколько текста человек прочитает, чтобы найти ответ. На этапе 8.

## Почему средних недостаточно

Правило из [[lab-style#Правило 10. Санитарная проверка не заменяет метрику|правила 10]]
здесь работает в полную силу: прежде чем сравнивать средние, считать,
**сколько вопросов вообще изменили ответ**.

На 32 вопросах один изменившийся вопрос сдвигает recall@5 на 0,03 —
столько же, сколько «улучшение» от смены модели в замере 08.08.2026.
Отличить одно от другого по среднему невозможно; по счётчику
изменившихся вопросов — тривиально.

Поэтому `evaluate.py` печатает разбор по вопросам раньше сводки,
а не после.

## Открытые вопросы

1. **Базовая линия не поставлена** — блокер этапа, партия 2 корпуса.
2. **Метрика «сколько текста прочитает человек» не заведена.** Без неё
   recall можно улучшать укрупнением чанков, что для юриста ухудшение.
3. **Гибридный поиск не проверялся.** Вопрос «до какого числа действует
   перевозка с Ромашкой» — кандидат: там важно точное совпадение имени,
   а не смысл. Этап 8.
4. **Порог отсечения по score не изучен.** Сейчас всегда возвращается
   ровно 50 кандидатов, даже когда верного нет вовсе. Для продукта нужен
   ответ «не найдено».
5. **Разброс между прогонами не измерен.** Кэш векторов делает прогоны
   детерминированными, но при смене модели или пулинга это перестанет
   быть так.
