# Контекст и вводные

Дата: 28.07.2026.

## Что изменилось в бизнес-картине

Исходная ставка бизнес-волта — малые юрфирмы на 2–10 юристов (см.
`Business/legal-ai/01-pains-solutions.md`). Новая вводная: **закрытый контур
требуется и крупным компаниям — для отслеживания договоров**.

Почему это важно, а не просто «ещё один сегмент»:

- Крупный клиент даёт чек на порядок выше и оправдывает продажу руками;
  проблема «15–25 мелких подписок» из бизнес-плана частично снимается.
- У крупных уже есть серверы и GPU — исчезает главный технический тормоз
  малого сегмента («у юрфирмы нет железа», риск №2 в `Business/02-directions.md`).
- Задача другая: не «проверь мне этот договор», а «найди по портфелю из тысяч
  договоров всё, что попадает под условие» — то есть **поиск по корпусу**,
  а не разбор одного файла. Отсюда и техническая задача ниже.
- Цена входа выше: ИБ-требования, интеграции, приёмка. Ров тот же —
  данные не покидают периметр.

Бизнес-выводы (сегменты, чеки, каналы) в этом волте не разбираем — они
относятся к `Business`. Здесь только технология.

## Задача от партнёра (вводная, дословно по смыслу)

> Взять некоторый объём документов, разбить на чанки, загрузить в БД и делать
> семантический поиск. Этому нужно научиться.
>
> 1. Разбить исходный документ на чанки.
> 2. Векторизовать чанки.
> 3. Загрузить вектора и данные в Qdrant.
>
> В шаге 2 есть зависимость: чтобы получить вектора, нужна ИИ-модель для
> векторизации. Для этого есть отдельный VPS, там крутится сервер llama.cpp
> с моделью для векторизации. Скрипт обращается туда, получает по API вектора,
> дальше шаг 3.
>
> В отличие от реляционных БД, загрузка на шаге 3 сильно дольше поиска. Вообще
> в векторных БД insert — тяжёлая операция. Развёрнутый Qdrant использует
> оптимизации на GPU, но всё равно операция тяжеленькая. В Qdrant есть пакетная
> загрузка, и там есть какая-то особенность в части как загружать быстро —
> толи пакетом, толи ещё что-то. Скорее всего, столкнёшься.
>
> Первый шаг: научиться работать с Qdrant.
>
> Дальше нагенерим пачку хороших логистических договоров — это тестовые данные.
> И пойдём путём:
> 1. Научим агента извлекать формальные данные из договоров в SQL-БД.
> 2. Научим агента формировать поинты для векторной БД и загружать договор в Qdrant.
> 3. Исследуем реранкер — второй эшелон семантического поиска: поиск по векторной
>    БД даёт набор кандидатов, близких по косинусному расстоянию, нужно сузить
>    этот набор — более умный предварительный отсев. И только результат всего
>    этого отдаём в контекст главной модели консультанта для юристов.
>
> Сейчас просто тыкаем Qdrant. На дев-сервере десяток договоров нагенерил.
> Надо их правильно разбить на чанки, запихать в коллекцию Qdrant, попробовать
> делать поиск по запросам. Затем добавлять к постобработке реранкер.

### Что в этой вводной уже является архитектурным решением

Партнёр описал не «поиск», а **трёхуровневую архитектуру**, и это стоит
проговорить явно, потому что дальше всё строится на ней:

| Уровень | Что хранит | Чем отвечает на вопрос |
|---|---|---|
| SQL-БД | Формальные реквизиты: стороны, номер, дата, сумма, срок, тип | «Все договоры с ООО «Ромашка» дороже 5 млн, истекающие в Q4» — точный ответ, без ИИ |
| Qdrant | Чанки текста + вектора + метаданные | «Где у нас условия о простое транспорта под погрузкой?» — смысловой ответ |
| Реранкер + LLM | — | Сужение кандидатов и формулировка ответа юристу |

Ключевое: **не пытаться решать векторным поиском то, что решает SQL**. Вопрос
«сколько договоров истекает в декабре» векторный поиск решает плохо и
недостоверно, а `WHERE` — точно. Разделение зон ответственности — половина
качества будущей системы. Подробнее в [01-pipeline.md](01-pipeline.md).

Второе ключевое: «загружаем договор в Qdrant» — это не «загружаем файл».
Единица хранения — **пойнт**: id + вектор + payload (метаданные и текст чанка).
Один договор = десятки пойнтов.

## Инфраструктура (со слов партнёра, детали уточняются)

| Компонент | Что известно | Что нужно уточнить |
|---|---|---|
| Qdrant | Развёрнут у партнёра, с GPU-оптимизациями | Версия, адрес, порт, API-ключ, есть ли уже коллекции, сколько VRAM/RAM |
| llama.cpp | Отдельный VPS, модель для векторизации, доступ по API | Какая модель, эндпоинт, размерность вектора, pooling, нормализация, нужны ли префиксы, лимит токенов |
| Тестовые данные | ~10 сгенерированных логистических договоров на дев-сервере | Формат (docx/pdf/md/txt), как забрать |
| Реранкер | Не упомянут | Поднимать отдельно или вторым процессом llama.cpp |

## Разделение работ

- **Партнёр**: железо, Qdrant, llama.cpp-сервер, модели, генерация тестовых
  договоров.
- **Мы**: пайплайн — чанкинг, обращение к API векторизации, загрузка в Qdrant,
  поиск, реранкер, замеры качества.

## Принцип этого волта

Тот же, что в реестре страхов бизнес-волта: **проверяемое важнее красивого**.
Каждое утверждение о производительности или качестве здесь либо помечено
источником, либо помечено «проверить на стенде». Цифры, полученные из статей,
не считаются результатом до замера на нашем корпусе.
