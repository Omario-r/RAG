# Локальный стенд на MacBook Air M4 (24 ГБ)

Дата разворачивания: 06.08.2026. **Статус: развёрнут и проверен.**
Машина: Apple M4, 24 ГБ, macOS 26.5.1, arm64.

Стенд живёт в `~/Development/Home/RAG-stand/` — намеренно вне git-репозитория
волта (модели на 1,2 ГБ, ключи и будущий корпус договоров в коммит попасть не
должны). Волт — документация, стенд — рабочая среда.

Всё, что ниже, проверено на этой машине. Цифры в разделе «Измерено» — наши
собственные замеры, а не оценки из статей.

## Зачем

Три причины, в порядке важности:

1. **Снимает блокировку.** Этап 0 в [06-roadmap.md](06-roadmap.md) (доступы
   к Qdrant и VPS партнёра) стопорит всё. Локальный стенд позволяет пройти
   этапы 1–6 самостоятельно и переключиться на инфраструктуру партнёра
   сменой адресов в конфиге.
2. **Дешевле экспериментировать.** Пересоздать коллекцию, снести всё и начать
   заново, попробовать другую модель — на своей машине это минуты и ничьё
   разрешение.
3. **Репетиция форм-фактора для клиента.** Вариант «Mac mini M4» из
   `Business/legal-ai/02-tech.md` перестаёт быть теорией: цифры, полученные
   здесь, переносятся на mini с поправкой в лучшую сторону (у mini активное
   охлаждение).

## Решение: без Docker и без прав администратора

**Изначальный план этого документа был Colima + Docker. Он отменён.**

Qdrant публикует официальные нативные бинарники, в том числе под
`aarch64-apple-darwin`. Это убирает из схемы целый слой: не нужен ни Docker,
ни виртуальная машина, ни повышенные права.

| | Colima + Docker | Нативный бинарник |
|---|---|---|
| Права администратора | Не нужны для Colima (нужны для Docker Desktop) | Не нужны |
| Слой виртуализации | VM на 4 CPU / 6 ГБ | Нет |
| Установка | 2 пакета + образ | Скачать 26 МБ, распаковать |
| Веб-дашборд | В комплекте | **Ставится отдельно** (см. ниже) |
| Останов/запуск | Через docker | Обычный процесс |

Единственная потеря — статика веб-интерфейса: в tar-архиве лежит только сам
бинарник, и `/dashboard` отдавал 404. Чинится за одну команду: дистрибутив
дашборда выложен отдельным релизом `qdrant/qdrant-web-ui`, распаковывается
в папку и указывается параметром `service.static_content_dir`.

**Это же снимает блокер у партнёра.** Он не поставил Qdrant докером, потому
что требовались расширенные права. В том же релизе есть
`qdrant-x86_64-unknown-linux-musl.tar.gz` (статическая сборка, не зависит от
системных библиотек) и AppImage — оба запускаются от обычного пользователя,
без root и без Docker. Проверено нами только на macOS; для линукса это
ожидаемо, но помечаем **проверить**.

Воспроизводимая последовательность. Занимает около получаса, из них 25 минут —

```bash

```


Стенд — **отдельный репозиторий**, а не часть волта: см.
[[#Стенд под собственным гитом|ниже]].

### 3. Qdrant

```bash
curl -sL -o /tmp/qdrant.tar.gz https://github.com/qdrant/qdrant/releases/download/v1.19.0/qdrant-aarch64-apple-darwin.tar.gz
```

```bash
shasum -a 256 /tmp/qdrant.tar.gz
```

Бинарник подписан ad-hoc (linker-signed), Gatekeeper его пропускает; карантина

### 4. Веб-дашборд

```bash
curl -sL -o /tmp/qdrant-ui.zip https://github.com/qdrant/qdrant-web-ui/releases/download/v0.2.16/dist-qdrant.zip
```

Сумма: `4446f0cea024078011c78cd24a592c9b563656d15205818563fa6b22d394dd29`

```bash
unzip -q /tmp/qdrant-ui.zip -d /tmp/qdrant-ui && mv /tmp/qdrant-ui/dist ~/Development/Home/RAG-stand/static
```

### 5. Конфигурация и ключи

Файл `.env` в папке стенда, права 600, ключи случайные:

```bash
cd ~/Development/Home/RAG-stand && umask 077 && printf 'QDRANT_URL=http://127.0.0.1:6333\nEMBEDDER_URL=http://127.0.0.1:8080\nRERANKER_URL=http://127.0.0.1:8081\nQDRANT_API_KEY=%s\nLLAMA_API_KEY=%s\n' "$(openssl rand -hex 24)" "$(openssl rand -hex 24)" > .env
```

`.env` — единственное место с адресами. Переезд на инфраструктуру партнёра =
правка этого файла, а не кода.

### 6. Скрипты запуска

В папке стенда лежат `run-qdrant.sh`, `run-embedder.sh`, `run-reranker.sh`
и обёртки `start-stand.sh` / `stop-stand.sh` / `check-stand.sh`. Вся
конфигурация — внутри них, с комментариями «почему именно так». Ключевые
параметры разобраны ниже.

```bash
cd ~/Development/Home/RAG-stand && ./start-stand.sh && ./check-stand.sh
```

Первый запуск скачает обе модели (1,2 ГБ) — это долгая часть. Дальше `-hf`
берёт их из кэша в `models/`.

## Безопасность стенда

Раздел не формальный: привычки формируются на тестовых данных, а применяться
будут к договорам клиента. Здесь — то же, что в реестре страхов
`Business/03-fears.md`: свойство конструкции, а не обещание аккуратности.

### 1. Слушаем только петлю

**Дефолт Qdrant — `0.0.0.0`**, то есть база видна всей локальной сети без
пароля. На ноутбуке в коворкинге или кафе это означает открытую БД для соседей.
В `run-qdrant.sh` явно задано `QDRANT__SERVICE__HOST=127.0.0.1`; llama-server
запускается с `--host 127.0.0.1`.

Проверяется не доверием, а замером — `check-stand.sh` стучится на стенд
с собственного адреса в локальной сети и убеждается, что ответа нет.

### 2. Ключи даже на localhost

Привязка к петле защищает от сети, но **не от браузера**. llama-server сам
предупреждает при старте: CORS открыт для всех источников (`*`) и ключа нет —
значит любая открытая вкладка может слать запросы на `127.0.0.1:8080`,
использовать модель и читать ответы. Для Qdrant то же самое, только там цена
выше: сторонняя страница может удалить коллекцию.

Поэтому:

- оба llama-server запускаются с `--api-key` и `--cors-origins localhost`;
- Qdrant — с `QDRANT__SERVICE__API_KEY`;
- ключи случайные, лежат в `.env` с правами 600.

Проверено: без ключа обе службы отдают **401**.

### 3. Телеметрия выключена

Qdrant по умолчанию отправляет анонимную статистику наружу
(`QDRANT__TELEMETRY_DISABLED=true` в скрипте запуска). Для продукта, чьё
единственное обещание — «данные не покидают контур», исходящие соединения
по умолчанию неприемлемы. На тестовых данных это безобидно; смысл в том,
чтобы такой конфигурации не было в привычке.

### 4. Что проверено, а что нет

Проверено: привязка к петле, отказ без ключа, недоступность из локальной сети,
отсутствие карантина и корректность подписи бинарника, контрольные суммы
загрузок.

Не проверено и остаётся на доверии: содержимое GGUF-моделей и бинарника Qdrant.
Мы полагаемся на репутацию репозиториев (официальный Qwen, официальный Qdrant)
и на контрольные суммы — но контрольная сумма подтверждает, что файл не
изменился по дороге, а не что он безвреден.

## Проверка стенда — до всякого кода

`./check-stand.sh` выполняет четыре проверки. Пять минут, экономят часы отладки.

| # | Проверка | Что ловит |
|---|---|---|
| 1 | Сервисы отвечают | Не поднялось / порт занят |
| 2 | Без ключа — 401, из сети — недоступен | Ошибку конфигурации безопасности |
| 3 | Размерность + косинус на трёх текстах | Неверный pooling, забытые префиксы, неподходящую модель |
| 4 | Реранкер различает документы | Битую конвертацию GGUF |
| 5 | `/props` + тексты растущей длины | Расхождение скрипта запуска с реальностью; недостаточный контекст |

Третья проверка устроена так: два текста про одно и то же **разными словами**
(«неустойка 0,1% за просрочку доставки» и «пеня одна десятая процента в сутки
за задержку») и один про другое (санитарное состояние помещения). Разные слова
принципиальны — на одинаковых проверка выродилась бы в сравнение подстрок.

### Батчинг ничего не ускоряет

Замер 07.08.2026. Материал — 100 реальных пунктов из `corpus/TR-114-2026.md`,
по ~140 символов (≈50 токенов) каждый.

Проверялись все комбинации сразу, включая **второй экземпляр эмбеддера
на четырёх слотах**, поднятый на порту 8082 специально ради замера:

| Способ | 1 слот (8080) | 4 слота (8082) |
|---|---|---|
| По одному, 100 запросов | 4,17 с | 3,92 с |
| Один поток, пачками по 16 | 3,57 с | 3,95 с |
| Один поток, пачками по 64 | 3,68 с | 3,73 с |
| Четыре потока, по одному | 3,70 с | 3,68 с |
| Четыре потока, пачками по 16 | 3,53 с | 3,71 с |

**Разброс 3,53–4,17 с — то есть шум.** Ни батчинг, ни число слотов, ни
параллельные потоки не дают ничего: ≈40 мс на текст в любой комбинации.

Два следствия:

1. **Утверждение волта «батчинг — главный рычаг скорости» опровергнуто**
   ([03](03-embeddings.md)). Оно пришло из статей, а не из замера.
2. **Решение `--parallel 1` подтверждено.** Экономия KV-кэша принята 06.08
   как размен «память против параллелизма» — оказалось, что менять не на что:
   параллелизм здесь ничего не даёт, экономия чистая.

Ограничение замера, которое нельзя опускать в отчёте партнёру: снято на Metal,
модель 0,6B, короткие тексты. На дискретной GPU с моделью покрупнее вывод
может быть иным — там счёт дешевле относительно накладных расходов. Проверять
заново на их железе.

### Один текст — два вектора

Замер 07.08.2026, разбор — [[03-embeddings#Один текст — два вектора. Замер 07.08.2026|03-embeddings.md]].

Один и тот же текст даёт **два разных вектора** в зависимости от того, держит
ли сервер его в кэше промптов. Оба варианта стабильны и воспроизводимы;
косинус между ними 0,99999929.

Практически: пайплайн нельзя проверять сравнением векторов на равенство,
а кэш по хэшу текста получает второе обоснование — воспроизводимость замеров,
а не только скорость.

## Грабли, на которые уже наступили

Стоит того, чтобы быть записанным: дефект был тихим и обнаружился случайно.

### Оборванная команда в скрипте запуска

В `run-embedder.sh` после строки с обратным слешем оказалась **пустая строка**.
Для bash это конец команды: всё, что шло дальше (`-c 2048`, `--ubatch-size 2048`),
в llama-server не попало. Скрипт при этом отрабатывал без ошибок, сервер
поднимался, проверки стенда проходили.

Что было на самом деле против того, что думали:

| | Реально | Думали |
|---|---|---|
| `n_ctx_slot` | 32768 | 2048 |
| Слотов | 4 | 1 |
| `n_ubatch` | 512 (дефолт) | 2048 |
| Память эмбеддера | 4,2 ГБ | ~1 ГБ |

Найдено чтением лога: `embeddings enabled with n_batch (2048) > n_ubatch (512)`.
Проверки стенда этого не ловили — тестовые тексты были короткие.

### Вторая ошибка: неверный диагноз

Первое объяснение последствий было таким: «`n_ubatch=512` ограничивает длину
текста 512 токенами, значит контекстуализированные чанки не влезали бы».
**Это оказалось неверно** — и опровергнуто прямым замером, а не рассуждением.

С дефолтным `n_ubatch=512` текст в **30 000 токенов** обрабатывается штатно.
Предел задаёт `-c`, а не `--ubatch-size`; разбор — в
[03-embeddings.md](03-embeddings.md).

Отсюда неприятное: единственным реальным последствием оборванной команды был
перерасход памяти (4 слота × 32768), а «исправление» с `-c 2048` **сократило**
предельную длину текста с 32768 до 2048 — то есть чинило одно и ломало другое.
Итоговая конфигурация выбрана по замеру: `-c 8192`, один слот.

### Как это ловится теперь

`check-stand.sh` получил пятую проверку: читает `/props` и шлёт тексты растущей
длины, пока не придёт ошибка. Показывает **фактический** предел, а не
объявленный. На текущей конфигурации: 4502 токена проходят, 8252 отвергаются.

**Выводы, применимые и к серверу партнёра:**

1. Конфигурацию проверять по **логу сервера и `/props`**, а не по скрипту
   запуска. Написанное и применённое — разные вещи.
2. Проверять поведением, а не рассуждением о параметрах. Оба раза ошибка была
   в выводе из документации, а не в наблюдении.
3. `--parallel`: дефолтные 4 слота множат KV-кэш вчетверо без пользы для
   пакетной векторизации.

Диск: 1,3 ГБ всего, из них 1,2 ГБ — модели.

### Чего пока не замерено

Время векторизации корпуса, время загрузки в Qdrant, latency поиска и реранка.
Их считаем на этапах 2–6, когда появятся договоры.

## Ключевые параметры и почему они такие

| Параметр | Значение | Почему |
|---|---|---|
| `-c` (эмбеддер) | 8192 | Задаёт предельную длину **одного текста**. Выбрано по замеру: покрывает родительские разделы small-to-big, стоит ~670 МБ против 2048 |
| `--parallel` (эмбеддер) | 1 | Дефолтные 4 слота множат KV-кэш вчетверо без пользы для пакетной векторизации |
| `--ubatch-size` | не задаём | Вопреки распространённому утверждению, длину текста не ограничивает — проверено ([03](03-embeddings.md)) |
| `--pooling rank` + `--reranking` + `--embedding` | все три | Обязательны для реранкера, иначе эндпоинт `/v1/rerank` не работает |
| `QDRANT__SERVICE__HOST` | 127.0.0.1 | Дефолт `0.0.0.0` открыл бы базу в сеть |
| `LLAMA_CACHE` | `models/` в папке стенда | Иначе модели уедут в `~/Library` и потеряются из виду |

Эмбеддер и реранкер — **два отдельных процесса**: в одном llama-server они
не совмещаются.

## Что переносится на сервер партнёра, а что нет

Главная таблица документа. Локальный стенд — не копия боевой среды, и путать
их дорого.

| Переносится без изменений | Не переносится |
|---|---|
| Код: чанкер, загрузчик, поиск, реранк | **Размерность вектора** — у модели партнёра почти наверняка другая → коллекцию пересоздавать |
| Схема payload и структура пойнтов | Абсолютные значения метрик качества (recall, nDCG) — модель другая, цифры другие |
| Золотой набор вопросов и методика замеров | Время загрузки и индексации — другое железо, у партнёра GPU-индексация |
| Логика чанкинга и контекстуализации | Префиксы и pooling — зависят от конкретной модели |
| Схема SQL и логика извлечения | Наши 1024 — у Qwen3-Embedding-0.6B; у партнёра может быть 1536 или 4096 |
| Требования безопасности (петля, ключи, телеметрия) | |

Практический вывод: **обращение к эмбеддеру должно быть за одной функцией**,
адреса и имена моделей — в `.env`, размерность — читаться из ответа API,
а не быть константой в коде. Тогда переезд на VPS партнёра — это правка `.env`,
а не переписывание.

Второй вывод: локальные метрики — это **методика**, а не результат. Они
доказывают, что пайплайн работает и что измерения воспроизводимы; финальные
цифры считаются на модели партнёра.

## Ограничения Air, о которых стоит помнить

**Пассивное охлаждение.** Air без вентилятора: интерактивные запросы (поиск +
реранк) — секунды, троттлинга не будет. Многочасовые пакетные прогоны
(векторизация большого корпуса, извлечение реквизитов по сотням договоров)
приведут к снижению частот. На корпусе из 10 договоров неактуально; помнить
при планировании больших прогонов.

**Наши задачи упираются в prefill, а не в генерацию.** Реранкинг 50 пар,
извлечение полей из страниц договора, эмбеддинги — это «прочитать много,
написать мало». Обработка промпта — вычислительная задача, где Apple Silicon
слабее NVIDIA сопоставимой цены. Генерация упирается в пропускную способность
памяти, у базового M4 она скромная.

**Qdrant на Mac работает только на CPU.** GPU-индексация у него реализована
через Vulkan (NVIDIA/AMD/Intel), Metal не поддерживается. На нашем корпусе
разницы нет — индексация сотен чанков занимает секунды. Разойдётся с сервером
партнёра только на десятках тысяч документов, и это ожидаемо.

**Нюанс unified memory.** GPU по умолчанию не может занять все 24 ГБ — потолок
около двух третей. Поднимается системной настройкой (`iogpu.wired_limit_mb`),
но за счёт ОС; для стенда разработки не нужно.

## Гигиена данных

Тестовые договоры сгенерированы, ничего страшного в них нет. Но привычки
формируются на них, а применяться будут к документам клиентов.

1. **Рабочая папка вне синхронизации с iCloud.** Проверено на этой машине:
   `Desktop` и `Documents` **синхронизируются** в iCloud Drive. Для проекта,
   чьё главное обещание — «данные не покидают контур», документы клиента,
   уезжающие в облако Apple, — это провал обещания в буквальном смысле.
   Стенд поэтому в `~/Development`, который не синхронизируется.
2. **Документы клиентов и модели не коммитить.** Стенд вынесен за пределы
   репозитория волта — в волте `.gitignore` дополнительно закрывает `data/`,
   `corpus/` и `.env`. С 07.08.2026 у стенда собственный репозиторий, и правила
   для него — в разделе [[#Стенд под собственным гитом|«Стенд под собственным
   гитом»]].
3. **Никаких облачных API «для сравнения качества».** Соблазн «прогоню тот же
   вопрос в облачной модели, посмотрю разницу» на тестовых данных безобиден,
   на клиентских — то самое нарушение, ради предотвращения которого продукт
   и существует. Разделять эти режимы привычкой, а не силой воли.

## Стенд под собственным гитом

С 07.08.2026. Раньше стенд не версионировался вообще: `uv init` завёл
репозиторий, но коммитов в нём не было ни одного. Повод закрыть это — этап 2,
на котором появляется первый настоящий код пайплайна.

**Два репозитория, а не один.** Волт — документация, стенд — исполняемое.
Разный ритм изменений, и главное: физическая невозможность утащить модель
на 1,2 ГБ или документ клиента в репозиторий с текстами.

**Критерий, что версионировать:** нельзя восстановить командой.

| Под гитом | Мимо гита | Чем восстанавливается |
|---|---|---|
| шесть скриптов запуска | `.env` | `.env.example` + `openssl rand -hex 24` |
| `check-corpus.py`, `make_docx_contract.py` | `models/` (1,2 ГБ) | llama.cpp качает по `-hf` |
| `corpus/` и `golden-set.yaml` | `bin/`, `static/` (86 МБ) | разделы 3 и 4 выше |
| `src/rag_lab/` | `storage/`, `snapshots/`, `logs/` | пересоздаётся |
| `pyproject.toml`, `uv.lock` | | |

Итог первого коммита — 22 файла, 236 КБ из 1,3 ГБ содержимого папки.

**Корпус под гитом — с жёсткой оговоркой.** `golden-set.yaml` на 32 вопроса
и пять договоров с ловушками — ручная работа, которую обиднее всего потерять,
и без них не воспроизвести ни один замер. Но это создаёт привычку «договоры
лежат в гите», а через месяц придут настоящие. Поэтому одновременно с корпусом
заведено правило: `corpus-real/`, `incoming/`, `data/` прописаны в `.gitignore`
навсегда, и то же правило продублировано в `corpus/README.md` — там, где его
увидит тот, кто кладёт файл.

**Грабля на ровном месте:** в `.gitignore` комментарий действует только
с начала строки. Строка `models/  # 1,2 ГБ` — не правило с пояснением,
а шаблон имени целиком, и `models/` при этом **не игнорируется**. Поймано
до первого коммита, но поймано глазами, а не проверкой. Отсюда привычка:
после `git add` смотреть `git diff --cached --name-only` и грепать индекс
на значения ключей, а не доверять тому, что правила написаны верно.
