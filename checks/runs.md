# Журнал прогонов

Ключ к сравнимости: прогоны сравнимы **только** при одном наборе полей, единиц
и версии золотого набора. Несравнимость журнала — почти всегда «считали по разным
метрикам». Прогон, не занесённый сюда, не существует (дефект «замер без записи»);
решение, опирающееся на прогон, ссылается на его `id`.

## Схема прогона

Каждый прогон заполняет все обязательные поля:

```yaml
id: RUN-<дата>-<буква>        # устойчивый, не меняется
hypothesis: H-...             # какую проверку/гипотезу закрывает (если есть)
stand: local | partner        # на каком стенде
created: 2026-08-14

config:                       # проверяемая конфигурация целиком
  embedder: —
  pooling: —
  chunking: —
  reranker: —
  llm: —
  quantization: —
  k: —                        # сколько чанков подаётся в контекст

golden_set: gs-v2             # версия прибора

metrics:                      # имена из criteria.md; величина ВСЕГДА с единицей
  recall@5:  { value: —, unit: доля }
  precision@1: { value: —, unit: доля }
  ndcg@5:    { value: —, unit: доля }
  latency_p95: { value: —, unit: сек }
  context_tokens: { value: —, unit: токены }  # суммарный объём поданного контекста
  # метрику на потолке (hit@5) НЕ выбрасывать — у неё любое движение значимо

changed_answers:              # «сколько вопросов изменили ответ» — по каждой метрике
  ndcg@5: —
  recall@5: —

sanity:                       # санитарка ОТДЕЛЬНО, решений из неё не выводим
  result: —
  note: "проверяем, что модель не битая, а не качество поиска"

provenance:
  stand_commit: —             # коммит RAG-stand, чтобы прогон был воспроизводим
  raw: —                      # где лежит сырьё вывода
```

сравнивающих способы нарезки (`H-004`, `H-010`, `H-011`, `H-012`): без него
