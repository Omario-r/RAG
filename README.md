# RAG-lab — семантический поиск по договорам в закрытом контуре

**Точка входа в волт.** Здесь — что это за проект, как он устроен и где что
лежит. Состояние работ — в [06-roadmap.md](06-roadmap.md), статус этапа
меняется только там.

## Что за проект

Партнёр разворачивает у себя поиск по договорам: юрист спрашивает «где условия
о простое транспорта под погрузкой» и получает не список файлов, а конкретные
пункты конкретных договоров. Всё в закрытом контуре, без облачных API —
документы клиента наружу не уходят.

Наша часть — **пайплайн**: разбор документа, нарезка на пункты, векторизация,
загрузка в Qdrant, поиск, реранкер, извлечение реквизитов в SQL. Железо,
Qdrant и llama.cpp-сервер — на стороне партнёра. Задача его словами,
инфраструктура и разделение работ — [00-context.md](00-context.md).

Бизнес-часть (ниши, сегменты, экономика, страхи заказчика) живёт отдельным
волтом — `~/Development/Home/Business`. Здесь только техника.

**Режим проекта — эксперимент, а не разработка.** Читатель этих документов —
я сам через месяц. Цель — понимать, что происходит внутри пайплайна, поэтому
цифры важнее ощущений, а «почему так решено» записывается наравне с «как
сделано». Продуктовая работа отложена сознательно.

## Как это работает

Два контура. Подготовка — редко и долго, запрос — часто и быстро:

```
договор → текст → чанки (пункты) → векторы → Qdrant        [офлайн]
вопрос  → вектор → top-50 → реранкер → top-5 → ответ       [онлайн]
```

Тяжёлую работу делаем один раз при загрузке, чтобы запрос отрабатывал за доли
секунды. Разбор целиком, включая то, **где в этом пайплайне ломается
качество** (чаще всего в чанкинге, а не в модели), —
[01-pipeline.md](01-pipeline.md).

Второй контур, независимый от поиска: формальные реквизиты договора извлекаются
моделью по жёсткой схеме и складываются в SQL — [07-extraction.md](07-extraction.md).
Он опаснее поиска: неверно найденный пункт юрист заметит, неверно извлечённую
сумму — нет.

## Узлы пайплайна

Пайплайн работает сквозным образом на локальном стенде: договор → чанки →
векторы → Qdrant → поиск → реранкер → извлечение. Ниже он разложен на семь
узлов — это общая ось волта: у каждого узла есть теория в базе знаний,
практика в справочниках корня и своя команда на стенде. Состояние этапов
и что осталось — [06-roadmap.md](06-roadmap.md).

### В каком это состоянии

| Узел | Чем меряется | Сейчас | Чем подтверждено | Уверенность |
|---|---|---|---|---|
| **Корпус и разбор** | покрытие ссылок золотого набора, дефекты при чтении глазами | 5 договоров, 172 пункта, все 64 ссылки покрыты; партия 2 (~30 договоров) написана, не загружена | [[11-evidence#Чанкинг\|реестр 09.08]] | **средняя** — корпус синтетический, ИНН не проходят контрольную сумму |
| **Чанкинг** | медиана и максимум длины, осиротевшие заголовки | 172 пункта → 144 чанка, медиана 42 токена, максимум 299 при пределе 512 | [[11-evidence#9. Мелкие пункты склеиваются с родителем, а не с соседями\|11-evidence #9]] | **средняя** — правило проверено на пяти договорах одного типа |
| **Эмбеддинги** | `recall@5` на золотом наборе | пулинг `mean` 0,815 против `cls` 0,741; e5 против Qwen3 — разница в два вопроса из 27 | [[11-evidence#3. Префиксы-инструкции не нужны\|11-evidence #2,3,5]] | **раздельная**: по пулингу высокая, по выбору модели никакая — корпус разницы не видит |
| **Хранилище** | пойнт/с, время загрузки | батч ×22, gRPC ×3,3, оптимум батча 256–512, один работник быстрее четырёх, загрузка 0,03 с | [[11-evidence#1. Батчинг ничего не ускоряет\|11-evidence #1,4]] | **высокая по механике, никакая по масштабу** — 144 пойнта против цели в тысячи |
| **Поиск и реранк** | `recall@1`, `hit@1`, `nDCG@5`, мс/запрос | `recall@1` 0,508 · `hit@1` 28/32 · `nDCG@5` 0,905 · 161 мс при top-10 | [[11-evidence#7. Величина без единицы измерения обманывает\|11-evidence #7,12]] | **низкая** — `hit@5` на потолке, базовой линии нет до партии 2 |
| **Ответ** | не определено | — | — | **узла нет** — теория написана целиком, практики ноль |
| **Извлечение** | доля заполненных, доля прошедших цитат | 16 полей из 18, все 16 с проверенной цитатой, 74 с/документ, воспроизводимо побайтно | [[11-evidence#14. Отказ модели выглядит благополучно\|11-evidence #13,14]] | **низкая** — эталона нет, accuracy не мерена |

Колонка «уверенность» — оценка того, можно ли опереться на число, а не
самого числа. Метрики поиска выглядят отлично и при этом годятся только
для отлова поломки: `hit@5` = `hit@50` = 1,000 на корпусе из 144 чанков.
Что этими цифрами делать запрещено — [[11-evidence#Что запрещено делать с этими цифрами|11-evidence]].

Контур партнёра в таблицу не входит: там замерены конфигурация, скорость
и пулинг, но ни одной метрики качества — [13-partner-stand.md](13-partner-stand.md).

### Запустить

Стенд — `~/Development/Home/RAG-stand/`, отдельный репозиторий:

```bash
./start-stand.sh                            # Qdrant + эмбеддер + реранкер + модель
uv run python scripts/load-qdrant.py        # загрузить корпус
uv run python scripts/evaluate.py --rerank  # посчитать метрики
```

## Как вести волт

Десять правил, без которых документы разъезжаются. Первые четыре — про то,
что где лежит; остальные — про честность записи и про сцепку со стендом.

1. **Статус — только в [06-roadmap.md](06-roadmap.md)**, в таблице и в разделе
   этапа. Здесь статуса нет намеренно.
2. **Жанры не смешивать.** «Как устроено» — справочники 01–10; «почему так
   решено» — [12-decisions.md](12-decisions.md); «чем доказано, с цифрами» —
   [11-evidence.md](11-evidence.md); «что и когда прогоняли» —
   [09-experiments.md](09-experiments.md). Их смешение раздуло
   `08-local-stand.md` до 51 КБ, а этот файл — до 57.
3. **Ответы партнёра** сначала в [questions-to-partner.md](questions-to-partner.md),
   затем разносятся по профильным документам — маршрут указан там же в конце.
4. **Каждый документ заканчивается «Открытыми вопросами»** — это рабочий
   список, а не украшение: закрытый вопрос вычёркивается, новый дописывается.
5. **Решение без основания** через месяц выглядит как произвол
   и переоткрывается. Строка в журнале решений — с датой и основанием.
6. **Помечать непроверенное.** Всё, что взято из статей и не подтверждено
   на нашем стенде, несёт пометку «проверить». Цифра из чужого блога —
   гипотеза, а не результат.
7. **Помечать, что за блок перед читателем.** Примеры вывода команд
   подписываются: **Вывод (дословно)** · **Выжимка** (показано не всё) ·
   **Схема формата** (значения выдуманы). Выжимка без команды, которая её
   производит, недопустима — читатель сверяет свой экран с документом
   и принимает расхождение за поломку.
8. **Ссылка на раздел — только вики-ссылкой.** На документ целиком — обычная
   markdown-ссылка `[04-qdrant.md](04-qdrant.md)`. На раздел —
   `[[04-qdrant#5. Параметр wait|текст ссылки]]`: волт читается в Obsidian,
   а markdown-якорь там не переходит. Переименование заголовка ломает все
   ссылки на него, искать их `grep -rn '\[\['`.

9. **Узловой справочник открывается разделом «Как стоит сейчас».** Снимок
   фактической конфигурации с указанием файла стенда, откуда он снят. Без него
   читатель не отличает «так у нас сделано» от «так вообще бывает» — а после
   выноса теории в базу знаний в справочнике остаются оба жанра. Приём,
   который не применён, помечается прямо под своим заголовком: **«У нас
   не используется»**. Пометка идёт **под** заголовком, а не в нём:
   переименование заголовка ломает все вики-ссылки на него.
10. **Расхождение волта со стендом записывается, а не терпится.** Реестр —
   [[06-roadmap#Расхождения волта со стендом|06-roadmap.md]]. Замеренное,
   но не применённое — долг; молчаливое расхождение превращает справочник
   в художественную литературу.
