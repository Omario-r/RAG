# Лаб 4. Загрузка в Qdrant и замеры

Этап 4 из [06-roadmap.md](06-roadmap.md). Справочник — [04-qdrant.md](04-qdrant.md);
здесь только последовательность действий. Правила устройства лаб —
[lab-style.md](lab-style.md).

**Цель:** корпус загружается одной командой, время известно, повторный
запуск не плодит дублей. Лаба заканчивается модулем `rag_lab/store.py`,
загруженной коллекцией и своими цифрами вместо статейных.

Лаба **опровергает три утверждения справочника** — все три взяты из чужих
статей и помечены там как непроверенные. Проверка на своём железе их
не подтвердила.

## Что нужно знать до первого шага

Коллекция, пойнт и payload введены в [лаб 1](lab-01-qdrant.md), здесь только
новое:

| Термин | Рабочее определение |
| --- | --- |
| **Сегмент** | Файл-кусок коллекции. Qdrant режет коллекцию на сегменты сам; на нашем стенде их 5. Ключевое слово всей лабы |
| **`indexing_threshold`** | Порог в килобайтах, **на сегмент**. Сегмент меньше порога не индексируется: полный перебор быстрее графа |
| **`indexed_vectors_count`** | Сколько векторов реально попало в HNSW. Ноль — не всегда ошибка |
| **Статус коллекции** | `green` / `yellow` / `red`. Означает состояние оптимизатора, **не** готовность индекса |
| **`wait`** | Ждать ли применения записи. Три стадии записи и две точки возврата — [[04-qdrant#5. Параметр wait\|разбор в справочнике]] |
| **Идемпотентность** | Повторная загрузка тех же данных не создаёт дублей. Достигается детерминированным `id`, а не проверками |
| **UUID5** | Хэш от строки в форме UUID. `TR-114#4.2` всегда даёт один и тот же id |

Маркеры блоков вывода:

| Маркер | Что означает |
|---|---|
| **Вывод (дословно)** | Скопировано из терминала как есть |
| **Выжимка** | Показано только содержательное; команда печатает больше |
| **Схема формата** | Поля настоящие, значения выдуманы — со своими не сравнивать |

Все выводы сняты **09.08.2026**: MacBook Air M4, Qdrant 1.19.0 нативным
бинарником, `qdrant-client` 1.19.0, эмбеддер `Qwen3-Embedding-0.6B-GGUF:Q8_0`.

## Шаг 2. Идентификатор пойнта — не счётчик

```bash
uv run python -c "
import sys; sys.path.insert(0,'src')
from rag_lab.store import point_id
for a in ('TR-114#4.2', 'TR-114#4.2', 'TR-114#4.3'):
    print(f'{a:14s} -> {point_id(a)}')
"
```

**Прежде чем выполнить — ответьте себе:** одинаковый ли id получат две
первые строки?

**Вывод (дословно)**:

```none
TR-114#4.2     -> df1de3d4-17d8-5f3c-8aaf-7b6627ab04a9
TR-114#4.2     -> df1de3d4-17d8-5f3c-8aaf-7b6627ab04a9
TR-114#4.3     -> 34ab7735-5d77-57a7-be44-ecc156295ee2
```

**Одинаковый.** UUID5 — это хэш от строки, а не случайное число. Отсюда
идемпотентность: повторная загрузка того же договора **перезаписывает**
свои пойнты. При отладке чанкера корпус перезаливается десятки раз,
и со счётчиком коллекция быстро перестала бы значить что-либо.

Qdrant принимает только целые числа и UUID, а наш адрес — строка
`TR-114#4.2`. UUID5 переводит одно в другое без потери устойчивости.

## Шаг 4. Сколько стоит векторизация, а сколько загрузка

```bash
uv run python -c "
import sys, time; sys.path.insert(0,'src')
from rag_lab.corpus import build_chunks
from rag_lab.embed import Embedder
ch = build_chunks(); e = Embedder()
t0=time.perf_counter(); e.embed([c.embed_text for c in ch], use_cache=False)
print(f'холодный кэш: {time.perf_counter()-t0:.2f} с на {len(ch)} чанков')
t0=time.perf_counter(); e.embed([c.embed_text for c in ch])
print(f'тёплый кэш:   {time.perf_counter()-t0:.2f} с')
"
```

**Вывод (дословно)**:

```none
холодный кэш: 7.10 с на 144 чанков
тёплый кэш:   0.01 с
```

**Соотношение важнее абсолютных чисел.** Векторизация — 7,10 с, загрузка
в Qdrant — 0,03 с. Узкое место пайплайна не в базе и в 230 раз не в ней.

Отсюда практический вывод, который стоит помнить всю оставшуюся часть
проекта: оптимизировать загрузку в Qdrant на нашем масштабе — занятие
для отчёта, а не для дела. Приёмы из следующих шагов начинают что-то
значить на сотнях тысяч пойнтов.

## Шаг 7. Параметры, которые ничего не дали

Своей команды у шага нет — замеры 3, 4 и 5 из тех же семи. Все три
против ожиданий справочника.

**Вывод (дословно)**, замер 3 — параметр `wait`:

```none
  wait=False                                      0.46 с      21549 пойнт/с   (разброс 0.46–0.49)
  wait=True                                       0.66 с      15218 пойнт/с   (разброс 0.64–0.68)
```

`wait=True` стоит около 30 % — ожидаемо, справочник прав.

**Вывод (дословно)**, замер 4 — размер батча:

```none
  batch_size=32                                   0.88 с      11397 пойнт/с   (разброс 0.70–1.05)
  batch_size=64                                   0.66 с      15261 пойнт/с   (разброс 0.65–0.66)
  batch_size=128                                  0.47 с      21394 пойнт/с   (разброс 0.42–0.47)
  batch_size=256                                  0.37 с      27189 пойнт/с   (разброс 0.32–0.38)
  batch_size=512                                  0.36 с      28058 пойнт/с   (разброс 0.36–0.36)
```

Справочник советует 64–256. Нижняя граница явно мала: 64 работает вдвое
медленнее 512. Наш оптимум — **256–512**.

**Вывод (дословно)**, замер 5 — параллелизм:

```none
  parallel=1                                      0.42 с      23714 пойнт/с   (разброс 0.36–0.45)
  parallel=2                                      0.60 с      16807 пойнт/с   (разброс 0.58–0.72)
  parallel=4                                      0.57 с      17687 пойнт/с   (разброс 0.53–0.61)
```

**Параллелизм мешает.** Один работник быстрее двух и четырёх, и это
не разброс: разбросы не перекрываются. Справочник советует 2–4 —
на нашем железе совет вредный.

Ровно та же форма результата, что в [[lab-02-embeddings#Шаг 12. Замер: помогает ли батчинг|лаб 2 с батчингом]]:
приём, который «должен» помогать, не помогает, потому что узкое место
не там, где предполагалось.

**Отдельно — грабля.** `parallel > 1` в `qdrant-client` разводит работу
**процессами**, а не потоками. На macOS процессы порождаются через spawn,
то есть дочерний заново импортирует главный модуль. Скрипт без
`if __name__ == "__main__"` выполняется целиком в каждом работнике —
на этом стенде получилось три процесса, заново векторизующих корпус,
вместо загрузки. Значение по умолчанию в `store.upload` поэтому 1.

## Шаг 8. Главный приём, которого не оказалось

Своей команды у шага нет — замер 6 из тех же семи.

Справочник называет `indexing_threshold=0` на время загрузки **главным
приёмом** и приводит из статьи Qdrant «порядка +30 % пропускной способности».

**Вывод (дословно)**, замер 6:

```none
  indexing_threshold=0 (индексация выключена)     0.41 с      24123 пойнт/с   (разброс 0.33–0.43)
  indexing_threshold=1000 (индексация идёт)       0.38 с      26076 пойнт/с   (разброс 0.37–0.39)
  -> выключенная индексация экономит -8 % времени заливки
     (у рабочего порога 20000 КБ разницы с нулём нет вовсе:
      сегменты до него не дорастают, индексация не начинается)
```

**Минус восемь процентов** — то есть ничего, в пределах разброса.
Тридцати процентов нет.

И это ещё не самое интересное. Обратите внимание на строку в скобках:
при **рабочем** пороге 20000 КБ сравнивать вообще нечего, потому что
индексация не запускается ни в одном из режимов. Почему — следующий шаг.

## Шаг 9. Зелёная коллекция без индекса

Своей команды у шага нет — последний, седьмой замер шага 5.

**Вывод (дословно)**, замер 7 — тот же корпус, два разных порога:

```none
  порог 20000 КБ:
    статус: green
    пойнтов: 10000
    сегментов: 5
    проиндексировано векторов: 0
    ждали, с: 5.05
    вердикт: HNSW НЕ строился: ~8000 КБ векторов на сегмент при пороге 20000 КБ

  порог 1000 КБ:
    статус: green
    пойнтов: 10000
    сегментов: 5
    проиндексировано векторов: 10000
    ждали, с: 3.03
    вердикт: HNSW построен
```

**`indexing_threshold` применяется к сегменту, а не к коллекции.**
Qdrant разложил 10 000 пойнтов на 5 сегментов, в каждом около 8 МБ
векторов при пороге 20 МБ — ни один сегмент до порога не дотянул,
и граф не построился вовсе.

Проверено с двух сторон, обе показаны выше и в шаге 10: понизить порог —
индекс строится за 2–3 секунды; оставить порог и свести всё в один
сегмент — тоже строится.

**Отсюда главный вывод лабы:**

> Зелёный статус означает «оптимизатору нечего делать», а не «индекс
> построен». Он выставлен с самого начала и потому не является
> проверкой готовности.

Справочник предписывает «дождаться, пока статус станет `green`». На нашей
коллекции это ожидание завершается мгновенно и не значит ничего.

## Шаг 10. Убедиться самому

Стоит проверить руками — утверждение из шага 9 неочевидное.

```bash
uv run python -c "
import sys, time; sys.path.insert(0,'src')
import numpy as np
from qdrant_client import models
from rag_lab import store
cl = store.client(); N, DIM = 10000, 1024
if cl.collection_exists('probe'): cl.delete_collection('probe')
cl.create_collection('probe',
  vectors_config=models.VectorParams(size=DIM, distance=models.Distance.COSINE, on_disk=True),
  optimizers_config=models.OptimizersConfigDiff(indexing_threshold=0, default_segment_number=1))
v = np.random.default_rng(1).normal(size=(N,DIM)).astype('float32')
v /= np.linalg.norm(v, axis=1, keepdims=True)
cl.upload_points('probe', [models.PointStruct(id=i, vector=v[i].tolist()) for i in range(N)], batch_size=256)
cl.update_collection('probe', optimizer_config=models.OptimizersConfigDiff(indexing_threshold=20000))
for _ in range(6):
    i = cl.get_collection('probe')
    print(f'  статус={str(i.status):8s} сегментов={i.segments_count} проиндексировано={i.indexed_vectors_count}')
    if i.indexed_vectors_count >= N: break
    time.sleep(1)
cl.delete_collection('probe')
"
```

Отличие от шага 9 одно — `default_segment_number=1`: тот же порог,
те же 10 000 пойнтов, но в одном сегменте.

**Вывод (дословно)**:

```none
  статус=yellow   сегментов=1 проиндексировано=0
  статус=yellow   сегментов=2 проиндексировано=0
  статус=green    сегментов=2 проиндексировано=10000
```

**Было** (шаг 9, автосегментация, 5 сегментов):

```none
  статус=green    сегментов=5 проиндексировано=0
  статус=green    сегментов=5 проиндексировано=0
  ... и так 24 секунды
```

**Стало** (один сегмент, тот же порог 20000 КБ), полторы секунды:

```none
  статус=yellow   сегментов=1 проиндексировано=0
  статус=yellow   сегментов=2 проиндексировано=0
  статус=green    сегментов=2 проиндексировано=10000
```

Разница только в количестве сегментов. Статус `yellow` здесь — признак
того, что оптимизатор **работает**; в первом случае его не было ни разу,
потому что работать было не над чем.

## Шаг 12. Фильтр по payload-индексу

```bash
uv run python -c "
import sys; sys.path.insert(0,'src')
from qdrant_client import models
from rag_lab import store
cl = store.client()
f = models.Filter(must=[models.FieldCondition(key='doc_id', match=models.MatchValue(value='SH-45'))])
print('пойнтов по doc_id=SH-45:', cl.count(store.COLLECTION, count_filter=f, exact=True).count)
print('индексы:', sorted(cl.get_collection(store.COLLECTION).payload_schema))
"
```

**Вывод (дословно)**:

```none
пойнтов по doc_id=SH-45: 31
индексы: ['clause_no', 'doc_id', 'doc_type', 'has_table', 'part', 'section_no']
```

31 — ровно столько пунктов у SH-45 (лаб 3, шаг 12). Индексы созданы
вместе с коллекцией, а не «когда понадобятся»: отложенный шаг такого
рода не делается никогда.

**Эффекта от индексов на 144 пойнтах не увидеть** — фильтр работает
и без них, а разница в скорости на таком объёме не измеряется. Индекс
здесь создаётся ради привычки и ради переезда к партнёру, где объём
другой ([[lab-01-qdrant#Шаг 10. Создать payload-индексы|лаб 1, шаг 10]]).

# Разбор

## Почему цифры этой лабы не переносятся к партнёру

Ни одна не переносится, и вот почему по пунктам:

| Замер | Что изменится у партнёра |
|---|---|
| Пакетно против поштучно | Разрыв станет **больше**: у нас клиент и сервер на одной машине, сетевого круга нет вовсе |
| gRPC против REST | То же — на сети накладные расходы REST дороже |
| `parallel` | У нас один узел без шардов. При нескольких шардах отправная точка «поток на шард» может заработать |
| `indexing_threshold` | GPU-индексация меняет цену построения графа на порядок |
| Абсолютная пропускная способность | Другой диск, другая память, другая сеть |

Переносится не число, а **методика**: временная коллекция, медиана из
трёх прогонов, разброс рядом со средним, проверка вердикта с двух сторон.

## Почему разброс печатается рядом со средним

Первый прогон этой лабы дал «выключенная индексация экономит +14 %»,
второй — «−12 %». Оба замера были честными, оба по одному прогону.
Приёма нет, есть шум.

Правило то же, что и в [[lab-style#Правило 10. Санитарная проверка не заменяет метрику|правиле 10]]:
прежде чем сравнивать средние, надо знать разброс. Три прогона и печать
`min–max` рядом с медианой стоят десяти строк кода и снимают вопрос.

Где разбросы перекрываются — разницы нет, как бы ни выглядели средние.
Где не перекрываются (gRPC против REST, `parallel=1` против 2) — разница
есть.

## Почему `indexed_vectors_count = 0` — это не ошибка

Полный перебор на малой коллекции быстрее графа. HNSW — многослойный
граф, спуск по нему стоит накладных расходов, и на тысячах векторов
они не окупаются. Qdrant это знает и потому не строит индекс, пока
сегмент мал.

Опасность не в самом факте, а в том, что **о нём легко не знать**.
Сценарий: коллекция выросла, порог не пересмотрен, сегменты по-прежнему
мелкие из-за автосегментации, поиск идёт перебором, latency растёт
линейно с объёмом — и никто не понимает почему, потому что статус
зелёный, а `indexing_threshold` «выставлен правильно».

Проверка, которая это ловит, — не статус, а `indexed_vectors_count`
против `points_count`, вместе с числом сегментов. Она встроена
в `store.finish_indexing` и печатается вердиктом.

## Что делать с забытым `indexing_threshold=0`

Справочник называет это главной ловушкой этапа: забытый ноль оставляет
коллекцию без HNSW навсегда. Замер эту опасность **не отменяет**,
а уточняет: на малой коллекции разницы не будет и с забытым нулём,
а на большой — будет, и катастрофическая.

То есть ловушка не проявляется ровно там, где её стали бы искать
(на тестовом корпусе), и проявляется там, где искать поздно. Поэтому
возврат порога сделан не пунктом инструкции, а функцией, которая
ещё и печатает вердикт.

## Почему пойнт — это чанк, а не пункт

Пойнт соответствует чанку, а чанк может содержать несколько пунктов
(родитель со своими подпунктами, [лаб 3](lab-03-chunking.md)). Поэтому
в payload лежат оба адреса: `clause_no` — ведущий пункт, `clause_ids` —
все вошедшие.

Метрика считается по `clause_ids`: вопрос золотого набора может указывать
на подпункт 3.4.3.1, который физически лежит внутри чанка `AR-203#3.4`.
Если считать по `clause_no`, такой ответ будет засчитан как промах,
и recall окажется занижен без всякой связи с качеством поиска.

## Открытые вопросы

1. **Оптимальный размер батча замерен только до 512.** 1024 и выше
   не проверялись; ограничение gRPC на размер сообщения — 4 МБ,
   и при 1024 точках на 1024 измерения это уже 4 МБ, то есть предел рядом.
2. **`parallel` не проверен на нескольких шардах.** У нас один узел;
   утверждение «поток на шард» осталось непроверенным.
3. **Сколько сегментов правильно** — не изучено. Автосегментация дала 5
   и тем самым отключила индексацию; лечится ли это `default_segment_number`
   или пересмотром порога, на нашем масштабе не проверить.
4. **`on_disk=True` не сравнивался с `False`.** Взято по справочнику,
   влияние на скорость загрузки и поиска не замерено.
5. **Квантизация не трогалась вовсе.** Понадобится на объёмах партнёра.
