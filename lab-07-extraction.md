# Лаб 7. Извлечение реквизитов в SQL

Этап 7 из [06-roadmap.md](06-roadmap.md). Справочник — [07-extraction.md](07-extraction.md);
здесь только последовательность действий. Правила устройства лаб —
[lab-style.md](lab-style.md).

**Цель:** второй контур системы — из договора в таблицу, которой можно
доверять. Лаба заканчивается модулями `rag_lab/extract.py` и `rag_lab/db.py`,
рабочей схемой БД с историей значений и проверенными кодом нормализаторами.

> [!warning] Лаба проходится не целиком
> Шаг «модель заполняет схему» **не выполняется**: на стенде нет генеративной
> модели, есть только эмбеддер и реранкер. Что именно от этого не сделано
> и что нужно, чтобы доделать, — [[lab-07-extraction#Шаг 9. Чего не хватает и что для этого нужно|шаг 9]].
>
> Всё, что до модели (схема, отбор фрагментов) и после неё (проверка цитат,
> нормализация, история значений), сделано и проверено на настоящем корпусе.
> Это большая часть этапа: сама модель — один вызов между двумя барьерами.

## Что нужно знать до первого шага

| Термин | Рабочее определение |
| --- | --- |
| **Структурированное извлечение** | Модели дают текст и **жёсткую схему ответа**; она заполняет поля, а не пишет свободный текст |
| **`response_format`** | Параметр llama.cpp: JSON Schema, ограничивающая вывод. Невалидный JSON физически не сгенерируется |
| **GBNF** | Формат грамматик llama.cpp, в который конвертируется схема |
| **Цитата** | Дословный фрагмент документа, подтверждающий значение. Проверяется кодом на вхождение |
| **Дело** (`contract_case`) | Основной договор + допсоглашения + приложения. Единица учёта, а не файл |
| **История значений** | БД хранит не «значение поля», а все его редакции с датами; текущее вычисляется |
| **Очередь** (`pending`) | Куда уходит значение, не прошедшее проверку. Не в SQL |

**Главное отличие от поиска, из которого следует всё остальное.** Плохой
поиск виден сразу — «ничего не нашлось». Плохое извлечение невидимо: модель,
не найдя суммы, выдаёт правдоподобное число в правильном формате, оно ложится
в SQL, и через месяц юрист получает достоверно выглядящий ответ «договоров
свыше 5 млн — четыре», который просто неверен.

Маркеры блоков вывода:

| Маркер | Что означает |
|---|---|
| **Вывод (дословно)** | Скопировано из терминала как есть |
| **Выжимка** | Показано только содержательное; команда печатает больше |

Все выводы сняты **09.08.2026** на корпусе первой партии.

## Шаг 1. Схема полей: узкое ядро, а не сорок полей

```bash
uv run python scripts/extract-demo.py 1
```

**Выжимка** — команда печатает ещё и устройство поля, оно ниже:

```none
полей в схеме: 18  (ядро 12 + перевозка 6)
```

Соблазн описать сорок полей «на все случаи» приводит к тому, что модель
заполняет их наугад. Ядро — то, без чего не собрать фильтр: номер, дата,
тип, стороны, сумма, срок, подсудность. Расширение под перевозку —
предел ответственности, неустойка, простой, отсрочка платежа.

**Что заметить:** поле — не значение, а объект.

**Вывод (дословно)**, устройство одного поля:

```json
{
 "type": ["object", "null"],
 "properties": {
  "value": {"type": ["string", "number", "boolean", "null"]},
  "quote": {"type": "string"},
  "clause": {"type": ["string", "null"]}
 },
 "required": ["value", "quote"],
 "additionalProperties": false
}
```

Модель возвращает не `"amount": 4500000`, а значение **вместе с цитатой
и номером пункта**. Без цитаты записывать в SQL нечего — почему, в шаге 5.

## Шаг 2. Ловушка, о которую спотыкаются все

Своей команды у шага нет: это последние две строки вывода из шага 1.

**Вывод (дословно)**, конец раздела 1:

```none
Схема ограничивает вывод, но В ПРОМПТ НЕ ПОДСТАВЛЯЕТСЯ: модель её
не видит и без словесного описания заполнит валидный JSON чем попало.
```

Схема управляет **сэмплированием**: на каждом токене грамматика запрещает
всё, что нарушит структуру. Модель при этом схемы не видит и не знает,
что значит поле `demurrage_rate`.

Поэтому рядом со схемой обязателен промпт с описанием полей: что означает
каждое, в каком формате, что делать, если его нет. Иначе получится
безупречно валидный JSON, заполненный чем попало, — и это худший из всех
исходов, потому что он выглядит правильным.

## Шаг 4. Нормализация: суммы и сверка прописи

```bash
uv run python scripts/extract-demo.py 3
```

**Прежде чем выполнить — ответьте себе:** зачем разбирать пропись,
если цифры уже есть?

**Вывод (дословно)**:

```none
текст                                                           цифры    пропись  сходится
  4 500 000 (четыре миллиона пятьсот тысяч) рублей 00 копе    4500000    4500000  да
  6 200 000 (шесть миллионов двести тысяч) рублей 00 копее    6200000    6200000  да
  1 500 (одной тысячи пятисот) рублей за час                     1500       1500  да
  500 000 (пятьсот тысяч) рублей по каждому случаю             500000     500000  да
  4 500 000 (четыре миллиона пятьдесят тысяч) рублей          4500000    4050000  НЕТ
```

**Затем, что расхождение — сигнал.** Последняя строка: цифры говорят
4 500 000, пропись — 4 050 000. В настоящем договоре это опечатка,
и она стоит миллиона рублей в споре. Автоматика такое значение записывать
не должна, а человеку показать обязана.

**Грабля, на которую наступил этот код.** Первая редакция разбирала пропись
только в именительном падеже, и строка «одной тысячи пятисот» читалась как
**1 000**. Сверка объявляла расхождение там, где его нет, то есть слала
в очередь исправные договоры.

Ложная тревога в такой проверке хуже её отсутствия: на проверку, которая
кричит без причины, через неделю перестают смотреть. Лечится словарём
со всеми падежами.

## Шаг 5. Проверка цитаты — единственный барьер против тихой галлюцинации

```bash
uv run python scripts/extract-demo.py 5
```

**Прежде чем выполнить — ответьте себе:** пустая строка — она пройдёт
проверку на вхождение или нет?

**Вывод (дословно)**:

```none
  настоящая цитата           ПРОШЛА
  другие кавычки и пробелы   ПРОШЛА
  правдоподобная выдумка     отклонена
  пересказ своими словами    отклонена
  пустая строка              отклонена
```

Разбор строк:

| Что подавали | Почему такой результат |
|---|---|
| Настоящая цитата | Точная подстрока документа |
| Другие кавычки, двойные пробелы, другой регистр | Различия, о которых модель знать не обязана. Приводятся к одному виду |
| «…не может превышать **5 800 000**» | Число выдумано — подстроки нет |
| «Договор ограничен суммой четыре с половиной миллиона» | Пересказ, а не цитата |
| Пустая строка | Пустая строка — подстрока чего угодно. Отклоняется отдельной проверкой |

**Модель может выдумать число, но не может выдумать цитату, которая пройдёт
проверку вхождения.** Это и есть весь приём.

**Чего делать нельзя:** ослаблять проверку нечётким сравнением. «Похожая»
цитата — уже не цитата, и барьер, который можно обойти, барьером не является.

Барьер стоит **в одном месте** — в функции записи `put_field`. Не прошло —
строка уходит в `pending`, а не в `extracted_field`. Проверка, разбросанная
по пайплайну, рано или поздно окажется где-нибудь пропущена.

## Шаг 6. Контрольная сумма ИНН, и что она сказала про корпус

```bash
uv run python scripts/extract-demo.py 4
```

**Вывод (дословно)**:

```none
ИНН из нашего корпуса:
  7701234567     10 знаков  НЕ ВАЛИДЕН
  7809876543     10 знаков  НЕ ВАЛИДЕН
  6316543210     10 знаков  НЕ ВАЛИДЕН
  7810111213     10 знаков  НЕ ВАЛИДЕН
  6672334455     10 знаков  НЕ ВАЛИДЕН
  666012345678   12 знаков  НЕ ВАЛИДЕН

Ни один не проходит — и это НЕ ошибка кода. ИНН корпуса выдуманы
при генерации договоров без расчёта контрольной суммы (corpus/README.md).
Проверка на заведомо валидных, публично известных ИНН:
  7707083893     10 знаков  валиден    Сбербанк
  7736050003     10 знаков  валиден    Газпром
  500100732259   12 знаков  валиден    12 знаков, ИП
  7707083894     10 знаков  НЕ ВАЛИДЕН испорчен нарочно
```

**Зачем ИНН вообще.** `ООО «Ромашка»`, `ООО "Ромашка"` и `Общество
с ограниченной ответственностью «Ромашка»` — для SQL три разные компании,
и вопрос «все договоры с Ромашкой» вернёт треть правды. ИНН уникален
и проверяем.

**Находка про корпус.** Ни один ИНН не проходит контрольную сумму: их
выдумали при генерации договоров. Следствие для этапа 7 — на текущем корпусе
**все** контрагенты уйдут в очередь ручного сопоставления, и связку
«контрагент = ИНН» проверять не на чем. Партии 2 нужны валидные ИНН.

Обратите внимание на порядок действий: прежде чем объявлять данные плохими,
проверка проверена на заведомо валидных значениях. Иначе «все ИНН битые» —
такое же вероятное объяснение, как «мой код битый».

## Шаг 7. Схема БД: история значений, а не значение

```bash
uv run python scripts/extract-demo.py 6
```

**Прежде чем выполнить — ответьте себе:** договор ТР-114 ограничен суммой
4 500 000 рублей. Допсоглашение от 15 июня подняло её до 6 200 000. Какую
сумму должна показать система?

**Вывод (дословно)**:

```none
  TR-114       записано полей: 5 из 5
  TR-114-DS1   записано полей: 4 из 4

--- Как отвечает наивная схема «одна строка = один файл» ---
  amount           4500000
  payment_days     10
  demurrage_rate   1500
  date_end         2026-12-31

--- Как отвечает схема с историей значений ---
  amount           6200000                          <- TR-114-DS1, п. 1.1
  payment_days     20                               <- TR-114-DS1, п. 1.2
  demurrage_rate   1800                             <- TR-114-DS1, п. 1.3
  date_end         2027-06-30                       <- TR-114-DS1, п. 1.4
  jurisdiction     Арбитражный суд города Москвы    <- TR-114, п. 9.2
```

**Миллион семьсот разницы на одном поле.** И срок на полгода, и ставка
простоя, и отсрочка платежа — всё разное.

Наивная схема не ошибается в вычислениях. Она отвечает на другой вопрос,
чем ей задали: «что написано в файле» вместо «что действует сейчас».
Для задачи отслеживания договоров это отказ продукта, а не мелкий дефект.

**Что заметить:** `jurisdiction` пришла из основного договора — допсоглашение
её не трогало. Текущее значение вычисляется **по каждому полю отдельно**:
из документа с наибольшей датой, где это поле определено.

## Шаг 8. Что увидит юрист

Своей команды у шага нет: это последние строки вывода из шага 7.

**Вывод (дословно)**, конец раздела 6:

```none
--- История одного поля, как её увидит юрист ---
  2026-03-12  основной       устанавливает    4500000  п. 4.2
  2026-06-15  допсоглашение  изменяет        6200000  п. 1.1
```

Это то, ради чего история и хранится. Юристу нужна не текущая сумма,
а **ответ на спор**: какая сумма действовала в апреле, каким документом
её изменили, в каком пункте это написано.

Схема, хранящая одно текущее значение, такой ответ дать не может в принципе —
информация не потеряна в вычислениях, её просто нет.

**Три операции, а не одна.** Допсоглашение умеет «изложить в редакции»,
«исключить» и «дополнить пунктом» — они не синонимы, и в поле `operation`
хранится, какая именно
([[lab-03-chunking#Шаг 11. Допсоглашение делает три разные вещи|лаб 3, шаг 11]]).
Исключающая правка гасит поле, а не меняет значение.

## Готовность этапа

Критерий из роадмапа: «по полям ядра известна точность, доля ложных значений
измерена, неуверенные поля уходят в очередь подтверждения, а не в базу».

- [x] схема полей: узкое ядро + расширение под перевозку, 18 полей;
- [x] схема БД с историей значений, а не одним значением;
- [x] значение приходит с цитатой; цитата проверяется на вхождение;
- [x] неуверенные поля уходят в `pending`, а не в базу;
- [x] нормализация кодом: даты, суммы со сверкой прописи, ИНН;
- [x] допсоглашение размечено тремя операциями, текущее значение вычисляется;
- [ ] **извлечение моделью** — нет генеративной модели на стенде;
- [ ] **accuracy по каждому полю** — нужна модель и разметка 10–15 договоров;
- [ ] **доля `null` по каждому полю** — то же.

**Этап наполовину.** Сделана та половина, которая определяет, можно ли
доверять результату; не сделана та, которая его производит.

# Разбор

## Почему извлечение опаснее поиска

| | Поиск | Извлечение |
|---|---|---|
| Как выглядит ошибка | «ничего не нашлось» или явно не то | правдоподобное число в правильном формате |
| Когда заметят | сразу, при первом же запросе | через месяц, если вообще |
| Что делает пользователь | переформулирует вопрос | принимает решение на ложных данных |
| Оставляет ли след | да, пустая выдача | нет |

Отсюда все четыре приёма защиты — они конструкционные, а не «проверим
потом»: цитата обязательна, `null` легален, нормализация отдельным шагом,
контрагент по ИНН.

## Почему нормализация — не работа модели

Модель возвращает то, что написано в документе: `«12» марта 2026 г.`,
`4 500 000 (четыре миллиона пятьсот тысяч) рублей 00 копеек`. Привести
это к `2026-03-12` и `4500000.00` можно кодом — детерминированно,
проверяемо, с сообщением об ошибке при неудаче.

Поручить то же самое модели — значит добавить второй источник
галлюцинаций там, где его можно не иметь. Плюс потерять сверку прописи
с цифрами: модель, увидев расхождение, «исправит» его молча, а нам нужно
ровно обратное — чтобы расхождение всплыло.

## Почему `pending` — часть схемы, а не костыль

Соблазн: записывать всё, что извлеклось, а сомнительное помечать флажком
в той же таблице. Так делать нельзя по одной причине: **флажок можно
не заметить в запросе**. `SELECT amount FROM ... WHERE case_id = ?`
вернёт сомнительное значение наравне с проверенным.

Разные таблицы делают ошибку невозможной: непроверенного значения
в `extracted_field` просто нет. Цена — очередь, которую кто-то должен
разбирать; это осознанная цена, а не недоделка.

## Как это связано с Qdrant

Ключ связи — `doc_id`, общий для обеих баз. Часть полей намеренно
дублируется в payload Qdrant (`doc_type`, ИНН сторон, `date_end`) —
денормализация ради фильтрации: чтобы отобрать чанки нужных договоров
прямо в векторном запросе, без похода в SQL за списком идентификаторов.

Два сценария:

- **фильтр известен заранее** («в договорах с этим перевозчиком — что про
  утрату груза?») → фильтр по payload + векторный поиск, один запрос
  ([[lab-04-loading#Шаг 12. Фильтр по payload-индексу|лаб 4, шаг 12]]);
- **фильтр сложный** («договоры, где сумма > 5 млн и есть автопролонгация»)
  → сначала SQL возвращает список `doc_id`, потом векторный поиск
  с условием по ним.

Правило синхронизации: payload обновляется вместе с SQL, одной транзакцией
пайплайна. Рассинхрон здесь даёт «поиск находит договор, которого в списке
нет» — отлаживается мучительно.
