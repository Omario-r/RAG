# Лаб 2. Векторизация: llama.cpp руками

Этап 2 из [06-roadmap.md](06-roadmap.md). Справочник — [03-embeddings.md](03-embeddings.md);
здесь только последовательность действий. Правила устройства лаб —
[lab-style.md](lab-style.md).

**Цель:** научиться получать векторы воспроизводимо и знать, чему в них верить.
Лаба заканчивается модулем `rag_lab/embed.py` и первым сквозным прогоном:
договор → векторы → Qdrant → найденный пункт.

Первые двенадцать шагов — разведка сервера через `curl` и короткие
python-однострочники. Дальше пишется код.

## Что нужно знать до первого шага

| Термин                       | Рабочее определение                                                                                      |
| ---------------------------- | -------------------------------------------------------------------------------------------------------- |
| **Эмбеддинг**                | Массив чисел фиксированной длины, в который модель сворачивает смысл текста                              |
| **Размерность**              | Длина этого массива. У нас 1024. Задаётся моделью, а не текстом                                          |
| **Нормированный вектор**     | Вектор длины ровно 1. Тогда косинус равен скалярному произведению                                        |
| **Пулинг**                   | Как свернуть векторы отдельных токенов в один вектор текста. Задан архитектурой модели                   |
| **Холодный / тёплый расчёт** | Считал ли сервер этот текст заново или взял из кэша промптов. В шаге 8 выяснится, что это разные векторы |

Оболочка ответа у `/v1/embeddings` всегда одна:

```json
{"data": [{"index": 0, "embedding": [...1024 числа...]}], "usage": {...}}
```

Дальше показывается только содержательное. Маркеры блоков те же, что в лаб 1:

| Маркер | Что означает |
|---|---|
| **Вывод (дословно)** | Скопировано из терминала как есть |
| **Выжимка** | Показано только содержательное; команда печатает больше |
| **Схема формата** | Поля настоящие, значения выдуманы — со своими не сравнивать |

Все выводы сняты на стенде **07.08.2026**, сборка llama.cpp `b10280`,
модель `Qwen3-Embedding-0.6B-GGUF:Q8_0`.

## Подготовка

Поднять стенд, если не поднят:

```bash
~/Development/Home/RAG-stand/start-stand.sh
```

Загрузить адреса и ключи — **обязательно через `set -a`**:

```bash
cd ~/Development/Home/RAG-stand && set -a && source .env && set +a
```

`set -a` здесь не украшение. Без него `source .env` создаёт переменные
оболочки, но не экспортирует их — `curl` в той же строке их увидит,
а запущенный питон уже нет, и упадёт с `KeyError: 'EMBEDDER_URL'`.
Половина шагов этой лабы на питоне, так что грабля сработает обязательно.

Обёртка для запросов к эмбеддеру:

```bash
emb() { curl -s -H "Authorization: Bearer $LLAMA_API_KEY" -H 'Content-Type: application/json' "$@" | python3 -m json.tool --no-ensure-ascii; }
```

`--no-ensure-ascii` обязателен: без него `json.tool` печатает кириллицу
как `отв...` и вывод нечитаем.

## Шаг 1. Кто на том конце

```bash
emb $EMBEDDER_URL/v1/models
```

**Прежде чем выполнить — ответьте себе:** чтобы узнать размерность вектора,
надо что-нибудь векторизовать. Или не надо?

**Выжимка** — интересное лежит в `data[0].meta`:

```json
{"vocab_type": 2, "n_vocab": 151669, "n_ctx": 8192,
 "n_ctx_train": 32768, "n_embd": 1024,
 "n_params": 595776512, "size": 633205056, "ftype": "Q8_0"}
```

**Не надо.** `n_embd: 1024` — это и есть размерность, число, без которого
нельзя создать коллекцию в Qdrant. Она видна до первого запроса на
векторизацию.

**Что заметить:** `n_ctx` 8192 против `n_ctx_train` 32768. Первое — решение
того, кто запускал сервер, второе — свойство модели. У партнёра сервер вполне
может быть поднят с контекстом вчетверо меньше, чем модель умеет.

**Ловушка:** в ответе есть поле `capabilities` со значением `["completion"]`.
Для эмбеддера это неверно. Полю не верить, способность проверять запросом.

## Шаг 2. Фактическая конфигурация, а не та, что в скрипте

```bash
emb $EMBEDDER_URL/props
```

**Выжимка** — четыре поля из большого ответа:

```
model_alias : Qwen/Qwen3-Embedding-0.6B-GGUF:Q8_0
build_info  : b10280-61881b1f7
total_slots : 1
n_ctx       : 8192   (в default_generation_settings)
```

**Зачем этот шаг, если модель уже видна в шаге 1:** `/props` показывает
**применённую** конфигурацию. На этом самом стенде скрипт запуска содержал
`--ubatch-size 2048`, а сервер работал с 512 — команда в bash оборвалась
на пустой строке после обратного слеша, и часть аргументов потерялась.
`/props` показывал реальность, ошибался человек
([[08-local-stand#Оборванная команда в скрипте запуска|разбор]]).

Правило: конфигурацию читать у сервера, а не у скрипта и не со слов.

## Шаг 3. Первый вектор

```bash
emb $EMBEDDER_URL/v1/embeddings -d '{"model":"x","input":["Срок доставки груза — 5 календарных дней"]}' | head -20
```

Придёт тысяча чисел. Читать их незачем — интересны только три вещи, и для
них удобнее питон:

```bash
python3 -c '
import json,os,urllib.request,math
r=urllib.request.Request(os.environ["EMBEDDER_URL"]+"/v1/embeddings",
  json.dumps({"model":"x","input":["Срок доставки груза — 5 календарных дней"]}).encode(),
  {"Content-Type":"application/json","Authorization":"Bearer "+os.environ["LLAMA_API_KEY"]})
d=json.load(urllib.request.urlopen(r))["data"][0]["embedding"]
print("размерность:", len(d))
print("первые 5:", [round(x,6) for x in d[:5]])
print("длина вектора:", round(math.sqrt(sum(x*x for x in d)), 10))'
```

**Вывод (дословно):**

```
размерность: 1024
первые 5: [-0.040499, 0.002361, -0.000381, -0.068461, 0.004586]
длина вектора: 1.0000000044
```

**Что заметить:** размерность сошлась с `n_embd` из шага 1 — сервер не соврал.
Длина вектора равна единице: llama.cpp нормализует по умолчанию
(`--embd-normalize 2`).

Ровно это делало осмысленным наблюдение из лаб 1, что косинус измеряет угол,
а не длину: раз все векторы единичной длины, сравнивать их длины и правда
нечего.

## Шаг 4. Длина текста и длина вектора

Слово против трёх тысяч символов, одним запросом:

```bash
python3 -c '
import json,os,urllib.request
def emb(ts):
    r=urllib.request.Request(os.environ["EMBEDDER_URL"]+"/v1/embeddings",
      json.dumps({"model":"x","input":ts}).encode(),
      {"Content-Type":"application/json","Authorization":"Bearer "+os.environ["LLAMA_API_KEY"]})
    return [d["embedding"] for d in json.load(urllib.request.urlopen(r))["data"]]
short="Оплата"
long_="Оплата производится в течение 10 банковских дней с даты подписания акта. "*40
v=emb([short,long_])
for t,x in zip((short,long_),v): print(f"текст {len(t):5d} символов -> вектор {len(x)}")'
```

**Вывод (дословно):**

```
текст     6 символов -> вектор 1024
текст  2920 символов -> вектор 1024
```

**Что заметить:** длина вектора от длины текста не зависит вообще. Отсюда
плата за длинный чанк: тысяча символов сворачивается в те же 1024 числа,
что и одно слово, — чем длиннее текст, тем сильнее размывается его смысл.
Это и есть главный довод за резку по пунктам ([02-chunking.md](02-chunking.md)),
а не по 512 символов.

## Шаг 5. Косинус своими руками

Дальше он нужен в каждом шаге, поэтому заводим файл, а не однострочник:

```bash
cat > /tmp/lab2.py <<'PY'
import json, os, urllib.request
URL = os.environ["EMBEDDER_URL"] + "/v1/embeddings"
KEY = os.environ["LLAMA_API_KEY"]

def emb(texts):
    r = urllib.request.Request(URL, json.dumps({"model": "x", "input": texts}).encode(),
        {"Content-Type": "application/json", "Authorization": "Bearer " + KEY})
    return [d["embedding"] for d in json.load(urllib.request.urlopen(r))["data"]]

def cos(a, b):
    return sum(x * y for x, y in zip(a, b))
PY
```

`cos` — просто скалярное произведение, без деления на длины. Так можно
только потому, что векторы уже нормированы (шаг 3). На ненормированных
это была бы ошибка.

Проверка, что файл рабочий:

```bash
python3 -c 'exec(open("/tmp/lab2.py").read()); a,b=emb(["договор","контракт"]); print(round(cos(a,b),4))'
```

**Вывод (дословно):** `0.8765`

## Шаг 6. Санитарная проверка

Три текста: два про одно и то же **разными словами** и один про другое.
Разные слова принципиальны — на одинаковых проверка выродилась бы
в сравнение подстрок.

```bash
python3 -c '
exec(open("/tmp/lab2.py").read())
a="Перевозчик уплачивает неустойку 0,1% от стоимости перевозки за каждый день просрочки доставки груза."
b="За задержку доставки с исполнителя взыскивается пеня в размере одной десятой процента в сутки."
c="Арендатор обязан поддерживать помещение в надлежащем санитарном состоянии."
va,vb,vc=emb([a,b,c])
print(f"неустойка <-> пеня      : {cos(va,vb):.4f}")
print(f"неустойка <-> санитария : {cos(va,vc):.4f}")
print(f"разрыв                  : {cos(va,vb)-cos(va,vc):.4f}")'
```

**Вывод (дословно):**

```
неустойка <-> пеня      : 0.6755
неустойка <-> санитария : 0.2096
разрыв                  : 0.4659
```

**Что заметить:** ни одного общего значимого слова у первых двух текстов нет —
«неустойка» против «пеня», «просрочка» против «задержка». Модель их сближает.
Эта проверка ловит сразу три беды: неверный пулинг, неподходящую модель
и забытые префиксы. Занимает десять секунд, делать перед каждым разбором
«почему поиск плохой».

**И главное — 0,2096 у текстов, не имеющих общего ничего.** Ноля не бывает.
Абсолютное значение косинуса не означает ничего, информативен разрыв внутри
одной выдачи.

## Шаг 7. Тот же текст дважды

**Прежде чем выполнить — ответьте себе:** один и тот же текст, посланный
шесть раз подряд. Вы ожидаете шесть одинаковых векторов?

```bash
python3 -c '
exec(open("/tmp/lab2.py").read())
t="Срок доставки груза — 5 календарных дней"
vs=[emb([t])[0] for _ in range(6)]
for i in range(1,6):
    print(f"запрос1 vs запрос{i+1}: cos={cos(vs[0],vs[i]):.12f}  побитово={vs[0]==vs[i]}")'
```

**Вывод (дословно):**

```
запрос1 vs запрос2: cos=0.999999287612  побитово=False
запрос1 vs запрос3: cos=0.999999287612  побитово=False
запрос1 vs запрос4: cos=0.999999287612  побитово=False
запрос1 vs запрос5: cos=0.999999287612  побитово=False
запрос1 vs запрос6: cos=0.999999287612  побитово=False
```

**Нет.** Причём это не случайный шум: запросы со второго по шестой совпадают
между собой до последнего знака и **одинаково** отличаются от первого.
Что здесь происходит — [[#Почему один текст даёт два вектора|в разборе]].

**Практический вывод, который стоит запомнить сейчас:** проверять пайплайн
сравнением векторов на равенство нельзя. `v1 == v2` законно окажется ложью
на верном коде. Сравнивать косинусом с порогом.

## Шаг 8. Пустой текст

**Прежде чем выполнить — ответьте себе:** пустая строка на входе — ошибка
`400` или вектор?

```bash
python3 -c '
exec(open("/tmp/lab2.py").read())
for probe in ("", "   ", "\n"):
    v=emb([probe])[0]
    print(f"{probe!r:6} -> вектор {len(v)}, норма {sum(x*x for x in v)**0.5:.4f}, первые 3 {[round(x,4) for x in v[:3]]}")'
```

**Вывод (дословно):**

```
''     -> вектор 1024, норма 1.0000, первые 3 [0.0398, -0.1064, 0.0001]
'   '  -> вектор 1024, норма 1.0000, первые 3 [-0.0333, -0.0641, -0.0154]
'\n'   -> вектор 1024, норма 1.0000, первые 3 [-0.0523, -0.0199, -0.0143]
```

**Вектор.** Полноценный, нормированный, у каждого свой. Никакой ошибки.

**Чем это опасно:** пустой чанк, случайно доехавший до векторизации, молча
займёт место в коллекции и будет находиться поиском наравне с осмысленными.
Отсекать пустое и слишком короткое обязан чанкер на своей стороне
([02-chunking.md](02-chunking.md)) — на ошибку от сервера рассчитывать нельзя,
её не будет.

## Шаг 12. Замер: помогает ли батчинг

**Прежде чем выполнить — ответьте себе:** сто текстов. По одному — сто
запросов, пачками по 64 — два. Во сколько раз быстрее будет второе?

```bash
python3 -c '
exec(open("/tmp/lab2.py").read())
import time,re,os
src=os.path.expanduser("~/Development/Home/RAG-stand/corpus/TR-114-2026.md")
cl=[l.strip() for l in open(src,encoding="utf-8") if re.match(r"^\d+\.\d+", l.strip()) and len(l.strip())>80]
s=(cl*10)[:100]
emb(["прогрев"])
t0=time.perf_counter()
for x in s: emb([x])
one=time.perf_counter()-t0
print(f"по одному, 100 запросов : {one:.2f} с")
for bs in (16,64):
    t0=time.perf_counter()
    for i in range(0,len(s),bs): emb(s[i:i+bs])
    dt=time.perf_counter()-t0
    print(f"пачками по {bs:2d}           : {dt:.2f} с   ускорение x{one/dt:.1f}")'
```

**Вывод (дословно):**

```
по одному, 100 запросов : 4.17 с
пачками по 16           : 3.57 с   ускорение x1.2
пачками по 64           : 3.68 с   ускорение x1.1
```

**Ускорения нет.** Разброс 3,5–4,2 с — шум. Проверялось шире, чем показано
здесь: четыре потока, четыре слота на сервере — всё то же самое, ≈40 мс
на текст в любой комбинации
([[08-local-stand#Батчинг ничего не ускоряет|полная таблица]]).

Это опровергает утверждение, которое до 07.08.2026 стояло в нашем же
справочнике как «главный рычаг скорости на этапе 2». Оно пришло из статей.
Почему рычага нет — [[#Почему батчинг ничего не даёт|в разборе]].

## Шаг 15. Единая функция формирования текста

Дальше пишется код. Файл — `~/Development/Home/RAG-stand/src/rag_lab/embed.py`,
он уже под гитом.

Сердцевина модуля — вот эти шесть строк:

```python
def text_for(kind: str, text: str) -> str:
    """Единственное место, где текст готовится к векторизации."""
    if kind not in ("query", "document"):
        raise ValueError(f"kind должен быть query или document, не {kind!r}")
    return text.strip()
```

Сейчас обе ветки одинаковы — по результату шага 14. Ценность не в том, что
функция делает, а в том, что она **одна**: и индексация корпуса, и обработка
вопроса пользователя ходят через неё.

**Зачем так рано:** это страховка от самого дорогого дефекта в векторном
поиске. Если документы векторизовать с префиксом, а запросы без — не сломается
ничего. Не будет ни ошибки, ни исключения, ни подозрительного лога. Просто
поиск станет находить хуже, и понять это можно будет только замером на золотом
наборе — то есть на этапе 5, через неделю после того, как дефект внесён.

# Разбор

## Почему один текст даёт два вектора

К шагу 7. Сервер держит кэш промптов. Если пришедший текст уже посчитан
и лежит в кэше, часть вычислений переиспользуется, и порядок операций
с плавающей точкой оказывается другим, чем при расчёте с нуля. Сложение
чисел с плавающей точкой не ассоциативно: `(a+b)+c` и `a+(b+c)` дают разные
последние биты, и на тысяче координат расхождение накапливается.

Замер разложил это на два устойчивых состояния:

| Состояние | Результат |
|---|---|
| Холодный расчёт (кэш выбит другим текстом) | побитово один и тот же вектор, сколько ни повторяй |
| Тёплый (кэш держит этот же текст) | тоже стабильный, но **другой** вектор |
| Два одинаковых текста в одном запросе | побитово равны между собой |

Расхождение холодного и тёплого — косинус 0,99999929, до 1,5·10⁻⁴
на координату при типичном значении 4·10⁻². Параметр `cache_prompt: false`
эндпоинт `/v1/embeddings` игнорирует.

**Масштаб.** Разрыв между «похоже» и «не похоже» на нашем стенде — 0,47
(шаг 6). Расхождение в седьмом знаке не сдвинет ни одной выдачи. Опасно
не оно, а вывод, который из него делают: «векторы совпали — пайплайн верен».
Они законно не совпадут.

## Почему батчинг ничего не даёт

К шагу 12. Батчинг помогает там, где накладные расходы на запрос сравнимы
со счётом: сеть, разбор JSON, планирование на сервере. У нас счёт дороже
всего остального на порядки — 40 мс на пятьдесят токенов уходят в саму
модель на Metal.

Проверялось и предположение, что виноват наш `--parallel 1`: специально
поднимался второй экземпляр эмбеддера на четырёх слотах. Разницы нет
([[08-local-stand#Батчинг ничего не ускоряет|таблица замера]]).

Два следствия. Первое: батчинг в модуле оставлен, но ради меньшего числа
точек отказа, а не ради скорости — обещать ускорение в отчёте нельзя.
Второе, приятное: решение `--parallel 1`, принятое ради экономии памяти,
оказалось бесплатным — параллелизм здесь не даёт ничего, экономия чистая.

**Ограничение замера:** Metal, модель 0,6B, тексты по 50 токенов. На
дискретной GPU с моделью покрупнее соотношение может быть другим. На железе
партнёра — мерить заново, а не переносить вывод.

## Почему кэш оправдан воспроизводимостью, а не скоростью

К шагу 16. Привычное обоснование кэша — «не пересчитывать то, что не
менялось». На нашем масштабе экономить нечего: весь корпус векторизуется
за четыре секунды.

Настоящая ценность видна из шага 7. Без кэша повторная сборка корпуса даёт
не те же векторы, а соседние — в зависимости от того, что сервер держал
в памяти в этот момент. Разница ничтожна, но недетерминирована.

Дальше начинается этап 5 с журналом экспериментов, где сравниваются версии
пайплайна между собой. Если базовая линия и новый замер получены на разных
векторах, любое расхождение метрики в третьем знаке становится необъяснимым:
это улучшение чанкера или сервер иначе прогрелся? С кэшем вопрос не возникает.

Кэш ключуется по `модель + kind + текст`, поэтому смена модели или переход
с `document` на `query` не подсунут старый вектор.

Скорость при этом тоже появляется, и на будущих масштабах она перестанет быть
бесплатным приятным довеском: при переиндексации корпуса крупного клиента
векторизация станет часами GPU-времени.

## Чем этот замер не является

К шагам 13, 14, 17. Цифры recall и MRR здесь получены на черновом разборе
пунктов — регулярка в одну строку, `SH-45` не покрыт вообще (там нумерация
Word, в тексте цифр нет — [ловушка корпуса](06-roadmap.md)). Из 65 ссылок
золотого набора покрыто 49.

Годятся эти цифры ровно для одного: сравнить два варианта запроса между собой
в одинаковых условиях (шаг 14). Базовая линия проекта ставится на этапе 5,
после настоящего чанкера, и её значения будут другими.

Смешивать эти два вида чисел — верный способ через месяц не понять, откуда
взялась цифра в отчёте.
