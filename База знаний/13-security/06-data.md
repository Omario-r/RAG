# Данные: чем является индекс и что значит «удалено»

Файл 6 из 11 в разделе [13-security](README.md). Предыдущий файл
кончился на том, что права надо применять к кандидатам. Здесь —
вопрос уровнем ниже: что вообще является копией корпуса, сколько
таких копий существует и почему команда «удалить документ» почти
никогда не означает, что документа больше нет.

**Состояние на 19.08.2026.** Главная новость года по этой оси —
измеренная, а не предполагаемая восстановимость «удалённых» векторов
из файлов хранилища.

---

## 1. Вектор — не обезличенное производное

Интуиция, с которой приходят к векторной базе: эмбеддинг — это
«хэш смысла», числа, по которым текста не восстановить, поэтому
хранить и передавать их можно свободнее, чем документы. Из этой
интуиции вырастают решения вида «сами договоры внутри, а индекс
можно вынести».

Интуиция неверна, и разбор в
[[04-leakage#4. Инверсия эмбеддингов: что изменилось за год|файле про утечки]]
показывает, насколько именно: из вектора восстанавливается текст,
требование знать модель-жертву снято, шум как защита ослабел.
С поправкой на длину: точная реконструкция подтверждена
на коротких входах, для чанков реального размера независимых
замеров нет, зато вывод атрибутов дословности не требует.

Практических следствий три, и они не про безопасность, а про статус
хранилища:

1. **Векторная база — хранилище тех же данных**, что и хранилище
   документов, и требования к ней те же. «Там только числа» —
   не аргумент ни в разговоре с безопасностью, ни в разговоре
   с юристом.
2. **Отправить чанк в облачный эмбеддер — это отправить чанк.**
   Разница между «мы передаём документы» и «мы передаём только
   векторы» для целей комплаенса отсутствует.
3. **Требование удаления распространяется на индекс** наравне
   с исходниками. И вот здесь начинается техническая часть.

Регуляторная сторона (европейский подход трактует эмбеддинги как
псевдонимизированные персональные данные, право на удаление
требует **проверяемого** стирания, а не функционального) разобрана
отдельно в [09-guidance.md](09-guidance.md); здесь достаточно того,
что требование существует и адресовано именно этому слою.

## 2. Полный список мест, где остаётся копия

Пока не перечислены все места, разговор об удалении бессмысленен.
Список для типичного RAG:

| Где | Что там лежит | Чем удаляется |
|---|---|---|
| Векторный индекс | вектор + payload (часто и сам текст чанка) | API удаления + принудительное уплотнение |
| Лексический индекс | тот же текст в другой форме | своей операцией, отдельно |
| Реляционные реквизиты | извлечённые поля, часто самое чувствительное | своей операцией |
| Кэш ответов | фрагменты в составе прежних ответов | инвалидация по документу — если ключ это позволяет |
| Логи запросов и ответов | вопрос, контекст, ответ | сроком хранения, не точечным удалением |
| Трассировка | поданный контекст целиком | тем же |
| Промежуточные файлы разбора | распознанный текст, картинки страниц | уборкой каталога |
| Снапшоты и резервные копии | всё перечисленное на момент снятия | сроком ротации либо криптостиранием |
| Сырые файлы сегментов индекса | см. раздел 4 | не удаляется вовсе до уплотнения |

Удаление, затрагивающее первую строку, — не удаление. Строки
с четвёртой по восьмую обычно не принадлежат команде, которая
строит RAG, и потому выпадают из рассмотрения целиком.

**Асимметрия, о которой стоит сказать прямо:** права на логи
и трассировку почти всегда шире прав на корпус. Разработчик,
которому не положено читать договоры, обычно имеет доступ
к трассировке, где эти договоры лежат кусками. Это не нарушение
регламента — это следствие того, что трассировку заводили для
отладки, а не для данных.

## 3. Механика мягкого удаления

Векторные базы удаляют отложенно, и на то есть причина, а не
недосмотр. Графовый индекс держит связность через узлы: удалить
узел по-настоящему — значит разорвать пути, которые через него
шли. Поэтому стандартное решение — **надгробие**: точка помечается
удалённой (в некоторых системах — битом в маске), из выдачи
пропадает, физически остаётся до фоновой уборки.

Из этого следуют три факта, каждый из которых удивляет на практике:

- **После вызова удаления данные ещё в файле.** Точка сразу
  недоступна через API — и это всё, что гарантировано.
- **Уборка асинхронна и по условию.** Фоновый оптимизатор
  вычищает сегмент, когда доля удалённого перевалит настраиваемый
  порог. Сегмент, где удалён один документ из тысячи, может лежать
  нетронутым сколько угодно.
- **Запечатанные сегменты неизменяемы.** Достигнув размера, сегмент
  перестаёт переписываться в принципе; всё, что с ним происходит, —
  надгробия и, позже, слияние целиком.

Разбор того же со стороны эксплуатации и качества поиска —
[[База знаний/06-vector-db/06-operations#1. Удаление ломает граф|файл про операции хранилища]]:
там накопление надгробий разбирается как причина деградации recall.
Здесь важно другое: то же самое накопление — причина, по которой
«удалено» не равно «нет».

## 4. Призрачные векторы: измерение вместо предположения

Июньская работа 2026 года (Тринити-колледж) перевела эту тему
из области рассуждений в область чисел. Постановка: три
распространённых хранилища на графовом индексе, по 5000 записей,
10 % помечены удалёнными штатным вызовом API, дальше — доступ
не через API, а **к файлам на диске**: снапшот, резервная копия,
украденный том, любой из обычных сценариев утечки хранилища.

Что восстановилось из «удалённого»:

| Данные | Результат восстановления |
|---|---|
| Биографические тексты | 25,5 % имён людей, 46,4 % географических названий |
| Синтетические клинические записи | 73,4 % пола, 49,9 % фамилий |
| Лица (набор LFW) | 99,17 % верного опознания личности |
| Медицинские изображения | 100 % верной классификации ткани |

Восстановление текста по метрике совпадения оказалось скромным
(0,207) — что согласуется с уточнением про длину из
[[04-leakage#4. Инверсия эмбеддингов: что изменилось за год|файла про утечки]].
Но обратите внимание, чего это не отменяет: **атрибуты
восстанавливаются даже там, где дословный текст — нет**. Для
требования «данные субъекта удалены» разницы между «восстановили
текст» и «восстановили, что это за человек» не существует.

Из мер авторы измеряли три. Шум портит поиск раньше, чем защищает.
Ортогональные преобразования обратимы для того, у кого есть файлы.
Работает третья: **криптостирание** — вектора шифруются ключом
эпохи, при удалении ключ уничтожается, и восстановить нечего.
Цена измерена и мала: около 2,5 мс на 500 удалённых векторов,
плюс подписанное доказательство операции, которое можно предъявить
аудиту.

Ограничение метода надо назвать честно: он закрывает **хранилище**
и ничего не делает с остальными восемью строками таблицы
из раздела 2.

## 5. Что из этого складывается в порядок удаления

Порядок, который следует из механики, а не из здравого смысла:

1. **Удалить точки** из векторной коллекции — по идентификатору
   документа, не по тексту.
2. **Принудительно уплотнить** затронутые сегменты, если система
   это позволяет, либо дождаться уборки и **проверить**, что она
   прошла, а не предположить.
3. **Удалить из лексического индекса** и из реляционных таблиц
   отдельными операциями: они не связаны с векторным хранилищем
   ничем, кроме вашего кода.
4. **Инвалидировать кэш** по документу. Если ключ кэша не содержит
   идентификатора документа, инвалидировать придётся целиком —
   и это аргумент за то, чтобы ключ его содержал.
5. **Отработать логи и трассировку** сроком хранения. Точечное
   удаление из логов обычно невозможно; следовательно, единственный
   рычаг — не хранить дольше нужного и не писать в них лишнего.
6. **Резервные копии** — либо ротация, либо криптостирание.
   Требовать удаления из снятой копии бессмысленно, поэтому решение
   принимается заранее, на этапе выбора схемы шифрования.

Пункты 3–6 — не эксплуатационные хвосты, а половина работы:
на них приходятся все места, где после «удаления» текст остаётся
доступным человеку без всякой инверсии векторов.

## 6. Что мерить на этой оси

**Тест на полноту удаления с канареечной строкой.** Тот же
документ-канарейка из [[04-leakage#6. Что мерить на этой оси|файла про утечки]]:
уникальная строка, которой нет больше нигде. Порядок: загрузить,
дождаться индексации, удалить штатным способом, затем **искать
строку везде**:

- поиском по коллекции и по лексическому индексу;
- по кэшу и по таблицам реквизитов;
- обычным `grep` по логам, трассировке, промежуточным файлам;
- **бинарным поиском по файлам сегментов и по снапшотам** —
  именно этот пункт даёт результат, ради которого тест ставится.

Метрика — число мест, где строка ещё находится. Единица измерения
штуки, целевое значение ноль, а первое измерение почти всегда даёт
не ноль, и это его главная ценность.

**Время до физической уборки.** Отдельная величина: сколько
проходит между вызовом удаления и исчезновением из файлов
при обычной нагрузке. Это не любопытство — это то самое окно,
на которое ссылаются требования о сроках.

**Инвентаризация сроков хранения.** По каждой строке таблицы
из раздела 2: срок и кто имеет доступ. Не метрика, но без неё
предыдущие два замера меряют один угол комнаты.
