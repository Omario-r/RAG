# Пайплайн RAG — 5 узлов

RAG-система строится из пяти основных компонентов. Первые четыре
относятся к подготовке базы знаний (выполняются заранее, при появлении
новых документов), пятый — к обработке конкретного вопроса пользователя
(выполняется на каждый запрос).

## Контур подготовки (offline, при загрузке/обновлении документов)

**1. Document — исходные данные.**
Сырые документы, из которых будет собираться база знаний: страницы
сайта, PDF, регламенты, база договоров, вики-статьи. На этом шаге данные
просто приводятся к текстовому виду, пригодному для дальнейшей
обработки.

**2. Chunking — разбиение на чанки.**
Документ режется на небольшие смысловые фрагменты (чанки). Модель не
может (и не должна) искать по документу целиком — она ищет по чанкам,
поэтому от качества разбиения напрямую зависит качество всей системы.
Подробно: [04-chunking](../04-chunking).

**3. Embeddings — векторизация.**
Каждый чанк превращается в вектор — набор чисел, кодирующий его смысл.
Тексты о похожем оказываются близко друг к другу в этом числовом
пространстве. Подробно: [05-embeddings](../05-embeddings).

**4. Vector DB — хранение.**
Векторы вместе с исходным текстом чанка и метаданными (источник,
раздел, дата) сохраняются в специализированной базе данных, умеющей
быстро находить ближайшие по смыслу векторы среди миллионов записей.
Подробно: [06-vector-db](../06-vector-db).

## Контур запроса (online, на каждый вопрос пользователя)

**5. Retrieval + Generation — поиск и генерация ответа.**
Вопрос пользователя векторизуется той же моделью эмбеддингов, что
использовалась при индексации. Векторная база находит наиболее близкие
по смыслу чанки. Эти чанки вместе с исходным вопросом собираются
в промпт для LLM с инструкцией отвечать строго на основе предоставленного
контекста. Модель генерирует ответ. Подробно: [07-retrieval](../07-retrieval)
и [10-runtime-flow](../10-runtime-flow).

## Почему важно различать эти два контура

Подготовка (шаги 1–4) выполняется редко, но не мгновенно и не бесплатно —
переиндексация большого объёма документов занимает время и стоит денег
(эмбеддинг каждого чанка — это отдельный вызов модели). Запрос
(шаг 5) должен быть быстрым — пользователь ждёт ответ в реальном
времени. Ошибка, допущенная в контуре подготовки (плохой чанкинг,
неподходящая модель эмбеддингов), не может быть исправлена на этапе
запроса — она системно ухудшает каждый последующий ответ, пока база не
будет переиндексирована заново.
