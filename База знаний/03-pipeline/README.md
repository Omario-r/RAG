## Вводный конспект

RAG-система строится из пяти основных компонентов. Первые четыре относятся к подготовке базы знаний (выполняются заранее, при появлении новых документов), пятый — к обработке конкретного вопроса пользователя (выполняется на каждый запрос).

### Контур подготовки (offline, при загрузке/обновлении документов)

**1. Document — исходные данные.** Сырые документы, из которых будет собираться база знаний: страницы сайта, PDF, регламенты, база договоров, вики-статьи. На этом шаге данные просто приводятся к текстовому виду, пригодному для дальнейшей обработки.

**2. Chunking — разбиение на чанки.** Документ режется на небольшие смысловые фрагменты (чанки). Модель не может (и не должна) искать по документу целиком — она ищет по чанкам, поэтому от качества разбиения напрямую зависит качество всей системы. Подробно: [04-chunking](../04-chunking).

**3. Embeddings — векторизация.** Каждый чанк превращается в вектор — набор чисел, кодирующий его смысл. Тексты о похожем оказываются близко друг к другу в этом числовом пространстве. Подробно: [05-embeddings](../05-embeddings).

**4. Vector DB — хранение.** Векторы вместе с исходным текстом чанка и метаданными (источник, раздел, дата) сохраняются в специализированной базе данных, умеющей быстро находить ближайшие по смыслу векторы среди миллионов записей. Подробно: [06-vector-db](../06-vector-db).

### Контур запроса (online, на каждый вопрос пользователя)

**5. Retrieval + Generation — поиск и генерация ответа.** Вопрос пользователя векторизуется той же моделью эмбеддингов, что использовалась при индексации. Векторная база находит наиболее близкие по смыслу чанки. Эти чанки вместе с исходным вопросом собираются в промпт для LLM с инструкцией отвечать строго на основе предоставленного контекста. Модель генерирует ответ. Подробно: [07-retrieval](../07-retrieval) и [10-runtime-flow](../10-runtime-flow).

### Почему важно различать эти два контура

Подготовка (шаги 1–4) выполняется редко, но не мгновенно и не бесплатно — переиндексация большого объёма документов занимает время и стоит денег (эмбеддинг каждого чанка — это отдельный вызов модели). Запрос (шаг 5) должен быть быстрым — пользователь ждёт ответ в реальном времени. Ошибка, допущенная в контуре подготовки (плохой чанкинг, неподходящая модель эмбеддингов), не может быть исправлена на этапе запроса — она системно ухудшает каждый последующий ответ, пока база не будет переиндексирована заново.

## Четыре поправки к конспекту

### 1. Узлов не пять, контуров не два, и поток не линеен

Схема из пяти стрелок верна как перечень артефактов и обманчива как описание архитектуры.

**Узлов порядка пятнадцати.** За словами «Document» и «Generation» спрятаны разбор PDF, восстановление порядка чтения, извлечение таблиц, нормализация, дедупликация, провенанс, обогащение чанка, сборка промпта, проверка цитат, отказ, логирование.

**Контуров четыре.** Кроме индексации и запроса есть контур **обслуживания** (обновление, удаление, миграция эмбеддера) и контур **измерения**. Оба не опциональны: без первого система расходится с корпусом за недели, без второго нельзя ответить «стало ли лучше», а значит нельзя ничего осмысленно менять.

**Поток — одна из четырёх форм.** Последовательная, условная (маршрутизация), ветвящаяся, циклическая. Три из четырёх стрелками слева направо не выражаются, и самая окупаемая из них — условная: она единственная **убирает** работу, а не добавляет.

Разбор — [01-architecture.md](01-architecture.md).

### 2. Самое дорогое место — не нарезка и не модель, а разбор документа

Конспект отводит первому узлу одну строку («данные приводятся к текстовому виду»). По разбору трёх независимых внедрений (Barnett и др., CAIN 2024) самый частый класс отказов — **FP1: нужного содержания нет в корпусе**, и в значительной части случаев это не «не загрузили документ», а «загрузили, но парсер потерял»: таблицу, вторую колонку, скан, сноску.

Отличительное свойство этого узла — он **первый**, поэтому его потеря невосстановима ниже по потоку, молчалива (парсер не падает, он возвращает не тот текст) и системна (ломаются целые классы мест одинаково во всём корпусе, без выбросов, которые привлекли бы внимание).

Разбор — [02-ingestion.md](02-ingestion.md).

### 3. Пятый узел склеивает два, и после поиска отказов больше, чем до него

«Retrieval + Generation» — это два узла с разной природой, разными метриками и разными способами ломаться. Из семи классов отказа **четыре (FP3–FP6) наступают уже после того, как поиск отработал правильно**: нужный фрагмент нашёлся, но не влез в контекст; влез, но модель его не использовала; ответ не в том формате; ответ не той степени конкретности.

Сюда же — целый пласт решений, которого в конспекте нет: бюджет контекста (больше чанков ≠ лучше: деградация на длинном входе начинается задолго до лимита окна), порядок фрагментов (эффект «потерянного в середине»), проверка цитат кодом, право на отказ и его измерение.

Разбор — [11-generation](../11-generation); место узла в конвейере и указатель — [03-generation.md](03-generation.md).

### 4. «Переиндексация стоит времени» — верно, но следствие из этого другое

Конспект делает из дороговизны подготовки вывод «ошибайтесь поменьше». Практический вывод другой: **эта цена платится не один раз, а при каждом улучшении** — при смене парсера, нарезки, эмбеддера, схемы метаданных. Пайплайн, в котором переиндексация не спроектирована, замерзает в том виде, в каком его собрали в первый раз, и всё накопленное знание о том, как сделать лучше, остаётся нереализованным.

Отсюда же вещи, которых в конспекте нет вовсе и которые дешевле завести сразу: идемпотентность загрузки, удаление вместе с обновлением, сверка индекса с источником, версии обработчиков на каждой точке, безопасная схема миграции.

Разбор — [05-operations.md](05-operations.md).

## Правило, ради которого стоит читать раздел

Все узлы связаны одним отношением — **каждый предыдущий задаёт потолок следующему**:

```
корпус ≥ разбор ≥ нарезка ≥ индекс ≥ выдача ≥ контекст ≥ ответ
```

Из него следуют два практических приёма, каждый из которых экономит недели: диагностику ведут **против потока** (от ответа к исходному файлу, двоичными вопросами), а оптимизацию узла ограничивают сверху его долей в общем распределении отказов — то есть сначала меряют, какой узел виноват, и только потом улучшают.
