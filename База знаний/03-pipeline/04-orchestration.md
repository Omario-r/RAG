# Оркестрация — кто решает, каким путём пойдёт запрос

Дата составления: 18.08.2026. Документ разбирает слой, которого в конспекте нет вовсе: управление потоком. В схеме из пяти узлов маршрут один и задан заранее; в системах 2026 года маршрут — это решение, принимаемое на каждый запрос.

Тема пересекается с [09-usage-patterns](../09-usage-patterns) (наивный и агентный RAG) и с осями А и Д из [07-retrieval/01-methods.md](../07-retrieval/01-methods.md). Здесь — инженерная сторона: чем платят, где ставят предохранители и как это измеряют.

---

## 1. Лестница управления

Четыре уровня, и это **не** лестница зрелости: подниматься надо не по порядку, а по необходимости, доказанной замером.

**Уровень 0. Фиксированный маршрут.** Один путь для всех запросов. Предсказуемая задержка, предсказуемая стоимость, тривиальная отладка. Обязателен как базовая линия: любой следующий уровень доказывает прирост относительно него.

**Уровень 1. Маршрутизация.** Запрос классифицируется и идёт своим путём. Единственный уровень, который **одновременно** улучшает качество и снижает стоимость, потому что убирает работу, а не добавляет. Самый окупаемый и самый недооценённый.

**Уровень 2. Итерации.** Поиск → оценка достаточности → уточнение → снова поиск. Сюда попадают Self-RAG (ICLR 2024), CRAG (2024) и большинство «продвинутых» схем. Помогает на многошаговых вопросах, на однократных фактических — почти не помогает.

**Уровень 3. Агент.** Модель сама выбирает инструменты, порядок и число шагов. Максимальная гибкость, максимальная непредсказуемость.

**Цена подъёма, измеренная.** Разборы 2026 года сходятся: рефлексивные циклы потребляют **в 3–10 раз больше токенов**, чем прямой проход. Но важнее не множитель, а смена природы величины: **стоимость и задержка перестают быть числами и становятся распределениями**. На уровне 0 можно сказать «запрос стоит X»; на уровне 3 — только «медиана X, а хвост непредсказуем». Всё, что дальше в этом документе, про то, как удержать хвост.

## 2. Маршрутизация: убрать работу, а не добавить

Мотив утилитарный: многошаговый поиск на простом вопросе — это впустую потраченные секунды, а одношаговый на сложном — неверный ответ. Adaptive-RAG (NAACL 2024) обучает классификатор сложности и разводит запросы по трём маршрутам: без поиска, один поиск, многошаговый поиск.

Классы, которые окупаются почти в любой системе:

| Класс запроса | Маршрут | Почему |
|---|---|---|
| реплика без вопроса («спасибо», «а подробнее») | без поиска | поиск по «спасибо» вернёт случайный мусор |
| точный реквизит (номер, ИНН, дата, срок) | SQL / фильтр | косинус здесь не работает в принципе |
| ограничение по метаданным («за 2025 год») | фильтр + поиск | множество сужается до поиска |
| смысловой вопрос | обычный поиск | базовый случай |
| составной вопрос («чем отличается X от Y») | декомпозиция | это два поиска и сравнение |
| вопрос вне области | отказ | лучший ответ — сказать, что не по адресу |

**Чем классифицировать.** По убыванию дешевизны: правила и регулярные выражения (номер договора, ИНН, дата — распознаются надёжнее любой модели), обученный лёгкий классификатор на эмбеддингах вопроса (CPU, миллисекунды), малая языковая модель (сотни миллисекунд). Начинать разумно с первого: доля запросов, которые ловятся правилами, в предметной области с реквизитами неожиданно велика.

**Главная ошибка проектирования маршрутизатора** — делать его безошибочным. Он ошибётся; вопрос в том, что происходит потом. Маршрут должен **деградировать в общий путь**, а не в тупик: не нашлось по SQL — идём в поиск, а не отвечаем «не найдено». Классификатор с запасным путём при точности 0,8 полезен; классификатор без запасного пути при точности 0,95 опасен.

## 3. Инструменты как узлы пайплайна

Как только появляется маршрутизация, векторный индекс перестаёт быть единственным источником и становится одним из инструментов. Типичный набор для корпуса документов:

- **векторный поиск** — смысловые вопросы;
- **лексический поиск** — точные термины и формулировки;
- **фильтр по метаданным** — сужение до поиска, на стороне базы;
- **реляционный запрос** — реквизиты, агрегаты, «сколько», «какие
истекают»;
- **прямой доступ к документу по идентификатору** — «покажи п. 5.3
договора № 14»: поиск здесь вообще не нужен и только мешает.

Последний пункт стоит отдельного внимания: в системах, построенных вокруг векторного поиска, самый частый практический запрос — «открой вот это конкретное место» — часто решается семантическим поиском, хотя это адресация, а не поиск. Дешёвый инструмент прямого доступа снимает целый класс жалоб.

**Разграничение зон** — не техническое, а смысловое: вопрос, ответ на который обязан быть **полным и точным** (все договоры, истекающие в декабре), не может решаться приблизительным поиском, потому что приблизительный поиск не даёт гарантии полноты. Это свойство метода, а не качества модели, и оно не лечится улучшением эмбеддера.

**Стандартизация шва.** К 2026 году описание инструментов для моделей сошлось на протоколе MCP и совместимых с ним схемах вызова функций. Практическая польза для локального контура: инструменты описываются один раз и переносятся между моделями, включая замену локальной модели облачной и обратно. Это тот же шов, что и OpenAI-совместимый API для моделей ([01-architecture.md](01-architecture.md), раздел 9), — граница, которую полезно держать явной.

## 4. Итерации и агент: где ставить предохранители

Циклический поток без ограничителей — самый быстрый способ получить систему, которая иногда отвечает за 2 секунды, а иногда за минуту и в двадцать раз дороже. Проектируется здесь не стратегия, а **условие остановки**. Минимальный набор предохранителей:

1. **Жёсткий лимит шагов.** Число, а не «пока не будет достаточно».
Практически 2–3 для поиска по документам; больше почти никогда не окупается.
2. **Дедлайн по времени.** Отдельно от лимита шагов: медленный шаг
съедает бюджет так же, как лишний.
3. **Детектор отсутствия прогресса.** Если новая итерация вернула те
же документы, что предыдущая, цикл продолжать бессмысленно — останавливаться. Дешёвая и очень эффективная проверка.
4. **Ограничение накопления.** Контекст не растёт бесконечно:
при фиксированном бюджете свидетельства **заменяются**, а не дописываются (см. [11-generation/01-context.md](../11-generation/01-context.md), раздел 2).
5. **Определённый ответ при исчерпании бюджета.** Что система говорит,
когда бюджет кончился, а уверенности нет: честное «нашёл вот это, но не уверен» с показом кандидатов лучше и молчания, и уверенной выдумки.

**Локальная поправка, которой нет в облачных обзорах.** В облаке итерации стоят денег и почти не стоят времени — вызовы параллелятся на чужих машинах. Локально всё наоборот: деньги не тратятся вовсе, а время растёт линейно, потому что все шаги идут через одну видеокарту. Поэтому локальный агент упирается не в стоимость, а в терпение пользователя, и лимит шагов надо выбирать из бюджета задержки, а не из бюджета токенов.

**Обратная сторона той же монеты — ветвление.** Параллельные поиски по нескольким переформулировкам локально почти бесплатны, если размножается обращение к индексу (единицы миллисекунд), и дороги, если размножается вызов модели. Отсюда локальное предпочтение: **ветвиться по индексу, не ветвиться по моделям**.

## 5. Кэш на уровне оркестрации

Три вида, с разной степенью безопасности.

**Кэш вызовов моделей по точному входу.** Безопасен, полезен при разработке и при повторных прогонах золотого набора: тот же вход — тот же выход, без пересчёта. Экономит часы при отладке.

**Кэш префикса промпта.** Разобран в [11-generation/07-modes.md](../11-generation/07-modes.md), разделы 4–5. Безопасен, требует только правильного порядка частей промпта.

**Семантический кэш ответов** — «похожий вопрос уже спрашивали, отдадим прежний ответ». Соблазнительно и опасно: похожесть вопросов не означает совпадения ответов. «Какой срок оплаты по договору с Альфой» и «...с Бетой» близки по вектору и имеют разные ответы. Для корпуса однотипных документов этот кэш ошибается ровно там, где цена ошибки максимальна. Если применять — то с обязательным совпадением фильтров (тот же документ, тот же контрагент) и с высоким порогом, а не «по косинусу».

## 6. Фреймворк или свой код

Практический вопрос, на который у области есть устойчивый ответ, редко проговариваемый прямо.

**Что фреймворки дают:** готовые коннекторы к источникам, единый интерфейс к десяткам баз и моделей, реализованные схемы (маршрутизация, слияние, циклы), трассировка из коробки.

**Чем платят:** абстракции прячут именно те места, которые в RAG и надо контролировать, — как собран промпт, что именно ушло в индекс, в каком порядке фрагменты. Отладка через чужой слой абстракции медленнее, чем через свой код. Плюс скорость изменений самих фреймворков: код, написанный год назад, часто не запускается.

**Разумное разделение.** Брать из фреймворка **периферию** — парсеры, коннекторы, клиенты баз, трассировку — и писать самому **ядро**: сборку промпта, маршрут, порядок контекста. Для исследовательского проекта, где смысл работы в том, чтобы понимать происходящее, это тем более верно: фреймворк, скрывающий устройство, прямо противоречит цели.

Отдельная линия — **декларативная оптимизация** (в духе DSPy): описать пайплайн как программу и подбирать промпты и параметры автоматически по метрике. Идея сильная и правильная по духу (оптимизировать надо по замеру, а не по вкусу), но требует работающего измерительного контура. Без золотого набора оптимизировать нечего — то есть это инструмент этапа, следующего за [06-evaluation.md](06-evaluation.md), а не предшествующего ему.

## 7. Деградация: что делает система, когда часть её не работает

Раздел, который пишут после первого инцидента, а стоило бы до. Локальный контур делает его актуальнее облачного: модель может не влезть в память, видеокарта — быть занята, сервис — не подняться после перезагрузки.

| Отказал | Разумное поведение |
|---|---|
| реранкер | отдать выдачу первого этапа, пометить как непересортированную |
| эмбеддер запроса | уйти в лексический поиск целиком |
| модель-ответчик | показать найденные фрагменты без ответа — это уже полезно |
| векторная база | лексический поиск, если он есть отдельно |
| маршрутизатор | общий путь по умолчанию |

Общий принцип: **отказ узла понижает качество, а не отменяет ответ**. И второй, менее очевидный: пользователю надо сказать, что режим деградировал. Молчаливая деградация хуже явной, потому что подрывает доверие ко всем ответам, включая правильные.

## 8. Что измерять в оркестрации

Величины, которых нет ни в метриках поиска, ни в метриках генерации:

| Величина | Зачем |
|---|---|
| распределение запросов по маршрутам | видно, работает ли маршрутизатор вообще |
| точность маршрутизатора | по размеченной выборке вопросов |
| цена ошибки маршрутизации | насколько хуже ответ на неверном маршруте |
| распределение числа итераций | хвост важнее среднего |
| доля запросов, упёршихся в лимит | если велика — лимит или стратегия неверны |
| p95 задержки **по маршрутам отдельно** | среднее по всем маршрутам ничего не значит |
| доля деградировавших ответов | здоровье контура |

Последняя строка в таблице задержки — не педантизм. Система с маршрутизацией имеет **разные распределения задержки на разных классах запросов**, и общий p95 смешивает быстрый маршрут с медленным, скрывая и то, и другое.
