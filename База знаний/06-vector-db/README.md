## Вводный конспект

Ниже — исходный конспект из обучающего видео, с которого начинался
раздел, и поправки к нему по внешним источникам.

### Чем векторная БД отличается от обычной

Обычная база данных устроена как картотека по точному совпадению:
найти запись по конкретному ключу — имени, идентификатору, дате.
Векторная база устроена принципиально иначе — это скорее карта, на
которой документы расположены по смыслу: близкие по теме объекты
находятся рядом, далёкие по теме — далеко друг от друга. Когда приходит
вопрос, система ищет не по точному совпадению ключевых слов, а по
близости в этом смысловом пространстве — среди эмбеддингов документов
находятся те, что ближе всего к эмбеддингу запроса.

Технически задача векторной БД — эффективно решать задачу поиска
ближайших соседей (nearest neighbor search) среди миллионов и десятков
миллионов векторов за приемлемое время, что требует специализированных
индексных структур, а не линейного перебора.

### Основные варианты инструментов

- **Chroma** — локальная база, ориентированная на простоту запуска и
  прототипирование.
- **Pinecone** — управляемая облачная база, рассчитанная на серьёзную
  продакшен-нагрузку.
- **Qdrant** — open source база на Rust, self-hosted или облачная.
- **pgvector** — расширение для PostgreSQL, добавляющее векторный
  поиск в уже существующую реляционную базу.

### Как выбирать

Для старта и прототипирования — локальная база без конфигурации.
Для продакшена с высокой нагрузкой — сравнивать управляемые облачные
решения против self-hosted. Если в проекте уже есть PostgreSQL,
pgvector может быть самым простым способом.

## Три поправки к конспекту

### 1. Противопоставление «точность против смысла» устарело

Граница «обычная БД ищет по ключу, векторная по смыслу» была верна
в 2022 году и к 2026-му размылась с обеих сторон. Milvus и Weaviate
умеют полнотекстовый BM25 внутри себя, Elasticsearch пришёл к вектору
со стороны поиска, PostgreSQL с pgvector делает векторный поиск внутри
реляционной СУБД. Граница проходит не по «смыслу против точности»,
а по тому, что система умеет **одним запросом** и чем платит
за масштаб — [05-search-forms.md](05-search-forms.md),
[07-landscape.md](07-landscape.md).

### 2. «Миллионы векторов» — не единственный режим, и не первый

Ниже порядка **десяти тысяч объектов** специализированный индекс
не нужен и обычно не строится: полный перебор быстрее графа. Это
не запасной вариант, а рабочий режим, реализованный по умолчанию
и в Qdrant, и в Weaviate. Разбор и границы —
[02-index.md](02-index.md), раздел 6.

Практически это означает, что до определённого объёма выбор системы
**не решается скоростью поиска**: в этом диапазоне все кандидаты
неразличимы, и решают другие признаки (поправка 3).

### 3. Список из четырёх инструментов смешивает объекты разного рода

Chroma — встраиваемая библиотека с серверным режимом; pgvector —
расширение чужой СУБД; Qdrant — самостоятельный сервер; Pinecone —
сервис, который нельзя запустить у себя вообще. Сравнивать их «между
собой» — то же, что сравнивать SQLite, PostgreSQL и Amazon RDS:
формально все хранят данные, а решения принимаются разные.

И, что важнее, **почти всё, что определяет качество и цену векторного
поиска, лежит не в имени системы, а в конфигурации внутри неё**. Одна
и та же система с квантованием и без различается по памяти в 4–32
раза, с построенным индексом и без — по задержке на порядки,
с индексом по полям и без — по поведению под фильтром качественно.

Отсюда и критерий выбора, которого в конспекте нет: не простота
старта, а **фильтрация** ([04-filtering.md](04-filtering.md)),
**контур и приватность** ([07-landscape.md](07-landscape.md),
раздел 1) и **поведение при обновлениях**
([06-operations.md](06-operations.md)).

## Из чего состоит векторная БД

Почти все дальнейшие различия и почти все грабли живут в конкретных
слоях, поэтому их стоит один раз развернуть:

```
        запрос: вектор + фильтр + limit
                    │
   ┌────────────────▼────────────────┐
   │ 1. API-слой (REST / gRPC)       │  сериализация, батчинг
   ├─────────────────────────────────┤
   │ 2. Планировщик запроса          │  «фильтр до, внутри или после?»
   ├─────────────────────────────────┤
   │ 3. Векторный индекс (HNSW/…)    │  приблизительный поиск соседей
   ├─────────────────────────────────┤
   │ 4. Индексы по полям (payload)   │  инвертированные списки
   ├─────────────────────────────────┤
   │ 5. Хранилище векторов           │  RAM / mmap / SSD / объектное
   ├─────────────────────────────────┤
   │ 6. Журнал и сегменты (WAL)      │  долговечность, слияние, вакуум
   └─────────────────────────────────┘
```

Три следствия, которые в обзорах обычно не проговариваются.

**Индекс — не база.** FAISS, `usearch`, `hnswlib` — это слой 3
и ничего больше: ни долговечности, ни фильтров, ни обновлений
без перестройки. Взять их вместо базы — законное решение, означающее,
что слои 1, 2, 4 и 6 вы пишете сами.

**Медленное место обычно не там, где его ищут.** В типичном
RAG-конвейере поиск в базе — единицы или десятки миллисекунд, а
векторизация запроса и реранкер — сотни. Оптимизация слоя 3 ограничена
сверху его долей в общем времени, и эту долю полезно знать до начала
оптимизации.

**Долговечность — отдельный вопрос от корректности.** Слой 6 отвечает
на «переживёт ли запись перезагрузку», слой 3 — на «найдутся ли
соседи». Эти два вопроса в реальных системах разведены буквально:
запись может быть подтверждена и видна поиску, пока индекс по ней
ещё не построен — [06-operations.md](06-operations.md), раздел 4.
