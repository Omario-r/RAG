# Приватность и ландшафт систем

Файл 7 из 9 в разделе [06-vector-db](README.md). Не ось решения, а два вопроса поверх всех осей: что векторная БД представляет собой юридически и какие системы существуют на середину 2026 года.

---

## 1. Чем векторная БД является юридически

Раздел короткий, потому что вывод приходит извне — со стороны эмбеддингов, — но не повторить его здесь нельзя: он определяет выбор сильнее любой технической характеристики.

**Из эмбеддинга восстанавливается исходный текст.** На коротких фрагментах публикуемая точность восстановления — порядка 92 %, и поздние работы сняли требование знать модель, которой вектор был построен. Разбор — [05-embeddings/01-methods.md](../05-embeddings/01-methods.md), раздел 8.

Три следствия для хранилища:

1. **Коллекция векторов — хранилище конфиденциальных данных**,
а не обезличенных. Режим доступа, резервные копии, снапшоты, экспорт для отладки — всё это операции с исходным текстом.
2. **Облачная векторная БД равна отправке документов наружу.**
Не «почти равна» и не «в спорном случае»: поля обычно содержат текст чанка буквально, а вектор восстанавливается. Формулировка «мы отправляем только эмбеддинги» — это то же действие другими словами.
3. **Отладочный дамп — тот же документ.** Практическая мелочь
с большими последствиями: выгрузка нескольких точек с полями, вставленная в лог или в тикет, — это выгрузка исходного текста.

Отсюда же — зачем в этом разделе вообще разобраны облачные архитектуры, включая экономику объектного хранилища ([01-storage.md](01-storage.md), раздел 4). Понимать, от чего отказываешься и какой ценой, надо явно: разница в пятьдесят раз по стоимости хранения — реальная выгода, от которой отказываются сознательно, а не по незнанию.

## 2. Встраиваемые: без отдельного процесса

| Система | Что это | Замечание |
|---|---|---|
| **FAISS** | библиотека индексов от Meta | эталон алгоритмов; не база: ни полей, ни долговечности |
| **`usearch`, `hnswlib`** | компактные графовые индексы | встраиваются куда угодно, включая мобильные |
| **`sqlite-vec`** | расширение SQLite | вектор рядом с обычными таблицами в одном файле |
| **LanceDB** | встраиваемая БД поверх колоночного формата Lance | работает локально и поверх объектного хранилища; версионирование данных |
| **Chroma** | встраиваемая с серверным режимом | самый низкий порог входа, беднее по эксплуатации |

Общее свойство: **нет отдельного сервиса, нет сетевого доступа, нет своей эксплуатации**. Для закрытого контура это преимущество, а не компромисс.

Где проходит их граница применимости: на объёмах, где начинает требоваться фильтр внутри обхода графа при низкой селективности, фоновая оптимизация сегментов, устойчивость к потоку обновлений и разграничение доступа — то есть всё, ради чего эти библиотеки и не строились. Из списка дальше всех продвинулся LanceDB.

## 3. Серверные open source

| Система | Отличительное | Замечание |
|---|---|---|
| **Qdrant** | Rust; фильтр внутри обхода графа; квантование (TurboQuant); нативные бинарники без Docker | один узел разворачивается без прав администратора |
| **Milvus** | распределённость с самого начала; нативный BM25; до 100 000 коллекций | тяжелее в эксплуатации, рассчитан на кластер |
| **Weaviate** | арендаторы в модели данных; динамический индекс; гибрид штатно | модули для эмбеддингов встроены |
| **Vespa** | поисковая платформа с ранжированием и вычислениями | самая мощная и самая сложная |
| **Elasticsearch / OpenSearch** | зрелый полнотекстовый поиск + квантование BBQ | вектор пришёл к поиску, а не наоборот |
| **PostgreSQL + pgvector** | вектор внутри вашей СУБД | одна транзакция на данные и векторы |
| **pgvectorscale** | надстройка над pgvector | StreamingDiskANN, статистическое бинарное квантование, фильтрация с учётом меток |

## 4. Отдельная база или расширение СУБД

К 2026 году спор «нужна ли отдельная векторная БД» в основном разрешился, и разрешился не победой одной стороны, а **разделением по масштабу**:

- **до ~10–50 млн векторов** PostgreSQL с pgvector (и `pgvectorscale`,
если объём перерастает память) закрывает задачу без отдельного сервиса;
- **выше** начинают окупаться специализированные движки: скорость
построения индекса, шардирование, работа с диском, предсказуемая задержка под конкурентной записью.

Структурный аргумент в пользу расширения СУБД, не связанный со скоростью: **одна транзакция на реквизиты и на векторы** ([06-operations.md](06-operations.md), раздел 4). Расхождение между двумя источниками истины не даёт ошибки, и потому обнаруживается поздно.

### Как читать вендорское сравнение: разбор одного случая

Самый поучительный пример 2026 года.

Timescale опубликовала замер на 50 млн векторов, где `pgvectorscale` даёт 471 запрос в секунду при recall 99 %, а Qdrant — 41, то есть разрыв в 11,5 раза. Замер воспроизводили независимо, и он устоял — **это не подтасовка**.

В том же замере **Qdrant выигрывает по задержке одиночного запроса** (p95 лучше на 39 %, p99 — на 48 %) и по времени построения индекса.

То есть два вендора могут честно опубликовать взаимоисключающие заголовки с одних и тех же данных, просто выбрав разную метрику. Отсюда четыре правила чтения:

1. **Смотреть, какая метрика вынесена в заголовок** — почти всегда та,
где вендор выигрывает.
2. **Смотреть, что вендор не скрыл** — публикация проигрышных строк
повышает доверие к остальным сильнее, чем любые цифры.
3. **Помнить, что пропускная способность и задержка часто
в противофазе.** Пропускная способность растёт батчингом и параллелизмом, которые задержку ухудшают. Для интерактивного продукта, где человек ждёт ответа, значима задержка; для пакетной обработки — пропускная способность.
4. **Смотреть на объём.** 50 млн векторов — масштаб, где различия
архитектур проявляются. На десятках тысяч те же системы неразличимы.

## 5. Управляемые облачные

Pinecone, Zilliz Cloud, Qdrant Cloud, Weaviate Cloud, turbopuffer, Amazon S3 Vectors, Vertex AI Vector Search, Azure AI Search, MongoDB Atlas Vector Search.

Разбирать их по функциям смысла мало — категория за 2025–2026 годы сдвинулась от «векторная БД как сервис» к «векторный поиск как функция существующей платформы». Отдельно от неё выделилась ветка на объектном хранилище с принципиально другой экономикой ([01-storage.md](01-storage.md), раздел 4).

Для закрытого контура вся категория закрыта по причине из раздела 1, и это решение не про цену.

## 6. Что доступно локально

| Приём | Локально | Требует |
|---|---|---|
| Полный перебор | да | ничего |
| HNSW на CPU | да | память под граф |
| HNSW на GPU | зависит от железа | NVIDIA / AMD / Intel; на Apple Silicon недоступно |
| Диск как основное хранилище | да | SSD |
| Квантование (SQ / BQ / RaBitQ / TurboQuant) | да | ничего |
| Фильтр внутри обхода | да | индексы по полям |
| Разреженные векторы, BM25 в базе | да | своя лемматизация |
| Многовекторное представление, MUVERA | да | больше места |
| Объектное хранилище | технически да, практически бессмысленно | S3-совместимое хранилище |
| Управляемый сервис | нет | — |

Вывод, который стоит сформулировать явно: **ограничение закрытого контура почти ни от чего не отрезает**. Из практически значимого недоступны только ускорение построения индекса на GPU (там, где нет подходящего железа) и экономика объектного хранилища — а она нужна на объёмах, до которых большинство прикладных задач не доходит.
