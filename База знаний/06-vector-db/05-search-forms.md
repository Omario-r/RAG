# Ось Д. Формы поиска за пределами одного вектора

Файл 5 из 9 в разделе [06-vector-db](README.md). Пятая ось: что база умеет хранить и искать, кроме одного плотного вектора на объект.

Те же объекты разобраны со стороны модели в [05-embeddings/01-methods.md](../05-embeddings/01-methods.md), раздел 3, и со стороны поиска в [07-retrieval/02-representation.md](../07-retrieval/02-representation.md). Здесь — что с ними делает **база**: как хранит, во что это обходится и что из этого следует при выборе системы.

---

## 1. Именованные векторы: техническая основа

Один объект (в Qdrant — пойнт) может нести **несколько именованных векторов**: например `dense` (плотный, смысл), `sparse` (разреженный, слова), потенциально другие. Это не экзотика, а способ держать несколько представлений одного чанка рядом, чтобы искать по ним одним запросом и сливать выдачи на сервере.

Практическое следствие: **имена стоит закладывать при создании коллекции**, даже если второе представление появится позже. Цена ошибки, впрочем, снизилась: Qdrant с версии 1.18 умеет добавлять и удалять векторные поля без пересоздания коллекции.

## 2. Разреженные векторы и BM25 внутри базы

### Три места, где может жить лексический поиск

Гибридный поиск (плотный вектор + BM25) требует, чтобы где-то жил лексический индекс. Варианты не равноценны:

| Вариант | Плюс | Минус |
|---|---|---|
| Отдельный движок (Elasticsearch, Tantivy) | зрелость, богатый анализ текста | второй сервис в контуре, своя эксплуатация |
| Разреженные векторы в векторной БД | один сервис, одно API, слияние на сервере | анализ текста беднее, лемматизацию делаете вы |
| Нативный полнотекстовый индекс в векторной БД | один сервис, BM25 «из коробки» | зрелость ниже, чем у поисковых движков |

Состояние на 2026 год: Qdrant умеет именованные разреженные векторы и слияние выдач на сервере через Query API; Milvus 2.6 — нативный BM25 через семейство `SPARSE_INVERTED_INDEX` и абстракцию `Function`, превращающую текстовое поле в разреженный вектор прямо при вставке, плюс `hybrid_search` со слиянием RRF или взвешенным; Weaviate — гибридный поиск с BM25 как штатный режим.

### Где здесь морфология

**Для языков с богатой морфологией второй и третий варианты требуют внимания.** BM25 сопоставляет словоформы, а не слова: «неустойка», «неустойки» и «неустойку» для него три разных термина. Для английского это почти неважно, поэтому в англоязычных руководствах шаг не упоминается.

Отсюда вопрос, который надо задавать явно: **кто лемматизирует**. Если разреженные векторы строит встроенный токенизатор базы — это вопрос к его реализации. Если вы строите разреженное представление сами (например, выходом модели вроде BGE-M3) — это ваша ответственность и ваша ручка. Ни один вариант не делает лемматизацию автоматически.

### «Разреженный поиск медленный» — устаревшее возражение

За 2024–2026 годы здесь произошёл скачок. **Seismic** (SIGIR 2024, номинант на лучшую работу) организует инвертированные списки в геометрически связные блоки, каждый со своим вектором-сводкой, и пропускает блок целиком, если сводка не обещает попаданий. Результат — на один-два порядка быстрее прежних инвертированных индексов, и быстрее графовых победителей Big-ANN.

Порядок величины из соревнования: на разреженном треке победитель дал 10 749 запросов в секунду против 93 у базовой линии.

## 3. Многовекторные представления (late interaction)

Модели семейства ColBERT дают **вектор на каждый токен**, а близость считают как сумму максимумов по токенам запроса (мера Chamfer). Это точнее одновекторного представления, особенно на редких токенах.

Проблема для базы арифметическая: чанк из 200 токенов даёт 200 векторов вместо одного. Даже после сжатия это в 5–10 раз больше объёма индекса, и поиск по множествам векторов — другая задача, чем поиск по векторам.

### MUVERA меняет постановку задачи

**MUVERA** (Google, NeurIPS 2024) — самый значимый результат в этой области. Вместо того чтобы учить базу искать по множествам векторов, метод строит **фиксированное представление (FDE, Fixed Dimensional Encoding)**: один вектор для запроса и один для документа такие, что их скалярное произведение приближает многовекторную меру похожести.

После этого многовекторный поиск сводится к обычному одновекторному, и годится **любая существующая база**.

Опубликованные числа:

| Величина | Результат |
|---|---|
| Число кандидатов при том же recall | в 2–5 раз меньше |
| Recall в сквозном сравнении на BEIR | в среднем +10 % |
| Задержка там же | −90 % |
| Дополнительное сжатие FDE квантованием произведений | в 32 раза |

Практическое значение для выбора системы: **многовекторный поиск больше не требует базы, которая «умеет late interaction»**. Он требует ещё одного именованного векторного поля — то есть переходит из категории «сменить систему» в категорию «добавить поле».

## 4. Зачем это может понадобиться

Формы представления — не украшение. Каждая закрывает конкретный класс запросов, на котором одиночный плотный вектор работает плохо:

| Класс запроса | Чем закрывается |
|---|---|
| Точный идентификатор, номер, ИНН, фамилия | разреженный вектор / BM25 |
| Ограничение по метаданным («за 2025 год») | фильтрация ([04-filtering.md](04-filtering.md)) |
| Редкий термин в длинном тексте | многовекторное представление |
| Запрос с множеством верных ответов | разреженный вектор; у плотного здесь **доказанный** потолок |

Последняя строка заслуживает пояснения, потому что это не эмпирика, а геометрия: число различных множеств из `k` результатов, которые способна вернуть система с векторами размерности `d`, ограничено этим `d`. На наборе, построенном ровно на этом пределе, сильные эмбеддеры дают recall@100 от 4,8 % до 12,9 % при 93,6 % у BM25. Разбор — [05-embeddings/01-methods.md](../05-embeddings/01-methods.md), раздел 4.

То есть выбор форм представления — это не «сколько возможностей у системы», а **какие классы вопросов она в принципе способна обслужить**.
