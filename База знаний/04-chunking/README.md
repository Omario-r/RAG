Chunking — самый недооценённый и при этом самый критичный шаг всего пайплайна. Поиск и генерация работают с чанками, а не с документом целиком, поэтому неудачная нарезка не может быть компенсирована ничем дальше по пайплайну: если нужный факт разрезан пополам или потерял контекст, ни хорошая модель эмбеддингов, ни умный реранкер это не исправят.

## Почему разбиение — это не техническая деталь, а источник ошибок

Классический пример проблемы: в документе есть условие с оговоркой, например «ставка X% доступна только при условии Y». Если чанкинг разрежет это предложение ровно на границе оговорки, получится два самостоятельных чанка: один утверждает факт без условия, второй содержит только условие без факта. При поиске по вопросу «какая ставка» система найдёт первый чанк и выдаст ответ без критичной оговорки — формально не выдуманный, но вводящий в заблуждение. Такая ошибка тем опаснее, что она не выглядит как галлюцинация: текст-то реальный, просто неполный.

## Четыре категории методов, от механических к смысловым

### 1. Базовые механические

**Fixed-size chunking.** Текст режется строго через фиксированное число токенов (например, каждые 512), без учёта границ предложений или абзацев.

- Плюсы: быстро, дёшево, предсказуемый размер чанков (важно для
прогнозирования памяти и стоимости).
- Минусы: может разрезать посередине важного предложения или слова,
теряя смысл на границе.
- Когда уместно: однородный текст без сложной структуры, где точность
границ не критична.

### 2. Структурные

**Recursive chunking.** Метод пытается резать по «естественным» границам, начиная с самых крупных: сначала по двойным переносам строк (между абзацами), если кусок всё ещё большой — по одинарным переносам, затем по границам предложений, и только в крайнем случае — по пробелам между словами. Дополнительно применяется **overlap** — часть предыдущего чанка дублируется в начале следующего, чтобы не терять контекст, разорванный на стыке. Это наиболее универсальный и часто используемый метод по умолчанию — на практике он даёт стабильно хорошее соотношение качества и стоимости и обычно оказывается лучшей стартовой точкой, если непонятно, с чего начинать.

**Document-structure-based chunking.** Нарезка идёт по структуре конкретного формата документа: заголовки (`h1`, `h2`, `h3`) в Markdown, теги в HTML, разделы в Word.

- Отлично работает на хорошо структурированных документах: техническая
документация, FAQ, вики-статьи.
- Не работает на «сплошной стене текста» без разметки — резать
попросту не по чему.

**Page-level chunking.** Один чанк равен одной странице PDF-документа.

- Оправдан для документов, где разрезание таблицы или графика посередине
делает оба получившихся куска бесполезными: финансовые отчёты, юридические PDF, мануалы с таблицами. Целая страница сохраняет визуальную и структурную целостность.
- Минус: чанки получаются крупными (порядка 500–1000 токенов на
страницу), что быстрее расходует контекстное окно модели при генерации ответа.

### 3. Семантические

**Semantic chunking.** Каждое предложение документа превращается в эмбеддинг, соседние предложения сравниваются по косинусному сходству. Пока тема не меняется, сходство остаётся высоким; в момент смены темы оно резко падает — в этой точке и делается разрез.

- Идея звучит привлекательно, но на практике метод склонен создавать
слишком мелкие чанки: смысловой поиск находит нужный фрагмент, но ему может не хватать окружающего контекста для полного ответа.
- Дополнительная стоимость: эмбеддинг приходится считать для каждого
отдельного предложения на этапе индексации, а не для укрупнённого чанка.
- Полезен для сложных нарративных текстов, где важно строго сохранить
тематическую целостность фрагмента, но не как стартовый выбор по умолчанию.

**Proposition-based chunking.** LLM переписывает исходный текст в набор независимых, самодостаточных утверждений (propositions): каждое утверждение не содержит местоимений и ссылок на другие части текста — все они разворачиваются в явные сущности.

- Плюс: максимально точный поиск, поскольку каждый факт хранится и
ищется отдельно, без «размазывания» по большому чанку.
- Минус: число чанков вырастает в несколько раз по сравнению
с рекурсивным методом, и каждый исходный чанк нужно дополнительно прогнать через LLM на этапе индексации — это стоит денег и времени.

### 4. Продвинутые архитектурные

**Parent-child chunking («матрёшка контекста»).** Решает фундаментальное противоречие: маленькие чанки дают точный поиск, но мало контекста для ответа; большие чанки дают богатый контекст, но менее точный поиск. Решение — два уровня: маленькие дочерние чанки (например, по 100 токенов) используются для поиска, а найденному дочернему чанку в ответ LLM отдаётся целиком его крупный родительский раздел.

- Плюсы: высокая точность поиска и одновременно богатый контекст при
генерации.
- Минусы: двойная индексация (два уровня чанков нужно хранить и
поддерживать), более сложная реализация. Оправдан для серьёзных проектов, где к качеству предъявляются высокие требования.

**Late chunking.** Переворачивает порядок операций: вместо «сначала режем документ на чанки, потом каждый чанк превращаем в эмбеддинг независимо от остальных» — сначала весь документ целиком прогоняется через модель эмбеддингов, и только затем математически нарезается на чанки. Проблема традиционного порядка в том, что каждый чанк обрабатывается изолированно и не «знает» ничего о том, что было до и после него в документе — если в чанке написано что-то через местоимение без явного упоминания субъекта, контекст, объясняющий, о ком речь, может остаться в другом чанке. Late chunking позволяет каждому итоговому чанку «помнить» глобальный контекст всего документа, потому что векторизация происходит раньше, чем разрезание. Метод пока менее распространён в готовых инструментах, но считается перспективным направлением.

## Практические правила

1. **Нет универсального метода.** Выбор зависит от типа документов и
задачи: рекурсивный — для баз знаний и статей общего назначения; семантический — для сложных нарративных текстов; постраничный — для юридических/финансовых PDF и документов с таблицами; parent-child — для ботов, где важна максимальная точность поиска при сохранении контекста.
2. **Overlap обязателен.** Даже если выбран не рекурсивный метод, стоит
закладывать перекрытие порядка 10–20% между соседними чанками, чтобы не терять смысл на стыке. **Поправка 17.08.2026:** это правило больше не считается безусловным. Систематический разбор на ECIR 2026 не нашёл у перекрытия измеримой пользы при росте стоимости индексации — разбор в [01-methods.md](01-methods.md), раздел 2.2. Перекрытие стало гипотезой, которую проверяют замером, а не обязательной практикой.
3. **Тестировать на реальных запросах.** Теоретически привлекательный
метод может показывать себя хуже на практике конкретных документов и вопросов — единственный надёжный способ проверки — прогнать систему на реальных пользовательских запросах, а не полагаться на общие описания методов.
