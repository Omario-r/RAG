# GraphRAG

## Идея

Обычный RAG хранит информацию как набор независимых текстовых чанков и
ищет среди них по смысловой близости к вопросу. GraphRAG устроен
иначе: вместо плоского набора фрагментов он строит **граф знаний** —
сущности (люди, документы, продукты, понятия) и явные связи между
ними (кто с кем связан, что от чего зависит, что что требует).

Например, для базы про кредитные продукты граф может явно фиксировать
связи вроде «кредит требует документы», «процентная ставка зависит от
срока», «срок влияет на размер платежа» — как структурированные рёбра
графа, а не просто как текст, лежащий где-то в разных документах.

## Когда это нужно

Плоский поиск по чанкам хорошо отвечает на вопросы, ответ на которые
целиком содержится в одном (или нескольких независимых) фрагментах.
Он хуже справляется с вопросами, требующими **многошагового
рассуждения**, где ответ складывается из связывания нескольких фактов,
разбросанных по разным частям базы знаний — например, вопросов вида
«как изменение A повлияет на B через посредство C». Граф знаний
явно хранит эти связи, поэтому по нему проще проследить цепочку
рассуждений от одного факта к другому.

## Компромиссы

GraphRAG — существенно более сложная в реализации архитектура:
необходимо извлекать сущности и связи из текста (часто с помощью
дополнительных проходов LLM на этапе индексации), поддерживать и
обновлять сам граф, и строить поиск и генерацию поверх графовой
структуры, а не только векторного индекса. Для большинства типовых
задач (FAQ, служба поддержки, поиск по регламентам) обычный RAG
с хорошим chunking и гибридным поиском уже даёт достаточное качество,
а GraphRAG будет избыточной сложностью. Имеет смысл рассматривать его,
когда типичные вопросы пользователей систематически требуют
связывания информации из разных частей базы знаний, и обычный RAG
на практике с этим не справляется.
